1. 核心判断（TL;DR）

  • 【C】头部工具已收敛为“同一 agent 运行时的多前端”格局：Codex 覆盖终端 CLI、IDE 插件、桌面应用、浏览器与云任务，Claude Code 覆盖终端、IDE、桌面与浏览器，Qoder 覆盖 IDE、JetBrains 插件、CLI、桌面客户端、云与移动端，OpenCode 以 TUI 与无头服务端为主——形态差异的实质不在能力有无，而在交互回路与可达环境。[S01][S07][S14][S21]
  • 【C】CLI 的结构性优势在“终端即工作现场”：SSH、串口日志、构建、脚本与 CI 都是终端原生的，agent 与现有工具链零摩擦；四家都提供非交互模式（codex exec、claude -p、opencode run、Qoder CLI），可直接进脚本与流水线；Claude Code 官方文档直接写明“CLI 是终端原生工作最完整的面，脚本与 Agent SDK 仅 CLI 可用”，把这一优势从工程推断升级为厂商口径。[S05][S11][S23][S14][S26]
  • 【C】图形客户端的增量价值在“会话与任务是产品化对象”：图形化 diff 审批与计划确认、多会话并行、后台云任务、图形化配置 MCP / Skills / 钩子，这些在纯终端里要么缺失、要么需要自建约定（tmux、配置文件与脚本）。[S01][S07][S14][S20]
  • 【C*】远程场景不是 CLI 独有：CLI 依赖 tmux 等手段在 SSH 会话中保活长任务；云任务形态（Codex 云任务、Qoder Cloud Agents、Claude 云会话）把执行托管在远端侧，断线可续——Claude Code 官方表述为“任务在云端执行，断开连接后继续”；条件为网络与账号可用。[S01][S14][S17][S26]
  • 【P】对“远程 SSH 调试为主、报告产出密集、多任务并行”的工作流：不必二选一——CLI 做终端与自动化主干、客户端做并行任务与报告管线，是形态覆盖最全的组合；若必须精简，优先保留“一个 CLI + 一个图形客户端”的两件套，而不是押注单一形态；客户端位需按接续关系规划——QoderWork 已公告 2027-09-05 停运并建议迁移 Qoder Desktop（内置任务历史、技能与记忆导入）。[S14][S01][S15][S32]

2. 问题、范围与方法

本报告回答三个问题：(1) 主流 agent 工具当前各有哪些运行形态，同一能力在不同形态间是否等价；(2) CLI 与图形客户端的差异本质是什么（能力差异还是交互回路差异）；(3) 对以远程终端工作为主、同时有大量文档产出与多任务并行诉求的工程师，合理的工具组合是什么。

判断准则：能力有无以“官方文档或仓库是否明确定义接口”为准，官方未公开的一律标注推断【P】或缺口【?】，不为厂商补全能力；跨形态对比统一采用“同一任务在两形态下的交互步骤数、可脚本化程度、断连存活能力”作为可比口径。研究截点为 2026-10-09；证据来自两轮基准核验（2026-09-29、2026-10-09）与一次同日补强核验（2026-10-09：平台分工、沙箱、发布说明与可用性边界），未做性能与输出质量实测。本报告本身全程在图形客户端（QoderWork）内完成调研、制图与渲染发布，可视为客户端形态的一手使用样本；但其工作流步骤不构成对任何产品的评测结论。

3. 全球技术基线

四家工具的产品形态已高度重叠，差异从“有没有某个界面”转移到“同一运行时在不同界面下的交互回路”。OpenAI Codex 官方形态包括终端 CLI（openai/codex 仓库，Rust、Apache-2.0、约 12.7 万 stars；支持 npm、Homebrew 与 curl 脚本三种安装方式）、IDE 插件、桌面应用（入口 codex app）、浏览器端云 agent（chatgpt.com/codex）与云任务，并提供 GitHub 代码审查服务，登录使用 ChatGPT 账号或 API key；Claude Code 官方对形态分工有逐条描述——终端是“功能最全的 CLI”，桌面应用面向“可视化评审、并行会话与托管式安装”，Web 提供浏览器内、无需本地环境的运行方式，移动端被定义为“云会话或本地会话的瘦客户端”；Qoder 的产品矩阵扩展为新桌面旗舰 Qoder、Qoder IDE、JetBrains 插件、Qoder CLI、QoderWork（已公告 2027-09-05 停运）、Qoder Mobile、QoderWake 与 Cloud Agents；OpenCode 以 TUI 为核心，另有无头服务端、桌面 BETA 与编辑器集成。截至 2026-10-08 的发布线：Codex v0.162.0、Claude Code v2.1.295。四家的形态与能力映射见图 1。[S01][S28][S07][S26][S14][S32][S21][S02][S08]

扩展机制已经收敛：自定义指令文件（AGENTS.md、CLAUDE.md）、MCP、子代理、钩子、Skills 在四家都能找到对应物（Qoder 以 Hooks 与 Custom Agents 表达，Codex 以 AGENTS.md 与 skills 表达，OpenCode 以插件钩子表达），真正的差异集中在三点：(1) 开源深度——只有 OpenCode（MIT）与 Codex CLI（Apache-2.0）可以被 fork 与改内核；(2) 模型自由度——OpenCode 面向 75+ providers 与任意 OpenAI 兼容端点，Qoder 提供自定义模型与 BYOK，Codex 生态围绕 OpenAI 模型，Claude Code 限定 Anthropic 系（含 Bedrock、Vertex 托管）；(3) 客户端可替换性——只有 OpenCode 把“多客户端”写进架构（无头服务端 + OpenAPI + SSE），其余三家的图形界面与自家账号体系绑定。[S01][S07][S14][S21][S13]

定价结构上，四家均为“订阅 + 额度”模式，档位与核验状态见下表；对个人用户而言，形态选择会直接影响额度消耗方式——headless 与云任务按任务量消耗，交互形态按会话周期消耗。[S16][S31][S37]

4. 国内发展、差距与机会

国内的商业化代表是 Qoder（阿里）：产品矩阵已扩展为七类形态——新桌面旗舰 Qoder、Qoder IDE、JetBrains 插件、Qoder CLI、QoderWork、Qoder Mobile 与 QoderWake（数字员工平台），加上 Agent SDK 与 Cloud Agents；2026-05-20 起原通义灵码更名为 Qoder CN，通过阿里云销售并提供独立 CLI（命令 qoderclicn）。对个人与团队的价值是“一套账号覆盖终端到图形、本地到云端”，合规与治理面（企业版身份、策略、审计）随订阅提供；代价是内核闭源、能力节奏受平台路线图约束、各形态成熟度需逐项验证。两个必须写入选型决策的官方变化：其一，QoderWork 已公告将于 2027-09-05 停运（此前可照常使用），官方建议提前迁移至 Qoder Desktop，后者内置任务历史、技能与记忆的导入工具；其二，定价分离为两套体系——全球版 Free / Pro 20 / Pro+ 60 / Ultra 200 美元/月（Credits 制），国内版免费 300 Credits、专业版 59 元/月、高级版 169 元/月。[S32][S33][S34][S42][S14][S16]

国内其他厂商的工具与 Qoder 同构地覆盖 IDE、插件与 CLI 三面：腾讯 CodeBuddy（IDE + 插件 + CLI，标准版 99 元/月、高级版 199 元/月、旗舰版 999 元/月，三形态共享积分）；字节 Trae（IDE 加独立端 SOLO，境内从免费档到 Ultra 629 元/月起，国际版自 2026-02 起按 Token 计费、档位至 200 美元/月）；百度文心快码 Comate（插件 + AI IDE + CLI，个人免费、专业 70 元/月、旗舰 280 元/月）；智谱 CodeGeeX 提供免费插件，阿里心流 iFlow 的 CLI 已停运并引导迁移至 Qoder。开源侧 Qwen Code（TypeScript、Apache-2.0、约 2.8 万 stars）是最接近“可自建”的国内先例，README 明确说明其最初基于 Google Gemini CLI v0.8.2 二次开发，可作为观望位而非主力。[S38][S39][S40][S41][S24][S21]

一个必须显式写入选型约束的事实是国外工具在中国大陆的官方可用性边界：OpenAI 的支持国家/地区清单不含中国大陆与中国港澳，官方提示清单外访问可能导致账号封禁，Codex 虽已包含于全部 ChatGPT 套餐，服务地区限制未变；Anthropic 的 108 个支持辖区同样不含大陆与港澳，2025-09 起收紧对不支持地区的销售限制，Claude Code 文档要求使用地区在支持范围内——“界面提供中文”不等于“地区开放”。这意味着 CLI 与客户端的形态逻辑在国内同样成立，但“用哪家”需要在形态之外叠加可用性边界。[S35][S36][S37]

差距与机会并存：差距在于国内尚未出现与 OpenCode 同量级的“多客户端架构 + 插件系统 + 开放 SDK”开源运行时【?】，以及国产模型接入 agent 工具链普遍依赖 OpenAI 兼容协议、对工具调用与长上下文的支持差异需逐项验证；机会在于国内工具的形态覆盖、中文文档、本地支付与企业治理已经可以满足主力需求，CLI 与客户端的选择在国内生态内同样成立，不必以形态为由切换供应商。[S14][S16][S24]

5. 关键机制深挖

5.1 CLI 与客户端的能力同源：一个运行时、两种交互回路

接口与实现依据：Claude Code 官方平台文档给出了最直接的分工表述——“CLI 是终端原生工作最完整的面，脚本与 Agent SDK 仅 CLI 可用”，并注明桌面侧重可视化评审与并行会话 [S26]；其各形态共享会话与权限语义，claude -p 提供无头模式 [S07][S11]。Codex 以 codex exec 提供非交互模式，形态含 CLI、IDE 插件、桌面应用与浏览器 [S01][S05]；Qoder CLI 具备 Headless（面向 CI/CD）与并行 Agent 能力，其 Agent SDK 覆盖 planning、工具、会话与权限 [S43][S17]；OpenCode 的 TUI 被官方明确为 client/server 架构中的客户端之一，服务端暴露 OpenAPI 与事件流 [S22]。四家的形态共享同一套权限、MCP 与指令语义。

失效边界：同源不保证同能力。云任务只在云形态存在；图形审批只在图形形态存在；headless 模式若未预置权限策略，会在需要审批的步骤阻塞或直接失败 [S05][S11]；MCP、Skills 与钩子的加载作用域随形态与配置文件目录而变（项目级、用户级、应用级不同）。跨形态迁移的是“能力语义”，不是“会话状态”。

验证条件：同一仓库、同一任务的形态对照试验——分别在 CLI 与客户端完成一次多文件修改；观测三个指标：需要人工介入的审批次数、可脚本化程度（能否无人工完成）、断连后的恢复步骤数；通过条件为两形态均能完成同一任务，且差异可解释为交互回路而非能力缺失。

成本与权衡：CLI 的学习曲线（权限参数、tmux 约定）换来脚本化与零 GUI 依赖；客户端免除终端配置成本，但依赖图形会话在场，且按订阅额度消耗。选择本质上是把成本放在“配置与自律”还是“界面与订阅”。

5.2 远程与长任务：进程生命周期决定形态选择

接口与实现依据：CLI 进程的生命周期绑定 shell / SSH 会话，断开终端即发送挂断信号，长任务需要 tmux、screen 或 nohup 保活；云任务形态把执行搬到远端侧沙箱——Codex 提供云任务与 GitHub 代码审查 [S01]，Qoder Cloud Agents 提供 sessions 与事件流 REST 接口 [S17]，Claude Code 官方表述“任务在云端执行，断开连接后继续”、移动端即这些云会话的瘦客户端 [S26]；headless 模式（claude -p、codex exec、opencode run）在 CI 中天然无人值守，并把结果写入标准输出或文件 [S11][S05][S23]。

失效边界：对 CLI 长任务，本地或 SSH 链路是单点——tmux 保活仍依赖远端主机存活；云任务依赖网络与账号区域可用性，且在断网时无法查看实时进度；headless 模式不适合需要中途人工决策的探索性任务，改判需要重启会话。

验证条件：对照试验“断连重连”——在 SSH 会话中用 CLI 启动一个 30 分钟任务后强制断开，重连后检查任务存活与日志完整性；同一任务改用云任务 / 客户端形态执行，观测断网期间进度可见性与恢复步骤数。通过条件为组合方案下长任务存活率 100%、恢复步骤为零。

成本与权衡：tmux 方案零额外成本但需要自律（会话命名、日志留存、避免孤儿进程）；云任务方案省去保活负担，但按额度计费且受网络与合规约束；两种成本模型对应两类工作（探索式调试 vs 可委派的长任务）。

5.3 审批与权限：从终端策略到图形确认的同一问题

接口与实现依据：Codex 以 sandbox_mode 与 approval_policy 定义沙箱与审批（macOS Seatbelt、Linux Landlock 加 seccomp）[S03]；Claude Code 以 --permission-mode 与 Hooks 控制权限与动作前后拦截，并提供 OS 级 Bash 沙箱（macOS 用 Seatbelt、Linux 与 WSL2 用 bubblewrap），v2.1.295 发布线持续完善 auto 权限模式与 --restricted 受限模式 [S11][S10][S27][S30]；Qoder 在 Hooks 与 Agent SDK 的 permission 面提供同类能力 [S19][S17]；OpenCode 的权限模型为 allow / ask / deny 的逐条匹配规则 [S25]。

失效边界：自动批准（全放行）会放大误操作面，仓库越接近生产、越应保留 ask/deny 面；沙箱机制按操作系统不同——Codex 在 macOS 用 Seatbelt、Linux 用 Landlock 加 seccomp，Claude Code 在 macOS 用 Seatbelt、Linux 与 WSL2 用 bubblewrap，且 Claude Code 的沙箱默认关闭、原生 Windows 下命令不经隔离执行——“有沙箱”与“在用沙箱”是两回事，隔离需要显式配置换取，跨平台行为也不能直接迁移 [S03][S27]；钩子只在预定义事件触发，覆盖不了任意动作。

验证条件：受控仓库注入三类危险动作（删除文件、git push、向外部写数据），分别在四种形态下观察拦截与确认行为；观测指标为拦截率与误放行数，通过条件为危险动作 100% 被拦截或需要确认。该试验可在任意本地空仓库复现，无需真实凭据。

成本与权衡：审批粒度越细，安全面越大、流畅度越低；图形审批降低误批概率但需要人工在场，headless 场景以策略预置换取无人值守。建议把“策略在配置文件里、关键仓库保留交互确认”作为默认姿势。

图 2：CLI 回路（终端即工作现场：就地执行、终端审批、headless 复用）与图形客户端回路（会话列表、图形审批、多任务并行、图形化配置）共享同一套运行时语义；差异不在能力有无，而在交互回路与可达环境。来源：四家官方文档归纳 [S01][S05][S07][S11][S14][S17][S22][S23]；数据口径：2026-09 至 2026-10 官方文档口径。

见图 2，两条回路在中段汇合于同一权限与技能语义，这意味着用户可以“同一能力、按场景换门进入”，而不需要维护两套心智模型；真正的迁移成本在于交互习惯与配置作用域。

6. 演进方向与情景

三个情景的方向判断【S】，观察窗为 2026-2027：情景一（融合，概率最高）——客户端补齐脚本与 headless 入口、CLI 增加图形化审批体验，形态边界模糊化；触发信号包括桌面客户端推出本地 API / 命令行入口、CLI 发布图形审批面板；反证条件为官方明确形态分线且不互相渗透。[S01][S14] 2026 年的发布线提供了支持“融合”方向的近期信号：Codex 近版发布说明（v0.161–v0.162）出现 Guardian 审批决策、多代理 V2 子代理与托管 Git worktree 条目；Claude Code 更新日志（v2.1.295）持续完善 auto 权限模式、--restricted 受限模式与自托管执行器。[S29][S30] 情景二（分工固化）——CLI 与 IDE 归“执行”，客户端归“编排与多任务”，两件套成为默认姿势；触发信号为各形态路线图差异化更新、订阅向多会话/云任务额度倾斜。[S16][S17] 情景三（云优先）——长任务默认在云端沙箱执行，本地运行退居交互式快改；触发信号为云任务额度成为订阅主要计量项、GitHub 审查等云侧能力成为默认入口。[S01][S17]

三个情景的共性信号是“会话与任务的可迁移性”：只要同一会话可以跨形态续接，形态选择就退化为交互偏好问题；反之若会话绑定形态，用户就被迫按任务类型固定分工。建议以季度为周期核查两类官方更新：形态间能力同步率、用量计量结构的变动。[S07][S14]

7. 建议与验收

直接回答“CLI 是不是更好”：分场景，不是全局问题。对终端原生、远程 SSH、构建与脚本化任务，CLI 更优（就地执行、可管道、可 CI）；对长任务后台、多任务并行、报告与文档产出、图形化配置管理，客户端更优（会话托管、图形审批、技能与 MCP 的应用级管理）。对“远程调试为主 + 报告产出密集 + 多线程并行”的工作流，最优解是两件套组合：CLI 做主干（codex CLI 面向终端、远程与自动化），客户端做管线（Qoder 桌面客户端面向报告生产、并行任务与配置管理）；CLI 与客户端共享同一运行时语义，组合不会带来双份学习成本，各场景匹配见图 3。对精简诉求，优先裁掉“第二客户端”，而不是保留“双 CLI”。需要跟踪的官方变化：QoderWork 已公告将于 2027-09-05 停运（此前可照常使用），客户端位建议直接规划到接续产品 Qoder Desktop——官方提供任务历史、技能与记忆的导入工具，存量配置可按此路径迁移。[S05][S11][S14][S17][S32]

8. 不确定性与研究限制

本报告未做性能与输出质量实测，形态优劣结论均基于官方文档口径与交互回路分析，实际体验可能因版本与网络环境而异。定价与额度结构为 2026-09 至 2026-10 核验口径（含 2026-10-09 补强），各厂商调价频繁，验收经济性前应重新核对官方页面 [S16][S31][S37]；Codex 档位具体价格因官方定价页在本研究网络不可直接访问而未逐项核验【?】，验证路径为在可访问网络中核对官方定价页。Qoder CLI 与 Qoder Desktop 的能力边界按概览文档口径核验、未逐项实测【?】，验证路径为对照官方 CLI 与桌面文档逐条执行；国内工具本版已纳入 Qoder CN、CodeBuddy、Trae 与 Comate 的形态与计费口径 [S34][S38][S39][S40]，但 Teams 与企业版定价、QoderWork CN 是否同步停运、促销价与常规价并存等细节仍需以官方购买页为准【?】。可能推翻本报告主要结论的观察是：某形态宣布停止维护（本期已出现一例——QoderWork 公告 2027-09-05 停运，客户端位需迁移至 Qoder Desktop [S32]），或形态间会话不可迁移的架构决定被明确——两者都会改变第 7 节的组合建议。[S01][S14][S32]

  • 检索与核验顺序：官方文档与仓库元数据优先；两轮核验（2026-09-29 与 2026-10-09）；第三方资料只用于线索发现，不作为结论依据。
  • 证据等级与标记：【C】为官方一手来源核实；【C*】为带条件结论；【S】为情景判断；【P】为工程判断；【?】为未核实缺口，均按“可靠性标记”节使用。
  • 对照口径：跨工具与跨形态统一按“官方文档是否定义接口”判定能力有无；形态能力以文档口径为准，不替厂商补全未公开能力。
  • 复现方式：本报告第 5 节的验证条件均给出可在空仓库复现的对照试验；图 1 至图 3 由 ai-agent-tools-figs.py 生成，SVG 源文件与 PNG 预览随报告提供。
  • 写作环境：本报告全程在 QoderWork 图形客户端内完成（调研、制图、校验与渲染发布），可视为客户端形态的一手使用样本。
