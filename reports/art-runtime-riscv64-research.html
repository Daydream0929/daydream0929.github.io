摘要

  • ART 是 Android 的 Java 运行时：编译期由 dex2oat 把 DEX 编译成 oat/vdex/art 三种产物，运行期由 libart 在 zygote 中建立 Runtime（堆/类表/线程/解释器/JIT/入口点），应用进程经 fork 共享 boot image，未编译方法默认落到 nterp 快解释器再按热度进入 JIT/AOT [S01][S24][S25]。
  • RISC-V64 在公开 ART 中的支持自 2023-01 的骨架提交开始，Android 14 分支只有不可执行的骨架（解释器被显式排除，IsNterpSupported() 返回 kRuntimeISA != kRiscv64），Android 15 分支已包含下述实现：全量 codegen、JNI 编译、nterp、intrinsics 与 oat 相对重定位 [S06][S09][S12][S14]。
  • 当前（android17-release，26Q2 线）RISC-V64 的优化编译器、nterp、JIT、GC、JNI 相关实现已进入本报告核对的源码；缺口集中在三处事实点：JIT 的 arm 系专属快路径（pattern matcher、fast baseline 编译器）不对其它架构提供，RVV 仅有汇编器与向量寄存器分配基础设施而向量指令代码生成仍为 UNIMPLEMENTED(FATAL)，以及 GC 读屏障没有标记寄存器（marking register）导致逐寄存器入口点；源码落地不等于正式 Android ABI/CTS 或产品支持——本稿未做真机验证，支持层次以附录证据为准 [S24][S25][S26][S29]。
  • 按所统计公开提交记录，Google 是贯穿观察期的主要贡献方（riscv 路径提交约占三分之二），T-Head/Alibaba 与 Syntacore（Synopsys）承担了后端主体构建，SiFive、ARM 有零星贡献；2025-09 之后新提交密度明显下降，最新 android17 安全分支（截止 2026-07-10）无 RISC-V 提交；提交邮箱统计不能认证维护权限或治理归属 [S01][S31]。
  • 公开 main 分支自 2025-03-26 起冻结，Android 17（26Q2）开发通过 release 分支可见；任何“跟 main 就是最新”的假设在本主题（及整个 ART）上都已不成立，需以 release 分支/月度发布列车为准 [S01][S02]。

背景与现状

ART 在 Android 中的位置与形态。 ART 取代 Dalvik 成为 Android 的默认运行时后，以 Mainline（APEX com.android.art）形式随系统更新，主要职责是加载 DEX 字节码、执行 Java 代码（解释/JIT/AOT 三种形态并存）、管理 Java 堆与并发语义、并对外提供 JNI、反射、调试（JVMTI）等接口。其源码位于 AOSP 的 platform/art 仓库，与 libcore（Java 类库实现，含 core-oj/core-libart）、bionic（C 库，提供 pthread/mmap/TLS/dlopen）、frameworks/base（zygote、AndroidRuntime、ZygoteInit）以及构建系统（Soong、dexpreopt）耦合。运行时的部署形态、编译产物与启动链在本文中均以公开源码为准：Runtime::Init 依次建立 Monitor/ThreadList、gc::Heap（boot image 的装载就发生在 Heap 构造函数内部）、fault manager（并注册 nterp 代码段）、JVM 环境与 ClassLinker [S25]。

图 1：ART 在构建期/运行期/系统依赖中的位置总览（来源：[S01][S23][S25][S36] 源码与结构盘点，本项目绘制）。 读图要点：构建期管线（dex2oat/odrefresh/artd）产出 vdex/oat/art image 供运行期消费；运行期 libart 内部划分 Runtime 核心、执行引擎与 JNI/调试面；系统依赖面（libcore/bionic/frameworks/APEX）与 zygote fork 把三者串联。

产物与执行形态。 编译期产物有三种：vdex（原 DEX 的快速验证数据与 quickening 信息）、oat（编译后的机器码与元数据，含 boot classpath 校验键）、art image（堆对象快照，含未编译方法的 trampoline 入口）。设备侧由 odrefresh（开机时）与 artd（ArtService）触发 dex2oat，判定条件与编译过滤器（CompilerFilter：verify/space/speed/space-profile/speed-profile/everything 等 8 档）直接决定一个应用“哪些方法有 AOT 代码”，这是同一用例在不同设备/构建下性能差异的第一来源 [S32][S33]。运行期执行形态则叠加 JIT（默认启用，UseJitCompilation=true）与 nterp（默认快解释器）：未编译方法入口在镜像中先是 nterp trampoline，加载时若 CanRuntimeUseNterp() 成立则被原地改写为 ExecuteNterpImpl，否则退回 quick-to-interpreter bridge [S24][S25]。

分支模型（2025 年变化）。 2025-03-26 之后，platform/art 的公开 main 停止更新（tip 6484611f，其 tree 与官方网页核对一致），开发转入内部主线并只通过 release 分支发布：android16-release（25Q2，即 android-16.0.0_r1/r2）、android16-qpr1-release（25Q3，r3）、android16-qpr2-release（25Q4，r4）、android17-release（26Q2，合并目标名 26Q2-release）及其安全分支；截止 2026-10-16 公开 refs 中没有任何 android18/26Q4 分支 [S01][S02][S03][S04]。本报告全部结论锚定到上述 pin；“AOSP 17”指 android17-release 这条官方分支，不把 main 当作更新的别名。

RISC-V64 支持现状速览。 2023-01 起，Alibaba（T-Head 系）与 Google 的工程师把 RISC-V64 骨架带入 platform/art；2023 年中至年末由多方补齐汇编器、codegen、JNI 约定与 nterp 解释器，2024 年补 C 扩展、Zba/Zbb/Zbs 与大量 intrinsics，2025 年进入“维护与打磨”阶段（如 2025-09 的向量寄存器分配 part 1）[S06][S07][S09][S15][S16]。到 android17-release，riscv64 专属源码约 60 个文件（含汇编器 7800+ 行、codegen 7400+ 行、intrinsics 5800+ 行与 170 个 intrinsics 实现），并配有 test/458-checker-riscv64-* 等回归用例与 Cuttlefish/Orange Pi 的测试记录 [S25][S26][S31]。同时必须强调三个“有源文件”≠“能力完成”的例子：mterp/riscv64 目录最初只是 unimp 占位桩 [S10]；RVV 指令在汇编器、反汇编器与测试中可用，但优化编译器的向量指令生成在 android17-release 仍是 LOG(FATAL)/UNIMPLEMENTED [S26]；JIT 的 fast baseline 编译器仅 arm64，riscv64 的 JIT 只有通用优化管线 [S24][S31]。

研究口径。 本文以公开仓库固定 commit 为唯一引用来源（联网通道与限制见附录 C）。二进制运行、真机测量不在本任务范围；涉及“性能”的内容一律写成机制解释或待验证假设，不给出未实测的提升数字。RISC-V64 与 arm64 的差异均取自源码事实，而非推测。

4.1 从进程启动到执行准备：Runtime、boot image、DEX 与类加载

见图 2（启动与首方法执行链）。读图要点：镜像的装载不是独立步骤，而是嵌在 Heap 构造函数里；未编译方法的入口在“镜像生成 → 镜像加载”两处各改写一次；nterp 是入口改写的主角 [S23][S31][S38]。

调用链（自下而上均可在 android17-release（下称 a17r）源码复核）：app_process 侧（framework，AndroidRuntime.cpp，不在 art 仓库）触发 JNI_CreateJavaVM（runtime/jni/java_vm_ext.cc:1237）→ Runtime::Create（runtime/runtime.cc:1007，ParseOptions 于 :974）→ Runtime::Init（:1625）→ Runtime::Start（:1098）。Runtime::Init 的关键顺序：Monitor::Init（:1692）→ boot classpath 参数落位（:1695-1726）→ ThreadList/InternTable（:1766-1769）→ gc::Heap 构造（:1894），boot image 的装载在 Heap 构造函数内（runtime/gc/heap.cc:520 调 ImageSpace::LoadBootImage，runtime/gc/space/image_space.cc:3016）→ fault manager 初始化并登记 nterp 代码段（:2038-2074，CanRuntimeUseNterp() 为真时把 OatQuickMethodHeader::NterpMethodHeader 的代码范围加入 generated-code 范围）→ JavaVMExt::Create（:2081）→ Thread::Attach（:2096；此后入口点按线程初始化：Thread::Init → InitEntryPoints，riscv64 实现在 runtime/arch/riscv64/entrypoints_init_riscv64.cc:93）→ ClassLinker 创建与 InitFromBootImage（:2113/:2118）。Runtime::Start 随后执行 root clinits（Thread::FinishStartup → RunRootClinits，这是运行时内部最早的 Java 方法执行）、按需 CreateJit()（:1149-1150）、创建 system class loader、启动 daemon 线程 [S23][S31][S38]。

boot image 的装载与校验（image_space.cc）：BootImageLayout::Load 先按 BCP 组件做 VerifyImageLocation 与 ReadHeader（主镜像 header/oat 校验失败时，若允许内存编译（zygote 默认）走 CompileBootclasspathElements 兜底，否则整体失败）→ BootImageLoader::LoadImage 预留地址空间并按需重定位（Relocator::RelocateBootImage 修正镜像内指针、ArtField/ArtMethod 的声明类与 quick entrypoint）→ OatFile::InitializeRelocations 修补 .data.img.rel.ro 镜像内引用。校验对包括：镜像 OatChecksum 与 oat 头一致、boot classpath 位置串与运行期一致、逐 dex 的 multidex checksum 与真实 dex 一致（失败信息如 ValidateOatFile found checksum mismatch … (0x%x != 0x%x)）[S23][S38]。

首个 Java 方法的入口决策：镜像生成时（dex2oat/linker/image_writer.cc:3530），无 quick code 的方法按序取：native → GenericJNI trampoline；CanMethodUseNterp → nterp trampoline（需 clinit 者先走 resolution trampoline）；否则 quick-to-interpreter bridge。镜像加载时（class_linker.cc:2332-2342，AddImageSpace 内）把 nterp trampoline 原地改写为 interpreter::GetNterpEntryPoint()（条件即 CanRuntimeUseNterp()：非 debuggable、非 InterpretOnly、无 entry/exit stubs、非异步异常待决、JIT 非 JitAtFirstUse 等，nterp.cc:61-75）。方法调用经 ArtMethod::Invoke（art_method.cc:372）：未 started 或强制解释 → EnterInterpreterFromInvoke；否则直接跳 entry_point_from_quick_compiled_code（riscv64 经 art_quick_invoke_stub，quick_entrypoints_riscv64.S:266）[S23][S25][S38]。

失效边界与对照事实：镜像格式版本在 a17r 为 119（runtime/oat/image.cc:39，a16q2 与 main 为 118），版本或 BCP 校验不一致将拒绝镜像并回退（内存编译或纯解释路径）；debuggable/InterpretOnly（-Xint）下加载时所有方法被改指 quick-to-interpreter bridge，nterp 全局关闭。可复现观察：设备上可用 oatdump（art/oatdump）查看 boot image 中某方法的 entrypoint 与 dex 数据（前提：与镜像同版本的 oatdump 二进制）；带 -Xint 与不带对比同一应用的 logcat 中解释器相关日志。成本与权衡：镜像直映 + 加载时按需重定位减少了启动拷贝，压缩镜像走 LZ4 块解压（可并行）；executable 模式下对 oat 做 madvise 被注释标注为“显著改善 ZygoteInit 类预加载性能”（image_space.cc OpenOatFile 段注释）——这些是可复算的启动成本点 [S38]。

DEX、类加载与校验

DEX 的打开与校验已收敛到 DexFileLoader（a17r：libdexfile/dex/dex_file_loader.cc:384 DexFileLoader::Open；旧的 DexFile::Open/OpenInternal 已不存在）：读 magic → ZIP 分支（zip 内条目按 CRC32 作 location checksum）或普通文件 → OpenCommon（:472）构造 StandardDexFile → 可选 dex::Verify（dex_file_verifier.cc，CheckHeader 于 :616：magic/版本/header_size/endian/Adler32 checksum，v41 额外校验 container 字段；verify_checksum=false 时 checksum 不符仅告警）。magic 版本表支持 035/037/038/039/040/041（standard_dex_file.cc:29-40，036 因历史 bug 弃用）。CompactDex 已从主线移除：compact_dex* 文件在 a12–a16 存在（a16 已只剩 7 个），a16q2 与 a17r 为 0 [S39][S38]。

类加载主链（runtime/class_linker.cc）：FindClass（:3266）→ 命中 LookupClass 后 EnsureResolved，未命中走 DefineClass（:3505：AllocClass → PreDefine 回调 → RegisterDexFile → SetupClass → InsertClass（竞争失败转 EnsureResolved）→ LoadClass（:4491，成员加载现由 ClassAccessor+LoadClassHelper 承担，旧 LoadClassMembers 已不存在）→ LoadSuperAndInterfaces → LinkClass（:6646：LinkSuperClass/LinkMethods（现为 LinkMethodsHelper，vtable/IMT 构建与 embedded vtable 填充）/字段链接 → SetStatus(kResolved)）→ 由调用方按需 InitializeClass（:5938）。类状态机在 runtime/class_status.h:111-129：kLoaded → kResolved → kVerified → kInitialized → kVisiblyInitialized；EnsureResolved 的自旋+yield 协议（:2921-2948）与 InitializeClass 的 ObjectLock<Class> 双检协议（JLS 12.4.2）是并发正确性核心 [S38]。

校验器（runtime/verifier/method_verifier.cc）按 dex_pc 扫描指令宽度、try/catch、类型流；失败分级 kNoFailure/kSoftFailure/kHardFailure（verifier_enums.h:35-41）：硬失败抛 VerifyError 并置 kErrorResolved；软失败在 AOT 下映射为 kRetryVerificationAtRuntime（运行期重验、方法不可编译）或 kVerifiedNeedsAccessChecks；-Xverify:none|remote|softfail 由 parsed_options.cc:381-387 解析、默认 kEnable [S38]。方法分派：FindVirtualMethodForVirtualOrInterface（mirror/class-inl.h:531）经 vtable/iftable 入口定位；未解析调用由 art_quick_resolution_trampoline（riscv64 汇编 quick_entrypoints_riscv64.S:872，C++ 端 quick_trampoline_entrypoints.cc:1205）完成解析并跳转。异常路径：ArtMethod::FindCatchBlock（art_method.cc:328）用 CatchHandlerIterator 匹配 try item；编译代码异常由 QuickExceptionHandler 分派（quick_exception_handler.cc:146）；riscv64 的 art_quick_throw_null_pointer_exception 等桩在 quick_entrypoints_riscv64.S:826-865 [S25][S38]。

反射与代理：Method.invoke 落入 reflection.cc:698 InvokeMethod → InvokeMethodImpl（:477，virtual/interface 经 FindVirtualMethodForVirtualOrInterface 重定向）；代理类生成 ClassLinker::CreateProxyClass（class_linker.cc:5577，native 入口 java_lang_reflect_Proxy.cc:36）；MethodHandle 核心在 mirror/method_handle_impl.{h,cc} 与 method_handles.cc（invoke 变换 :366，含 RISC-V64 上 invokeExact 家族在 2024-12 至 2025-03 补齐 virtual/static/interface/direct 的提交记录，见 §4.6）[S38][S40]。

镜像兼容性（a17r）：AddImageSpace（class_linker.cc:2096）依次校验 oat header 有效性、kClassPathKey、kBootClassPathKey（与 GetBootClassPathLocations() 拼接串比对）、kBootClassPathChecksumsKey（与 GetBootClassPathChecksums() 比对，镜像块前缀 'i'、尾部 dex 前缀 'd'）；任一不匹配即拒绝镜像。验证条件示例：改动 boot classpath 或升级 BCP dex 后，同目录旧 boot.art 会被拒绝并触发内存编译兜底或解释执行——这是“镜像兼容性”最直观的负向用例 [S38]。

4.2 双执行引擎（一）：nterp 解释器与 RISC-V64 状态

解释器谱系（结论先行）：经典 computed-goto mterp 已于 2021-07 被整体删除（提交 e4f983c808 "Remove mterp."；该提交未进入 android12 分支，但 13 分支及其后均无经典 mterp 目录）[S05]。此后 ART 的“快解释器”只有 nterp 一种，其余情况回退 C++ switch 解释器（runtime/interpreter/interpreter_switch_impl0.cc）[S23][S25]。runtime/interpreter/mterp/ 下的 armng/arm64ng/x86ng/x86_64ng/riscv64 各目录均是 nterp 的架构实现（“ng”即新解释器；riscv64 目录因从未有过经典 mterp 而沿用本名），其生成框架仍是 python 模板（gen_mterp.py）[S28]。

RISC-V64 的 nterp 时间线（公开提交）：2023-04-10 e98bd2994b 先以 unimp 指令建桩（当时执行会对未实现指令陷停）[S10]；同日到 4 月完成基本约定与 ExecuteNterpImpl 初版；2023-06-15 993bcb1f02 "riscv64: Enable nterp with a method filter" 打开启用开关，并带方法过滤器（排除含 try 块或未实现 opcode 的方法），提交信息记录了上游作者的测试步骤与观察（Cuttlefish riscv64 镜像启动 zygote 并检查 logcat 无 SIGILL；属外部测试记录，非本报告实测）[S12]；2023 年余下月份逐一补齐 opcode（invoke 家族、AGET/APUT、IGET/IPUT、SPUT/SGET、const、浮点等）；2024-01-29 f1e2ce6390 启用 nterp 的异常捕获（测试 839-clinit-throw；测试方法为 Cuttlefish VM over SSH，见 §4.5）[S17]。作为负向对照：Android 14 分支（android14-release）的 IsNterpSupported() 为 return !kPoisonHeapReferences && kReserveMarkingRegister && kRuntimeISA != InstructionSet::kRiscv64;——riscv64 被显式排除，该分支上解释执行只能走 C++ switch 解释器 [S09]。

nterp 工作机制（a17r）：入口符号 ExecuteNterpImpl（带 clinit 变体 ExecuteNterpWithClinitImpl），GetNterpEntryPoint() 供 ArtMethod 直接指向 [S23]。riscv64 汇编侧固定寄存器约定（mterp/riscv64/main.S）：s1=xSELF（Thread）、s2=xFP（解释帧指针）、s3=xPC、s4=xINST、s5=xIBASE（computed-goto 基址）、s6=xREFS（引用影子数组基址）；分发是“handler 表基址 + opcode步长”的 computed goto，CheckNterpAsmConstants 校验 handler 尺寸：arm/arm64 有四套 16KiB 对齐 handler 表，其余架构（含 riscv64）为单套 [S23][S28]。

// runtime/interpreter/mterp/nterp.cc（a17r，节选）

4.3 编译分层与内存回收：JIT/profile 与 GC

图 3：nterp↔JIT↔AOT 分层与 OSR/退优化路径（来源：[S23][S24][S38] 源码研读，本项目绘制；RV64 缺口以注记标出；此图为固定源码分析，非设备实测）。 执行引擎与分层见图 3，读图要点：未编译方法入口先落 nterp；方法与回边热度驱动 baseline/optimized 两级 JIT，OSR 由解释器自跳或 osr_stub 完成；AOT 覆盖范围由编译过滤器圈定；去优化把帧还原回解释器重编。

JIT 架构与线程模型（a17r，runtime/jit/）：Jit 持有代码缓存 JitCodeCache（容量上限 64MB，zygote 继承 shared region 与进程私有 private region 分离，ProfilingInfo 只能放私有区）、编译线程池（1 个 worker，前台优先级 9/zygote 19）、以及 zygote 共享映射。任务分五类队列（generic/OSR/fast/baseline/optimized），出队优先级为 generic→OSR→fast→baseline→optimized；JitCompileTask 执行 CompileMethodInternal，fast 编译失败自动回退 baseline [S24][S38]。

热度与阈值（要点：默认阈值极大，“什么触发编译”主要由框架属性下调后的值决定）：kJitDefaultWarmupThreshold=0xffff、kJitDefaultOptimizeThreshold=0xffff（jit_options.cc），设备实际值由 framework 通过 -Xjitwarmupthreshold/-Xjithreshold 下发；JitAtFirstUse() = (optimize_threshold==0)（仅 zygote DEBUG_ALWAYS_JIT 标志会设置）。OSR 没有独立阈值：-Xjitosrthreshold 已在忽略参数表内，kJitRecheckOSRThreshold 无使用点。解释器侧热度来源：nterp 方法入口递减 hotness_count_（归零回调 NterpHotMethod）、回边走 NterpHotnessCheck、查表慢路径 +0xf；switch 解释器则 Jit::AddSamples [S23][S24][S38]。

分层路径（可复述的调用链）：未编译方法（nterp）— NterpHotMethod（nterp.cc）→ Jit::PrepareForOsr（若回边且已有编译代码）与 Jit::MaybeEnqueueCompilation → interpreter→baseline（可分配 ProfilingInfo 且非 native）或直接 optimized；baseline→optimized 由基线代码内 MaybeIncrementHotness 递减 ProfilingInfo::baseline_hotness_count_，归零进 CompileOptimizedSlowPathRISCV64 → art_quick_compile_optimized（riscv64 汇编 quick_entrypoints_riscv64.S:916）→ Jit::EnqueueOptimizedCompilation。OSR 有两条实现：nterp 回边由解释器自己完成帧迁移（PrepareForOsr 返回 OsrData 后，nterp 汇编丢弃当前帧、按 OsrData 拷贝 vregs 并直接 jr 到 native_pc，riscv64 mterp/riscv64/main.S:610-634）；switch 解释器则调 art_quick_osr_stub（riscv64 实现存在），要求目标 dex_pc 有 OSR stack map（CodeInfo::GetOsrStackMapForDexPc）[S24][S28][S38]。

去优化：编译代码命中去优化点 → invokeRuntime(kQuickDeoptimize) → art_quick_deoptimize_from_compiled_code（riscv64 汇编 :716-722）→ artDeoptimizeFromCompiledCode；Thread::Deoptimize → QuickExceptionHandler::DeoptimizeStack/DeoptimizeSingleFrame → DeoptimizeStackVisitor 逐帧重建解释器帧：nterp 帧直接拷贝寄存器/引用双数组（HandleNterpDeoptimization），optimized 帧按 stack map 的 GetStackMapForNativePcOffset/GetDexRegisterMapOf 把寄存器/栈位回写 ShadowFrame（HandleOptimizingDeoptimization）。instrumentation 强制去优化（debugger 挂起、方法 tracing）走 Instrumentation::Deoptimize(*) → 逐线程栈重写。注意：全树不存在名为 DeoptimizationEntry 的符号，QuickEntryPoints::pDeoptimize 实际初始化为 art_quick_deoptimize_from_compiled_code [S25][S29][S38]。

Profiles 与 PGO：profile 文件 magic 'pro\0'，普通版本 '015'、boot image profile '016'（profile_compilation_info.cc），boot profile 为 .bprof。运行期 ProfileSaver（保存周期 40s、最少 10 方法/10 类、内联缓存阈值 4000 等默认值）把采样写入 cur/（/data/misc/profiles/cur/<user>/<pkg>/…prof），dexopt 时与 ref/（reference profile）合并；“云 profile”即随 DM 文件下发的 profile，由 ART Service（libartservice，Java）在后台 dexopt 时合并（依据 libartservice README 与 path_utils 源码）。ProfileAssistant::ProcessProfiles 以“新方法/新类占比≥2%”决定是否值得重编（kCompile）。odrefresh 用 profile 选过滤器：主镜像 speed-profile（必须有 boot-image.prof）；mainline 扩展在 a17r 默认 speed-profile（无 profile 回退 verify）；system_server 有 vetted profile 时 speed-profile 否则 speed [S34][S38]。

“同一 Java 用例不同模式性能不同”的机制解释：入口来源不同——有可用 AOT 代码时方法直接落 oat 代码；否则落 nterp，热后 JIT 替换（Instrumentation::UpdateMethodsCode）。speed/speed-profile 决定“哪些方法有 AOT”；verify 档无 AOT，全靠 nterp+JIT；-Xint/debuggable 强制全解释且关闭 nterp；JitAtFirstUse（测试用）连 nterp 都关闭、AOT 弃用、首用同步编译。另有编译后淘汰/回退面：CHA 失配、inline cache 失配、BCE 去优化等会把方法打回解释器再重编——同一个 benchmark 在两台设备上的差异常常就是“它命中了这些路径中的哪一条” [S24][S25][S33][S38]。

RISC-V64 的 JIT 事实与缺口（android17-release）：JIT 默认启用且无 riscv 专属开关；runtime/jit/ 下的架构分支全库只有 5 处，其中三处构成实际缺口——TryPatternMatch（微型方法 mode 匹配编译，仅 arm/arm64）、SupportsFastCompiler()（fast baseline 编译器，仅 arm64；失败回退 baseline 的路径也只在 arm64 生效）、small_pattern_matcher 的 float/double 特例（仅 arm64）。后果：riscv64 的热方法要么 baseline 要么直接 optimized（阈值同样来自框架），没有 arm64 的 fast tier 与 pattern-match 快车道；art_quick_compile_baseline 在 riscv64 汇编中存在但唯一调用方是 arm64 fast 编译器，riscv64 上无触发路径（推断）。另一处开销相关事实：CanUseImplicitSuspendCheck() 在 riscv64 返回 false（源码待办注释未实现，a16q2/main 相同），挂起检查需显式 load+branch [S24][S26][S29][S38]。

GC 与内存：对象、分配、collector 与屏障

对象布局与引用：mirror::Object 头仅 2 个 32 位槽——klass_（32 位压缩引用）与 monitor_（LockWord 编码：锁状态/哈希/读屏障状态位/CMC 的 mark bit）。压缩引用已是无条件事实（kHeapReferenceSize=4；历史开关 kUseCompressedReferences 全树无命中），因此 Java 堆上限受 4GB 压缩寻址约束，-Xmx 等参数只影响 footprint 策略 [S37]。

分配路径：快速路径为 TLAB bump allocation——C++ 侧 Thread::AllocTlab 仅做 pos += size（空间由调用方先查 TlabSize() 保证），riscv64 编译代码路径为手写汇编（quick_entrypoints_riscv64.S 中 ALLOC_OBJECT_TLAB_FAST_PATH_RESOLVED 等宏实例，直接递增 THREAD_LOCAL_POS_OFFSET），慢路径统一 downcall 到 artAllocObjectFromCode* 系列 C++；≥12KB 的 primitive array/String 直接进 LOS（大对象空间）。TLAB 用尽时 AllocWithNewTLAB 先尝试按 kPartialTlabSize=16KB 部分扩张，否则向 BumpPointer/RegionSpace 取新 TLAB；失败进入 AllocateInternalWithGc 的“等待他人 GC→自己 GC→全堆 GC+清软引用”循环（最多 5 次），仍失败抛 OOM（消息含 “Failed to allocate a N byte allocation …”）[S29][S37]。

Collector 现状与历史：独立 CMS 实现早已删除（a12 及全部后续快照的 runtime/gc/collector/ 均无 cms* 文件；仅保留 kCollectorTypeCMS 枚举与 MarkSweep(is_concurrent) 复用形态，选项串仍接受 "CMS"）。当前默认由构建期 ART_DEFAULT_GC_TYPE=CMC 与运行期判定共同决定：Android 目标在 userfaultfd 可用时默认 CMC（并发 mark-compact，用 uffd 把 from-space 访问翻译到 to-space）；否则退回 CC（并发复制，RegionSpace）。generational 存在：sticky 做 minor、full 做 major，CC 有 young ConcurrentCopying、CMC 有 YoungMarkCompact（默认启用，受 persist.device_config.runtime_native_boot.use_generational_gc 与 CMC 附加 flag 门控） [S37][S38]。

屏障：读屏障为 Baker（对象读屏障状态位=gray→慢路径 Mark）；riscv64 的读屏障由通用 codegen 生成，没有标记寄存器（marking register）——arm64 用 wMR(x20) 常驻标记状态，riscv64 每次字段加载都要从 Thread 载入“该寄存器对应的 mark entrypoint 指针”再判空（art_quick_read_barrier_mark_regNN 每寄存器入口，quick_entrypoints_riscv64.S 宏 READ_BARRIER_MARK_REG），代码内注释明确标注待办“Introduce a marking register”；且非 Baker 的读屏障在 riscv64 codegen 为 LOG(FATAL) "Unimplemented"——即 riscv64 只支持 Baker。写屏障为卡表（CardTable::MarkCard，无 SATB）；riscv64 侧示例见 art_quick_aput_obj（存引用后按对象地址右移写入卡表一字节）[S26][S29][S37][S38]。

根扫描、挂起与转发：GC 安全点由 ThreadList::SuspendAll/SuspendAllInternal 实现（带 suspend barrier 计数与 immune 机制），GC 主流程 Heap::CollectGarbageInternal；根集合遍历线程栈（quick frame 逐 vreg）、Runtime::VisitRoots（ClassLinker/Intern 等）。nterp 帧用双数组协议（见 §4.2）参与根扫描与移动改写。转发指针：CC/SemiSpace 用 LockWord 的 forwarding 状态承载新地址（kStateForwardingAddress），CMC 不用 lockword 而依赖 uffd 的 from-space 地址翻译 [S37][S38]。

引用/finalizer/OOM：ReferenceProcessor 按类型分派（Soft 仅在“即将 OOM”时清理；FinalizerReference 入队由 GC 完成，Java 侧 Finalizer 线程消费）；-XX:FinalizerTimeoutMs 默认 10000ms；OOM 抛点在 Heap::ThrowOutOfMemoryError（含碎片诊断日志与 “<1% of heap free after GC” 提示）[S37][S38]。

RISC-V64 结论与风险点：GC 语义层三树（main/a16q2/a17r）未发现行为差异；riscv64 的 GC 相关硬编码集中在分配入口与屏障入口的汇编。风险点（推断，待设备验证）：CMC 默认依赖设备内核 userfaultfd 支持，否则 riscv64 实际落到 “Baker read barrier + CC” 组合——而 Baker 屏障正是 riscv64 缺 marking register 的痛点路径，读取放大效应在 GC 活跃期会更明显 [S26][S29][S37][S38]。

4.4 并发与边界：线程/Monitor/内存序；JNI 与 ART ABI

线程状态机：ThreadState（runtime/thread_state.h）把 Java 线程状态与内部挂起状态统一编码——kRunnable = 0（历史值 67，改为 0 以便用整字原子读 flags 判 Runnable）、kSuspended 等；挂起采用“标志位 + 汇编检查点”协议：GC/instrumentation 请求方经 ThreadList::SuspendAll（§4.3）逐线程累加 suspend_count 并等 suspend barrier，被挂起线程在安全点（方法入口/回边/慢路径）读取线程 flags 的 kSuspendOrCheckpoint 位再进 runtime 调用。riscv64 的安全点序列（nterp）：lwu t0, THREAD_FLAGS_OFFSET(xSELF); andi …; call art_quick_test_suspend；编译代码则是 artDeoptimizeIfNeeded/artTestSuspendFromCode 的调用路径（quick_thread_entrypoints.cc）。riscv64 没有独立的 rSUSPEND 寄存器（与 arm64 不同），检查是显式 load+branch；且 CanUseImplicitSuspendCheck() 在 riscv64 为 false（待办未实现），隐式挂起检查（arm64 借助 wMR 无分支）在 riscv64 全部为显式 [S26][S28][S29][S37]。

Monitor 与锁膨胀：锁状态编码在对象头 monitor_ 槽的 LockWord（runtime/lock_word.h）：低 30 位为 thin lock 的 owner thread id + 递归计数，kStateThinOrUnlocked=0/kStateFat=1/kStateHash=2/kStateForwardingAddress=3，位域还含读屏障状态位与 CMC mark bit。快速路径：art_quick_lock_object 内联宏 LOCK_OBJECT_FAST_PATH 用 lr.w.aq/sc.w 循环完成 thin lock（含递归计数与溢出判断），宏内注释特别说明 riscv64 的硬约束：“The LR/SC sequence must be at most 16 instructions, so we cannot have the recursive locking in a slow-path as on other architectures”——因此递归锁计数也必须在 LR/SC 临界区内完成；慢路径转 artLockObjectFromCode（C++）。膨胀（inflate）发生在竞争/等待场景，对象迁移到 Monitor（MonitorPool 分配，MonitorList 挂管理），wait/notify 语义由此层实现 [S29][S30][S37]。

托管与本地代码转换：quick 代码↔native 的入口体系由每线程初始化（InitEntryPoints，entrypoints_init_riscv64.cc）：调用进入托管经 art_quick_invoke_stub（A0=ArtMethod、A1=参数、A3=Thread→xSELF），退回到 quick_entrypoints 的返回桩；JNI 侧入口为 art_jni_dlsym_lookup_stub 与 generic JNI trampoline（详 §4.4）；对 Thread* 的获取在托管代码用 xSELF（s1），在 native/libc 上下文经 TLS（thread_riscv64.cc 提供偏移）[S25][S29][S30]。

JMM 到 RV64 机器码（本节核心，全部有源码锚点）：

  • 内存屏障映射（GenerateMemoryBarrier）：kAnyAny→fence rw,rw；kAnyStore→fence rw,w；kLoadAny→fence r,rw；kStoreStore→fence w,w（RVWMO 的 pred/succ 组合）[S26]。
  • volatile 读：load 前 fence rw,rw + load + fence r,rw（保守的 acquire+release 语义，等价于 seq-cst 读）；volatile 写：≥4 字节类型用 amoswap.{w,d}（kRelease 语义）丢弃返回值充当 seq-cst store，<4 字节用小类型 fence+store+fence（swap 只支持字宽）[S26]。
  • CAS/原子读改写：一律 LR/SC 循环（lr.w.aq/sc.w 及 64 位变体，见 intrinsics 的 LrW/ScW 使用与锁宏）；RISC-V 在此版本（无 Zacas）没有 native CAS 指令可用——这是与 arm64（LSE 单指令 CAS）最本质的原子实现差异 [S26][S27][S30]。
  • 读屏障标注：AmoSwap* 等使用 AqRl::kRelease 标注（assembler_riscv64.h 的 AqRl 枚举），锁宏用 .aq 获取序；编译代码的 GC 读屏障 Mark 检查是无内存序的普通 load（依赖 fake address dependency，与 arm64 同构）[S30][S37]。
  • 正确性边界：LoadAcquire/StoreRelease 语义、volatile 的 seq-cst 需求、GC 屏障的“先标记后使用”三者都已覆盖；但尚无 RV64 内存模型的形式化验证公开记录，且 WeakMemory 类用例（test/ 下 litmus 风格测试）未见 riscv64 专属清单——按公开源码只能给到“实现完整、边界与 arm64 对齐（除了无 LSE 类单指令路径）”的结论 [S27][S41]。

与 arm64 的可比点小结（供 §4.5 案例使用）：同一 Java 语义下，volatile 写 arm64 用 stlr（store-release），riscv64 用 amoswap.rl 或 fence+store+fence；CAS arm64 用 casal，riscv64 用 LR/SC 循环（可能重试、对高争用更敏感）；挂起检查 arm64 可隐式化，riscv64 显式。这三处是同一基准在 RV64 与 arm64 上“同算法不同机器码”的主要来源 [S26][S29]。

JNI 与 ART 私有 ABI

JNI 调用链：System.loadLibrary（libcore）→ Runtime::LoadNativeLibrary（art，java_vm_ext.cc/nativeloader 协作，经 linker namespace dlopen）→ 方法链接时 JNI stub 由 JNI macro assembler 生成（compiler/utils/riscv64/jni_macro_assembler_riscv64.cc：BuildJniFunctionTrampoline 等，普通 native 方法用 dlsym 缓存 lookup stub，@FastNative/@CriticalNative 有各自变体）；JNI 方法入口在镜像中是 GenericJNI trampoline（image_writer.cc 对 native 方法取 kQuickGenericJNITrampoline）[S25][S32][S38]。JNI 调用约定要点：JNIEnv* 是一级参数（线程绑定），jclass/jobject 传递在 riscv64 上遵循 psABI（a0-a7/fa0-fa7 + 溢出规则），断言 kNativeStackAlignment = 16 与托管 ABI 一致 [S30]。

@FastNative 与 @CriticalNative：FastNative 跳过部分 suspension/线程状态检查（调用期间不快挂起）；CriticalNative 更激进——无 JNIEnv*/jclass 参数、不着 JNI 帧、调用期间线程保持 Runnable 且不禁 GC，因此必须与 C 侧签名严格对齐；riscv64 实现中为此存在专门的 ABI 修补 pass（CriticalNativeAbiFixupRiscv64，编译期在 HIR 上插入 Float.floatToRawIntBits/Double.doubleToRawLongBits 伪调用），原因是 managed ABI 与 native（psABI）在浮点参数寄存器上的规则不同：managed 调用约定只在 FA0-FA7 传浮点（不溢出到整数寄存器，kMaxFloatOrDoubleArgumentRegisters=8，多出者进栈），而 native psABI 在 FA0-FA7 用尽后允许把浮点参数塞进 a0-a7（GetNativeOutArgsSize 按此计算帧）；CriticalNative 直呼时编译器需把参数按 native 规整化 [S30]。

ART 私有 managed ABI（riscv64，与 psABI 的差异清单）：A0 在托管调用中固定为 ArtMethod*（kArtMethodRegister = A0，参数从 A1 起），调用桩把 Thread* 装入 xSELF=s1；gp(x3) 被征用为影子调用栈指针（SCS，“unavailable, used for shadow stack”，由 2023-04 提交从沿袭 arm64 的 X18 改为 GP）[S08][S30]；TMP=t6/TMP2=t5 保留给汇编宏；帧布局常量：FRAME_SIZE_SAVE_REFS_ONLY=112 / SAVE_ARGS_ONLY=128 / SAVE_ALL_CALLEE_SAVES=208 / SAVE_REFS_AND_ARGS=224 / SAVE_EVERYTHING=480，nterp 帧 NTERP_SIZE_SAVE_CALLEE_SAVES=192——保存集合的注释明确列出了被排除的寄存器（如 ArtMethod 与 TR 不进某些帧的保存区）[S30]。

入口点与异常信号：quick entrypoints 全集（调用/字段/分配/异常/OSR/deopt/锁）由 quick_entrypoints_riscv64.S 提供，异常抛出桩把全部寄存器按约定保存后转 C++（art_quick_throw_* 系列，见 §4.1）；隐式空指针检查依赖 fault handler（SIGSEGV 判定 fault 地址在后端生成的“哨兵页”范围内转 Java 异常，Runtime::Init 注册并预留 sentinel page；nterp 的代码段也被加入 fault manager 的 generated-code 范围以共享同一机制）；栈溢出由 guard page 触发 StackOverflowHandler；JNIEnv 获取、native 帧的转义（jni_frame_riscv64.h 计算 CriticalNative 帧尺寸并注明“必须与编译器在调用点发出的额外帧一致”）[S25][S29][S30][S37]。SIMD/向量状态：JNI 边界只保存基础浮点寄存器（fs0-fs11 等）；riscv64 不使用向量寄存器做参数传递（无 V 状态跨 JNI 约定），向量域见 §4.5 [S30]。 成本与权衡贯穿本节的各档设计：LR/SC 循环相比 arm64 的 LSE 单指令路径在高争用下要承担重试与强排序开销；显式挂起检查让每次安全点多一条 load+branch；xSELF=s1 常驻线程指针省去取线程的访存，但占用了 callee-saved 寄存器；GP 让渡给影子栈意味着常规全局指针优化不可用——这些取舍都由 ABI 常量与汇编注释固化 [S29][S30]。

intrinsics 覆盖（可核对的量化缺口）：a17r 的 IntrinsicCodeGeneratorRISCV64::Visit* 去重后 170 个（a16q2 为 176、a15 为 164；arm64 同口径 179）。“arm64 有而 riscv64 无”的差集恰好是两类：CRC32 系列 3 个（CRC32Update/Bytes/ByteBuffer，arm64 用 CRC 扩展）与 FP16 系列 12 个（FP16 算术/比较/转换，arm64 用半精度硬件指令）；“riscv64 有而 arm64 无”6 个（Integer/Long.remainderUnsigned、Math.signum/copySign 的 Float/Double 版本——按 visit 名对照，可能反映 arm64 走了其它更早的命名/实现路径，不作强弱结论）。这组差集是“同一 libcore 用例在 RV64 上掉出内建、走通用慢路径”的首批排查清单 [S27][S38]。热点路径实例（可复述）：String.equals →（libcore StringLatin1.equals(byte[],byte[])，带 @HotSpotIntrinsicCandidate 注解）→ ART Intrinsics::kStringEquals → VisitStringEquals（riscv64 已实现，字节/字宽比较循环）；String.indexOf(int) 在 2023-10 于 RV64 实现；System.arraycopy → VisitSystemArrayCopy（含读屏障变体与“同数组向后拷贝”修正 8cc27702db）；Unsafe.compareAndSwap*/getAndAdd* → LR/SC 循环（§4.4）；分配快路径 new-instance → TLAB 汇编（§4.3）[S21][S26][S27][S47]。

RVV/向量化的真实状态（源码证实，见下表）：汇编器自 2023-11 支持 RVV 指令编码（fb0a1bb8e6 等），含向量寄存器定义与汇编器测试；2025-09 的“vector register allocation, part 1”（dde31eea21）把向量寄存器纳入分配基础设施（AllVectorRegisters()、慢路径保存向量寄存器）；但 a17r 的 codegen 对 HasSIMD() 图直接 LOG(FATAL) "Vector extension is unsupported"（Move 与 Save/RestoreFloatingPointRegister 两处，另有“need VTMP”待办注释）——即“优化器生成的代码尚不能使用向量指令”，当前 RVV 主要用于汇编器测试与基础设施。配套事实：测试用 SIGBUS workaround（ART_TEST_ON_SBC_RISCV64_V_ADRALN_WORKAROUND，仅测试构建）模拟被 SBC 触发的 vse64.v 非对齐存储异常，注释写明“一些 SBC（如 Orange Pi RV2）几乎符合 RVA22+V，但 V 扩展不满足 Zicclsm，向量指令非对齐访问会触发 SIGBUS/ADRALN”——这从侧面证明 ART 的 RVV 工具链已经在真实硬件上被使用过 [S13][S22][S26][S43] [S20]。

待验证的优化机会（假设，非结论）：(a) 为 riscv64 引入 marking register（源码待办注释自陈）以省去每次字段加载的 mark-entrypoint load——预期收益随 GC 活跃期与字段访问密度变化，需 PMU 对照；(b) JIT 层缺 fast/pattern-match 的代价量化（同一 microbenchmark 在 -Xusejit 开/关与不同阈值下的编译时机差异）；(c) LR/SC 循环在高争用下的重试代价（与 arm64 LSE 对照的 litmus 实验）；(d) 补 CRC32/FP16 intrinsics 的收益边界（先确认这些 API 在目标工作负载中的占比）；(e) RVV 向量 codegen 的推进节奏只能作为观察对象，不能当作既有能力使用 [S26][S27][S43]。

版本间 JIT/清理差异（实测）：fast 编译器集成方式三代不同——main 时代作为 baseline 可选实现（仅 arm64）；a16q2 时代独立 kFast tier 且由 nterp 查表热度触发（arm64 专属门控）；a17r 时代触发权收敛进 MaybeEnqueueCompilation（配置注册 use_fast_compiler_ 决定），fast 失败回退 baseline；odrefresh mainline 扩展默认过滤器从 verify 改为 speed-profile（a17r）[S34][S38]。CompactDex 实现则在 Android 16（25Q2）与 16QPR2（25Q4）之间从源码消失（a16 快照尚存 7 个 compact_dex 文件、a16q2 为 0）[S39]。

本节核查方法（可复现的三步链）：git ls-remote 先取官方 HEAD 与 release 分支（分支名与标签分开）→ git clone --filter=blob:none --no-checkout 保留全历史、blob 按需拉取 → worktree 检出各 pin 后对有界范围执行 git log --full-history --diff-filter=A <A>..<B> -- <path> 定位首现提交；降级判断用 git merge-base --is-ancestor。这条链的成本与权衡：全历史换取“何时引入/何时删除”的任意回答能力，代价是按需 blob 的网络往返与有界查询纪律（无界路径查询在部分克隆上会触发懒加载风暴）；若只求内容可用，DexFile::Open 级别的浅检出即可，但无法支撑演进结论 [S38]。

接口与实现层面的核对入口：本节涉及的所有“能不能用”判定，最终都落在两类实现上——解释器侧以 IsNterpSupported()、CanRuntimeUseNterp() 与 runtime/interpreter/mterp/nterp.cc 为准；代码生成与入口侧以 compiler/optimizing/code_generator_riscv64.cc、runtime/arch/riscv64/quick_entrypoints_riscv64.S 为准。同一 ABI 约定下，这些文件在不同版本的能力差异正是本节阶段划分的源码依据；后续复核只需固定 pin 的 commit，按同一张阶段表增行即可。

总结与展望

结论要点。 其一，机制层面：ART 的启动链、类加载、双执行引擎（nterp+JIT/AOT）、GC 与 JNI/ABI 都已能按“入口→调用链→失效边界”完整复述（§4.1–§4.4），其关键枢纽是“产物格式 + 编译过滤器 + 入口点改写”三件套：产物决定可用的代码、过滤器决定哪些方法有代码、入口点改写决定未编译方法的落点 [S23][S32][S33][S36]。其二，RISC-V64 层面：支持自 2023-01 的骨架起步，到 android15-release 形成完整后端，android17-release 处于“成熟维护 + 局部前沿（向量基础设施）”状态；剩余缺口清晰且有限：JIT 的两条 arm 系快路径不覆盖、RVV codegen 未落地、GC 缺 marking register、intrinsics 缺 CRC32/FP16 两族 [S11][S13][S24][S26][S27]。其三，趋势层面：公开 main 已冻结，发布以季度列车（25Q2/25Q3/25Q4/26Q2）cherry-pick 维护；RISC-V64 新提交的密度在 2025-09 后明显走低，26Q3 安全分支区间为零提交——当前处于“维护与跟随”而非“功能冲刺”阶段 [S01][S02][S31]。
