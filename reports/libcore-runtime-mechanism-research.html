摘要

  • libcore 的 String 不是 Java 字段 byte[] value：本 pin 的 value 已注释，字符数据由 ART 托管，count_ 用最低位表示压缩标志、其余位表示长度；charAt/intern 是 native，intern 入口为 InternWeak，但 InternTable::Insert 会先查 strong 表并可直接返回 strong 对象。[S01][S02]
  • Direct ByteBuffer 的 putChar 走 DirectByteBuffer.putChar → Memory.pokeShort → pokeShortNative，在 ART 侧可能走 JNI native 或 RV64/AArch64 intrinsic；Heap 路径直接写 Java byte[]，但不等于一定由解释器执行，JIT/AOT 仍可能优化；冻结调用点是否 intrinsify 必须由 odex/aot_map/机器码回答。[S01][S02]
  • System.arraycopy 的 Java char[] 专用路径、ART native 路径和 RV64/AArch64 intrinsic 是不同层：常量长度、变量长度和 typed 阈值分属不同门；同数组 src_pos < dst_pos 只是保守转 slow，并不证明区间实际相交。[S01][S02]
  • ConcurrentHashMap 的普通 put、MOVED 迁移协作、桶锁内写入、TreeBin 删除/平衡是不同状态分支；initTable 的 CAS 只改对象 SIZECTL 字段，局部 sc 保持旧非负值，OOME 在 finally 后传播。[S01]
  • AQS Condition 的等待/唤醒需要把条件队列、同步队列、release、canReacquire/reacquire 和 LockSupport.park 的 ART park_state_/futex 路径分开；超时/中断的返回值只在 timed boolean 方法成立，不能概括 void await。[S01][S02]

背景与现状

Android libcore 是 java.*/javax.* 核心库的 Android 实现集合：ojluni/ 提供 OpenJDK 派生 API，luni/ 提供 libcore.io、字符集与 ICU 适配，libart//dalvik/ 提供 VM 接口和注解，benchmarks/ 提供性能 cell 源码。它以 core-oj/core-libart 等 Soong 模块进入 art-bootclasspath-fragment，再由 com.android.art APEX 提供 boot image 与 native 共享库（libandroidio、libopenjdk、libart 等）；实际 APEX 内布局、odex/oat 参数与设备安装态仍需产物/设备依据。

1.1 性能 cell 的真实口径

来源：公开源码的 cell 参数矩阵与计时口径；本报告不包含内部实测值、未公开 dataset 或旧产物哈希。

本节只保留公开源码的 cell 参数矩阵、源码链与缺口说明，不包含内部测量值。

参数矩阵来自公开源码（pin 内 benchmarks/src/benchmarks/regression/ByteBufferBenchmark.java）：byteOrder ∈ {BIG, LITTLE}（L34-40、L42）、aligned ∈ {true, false}（L44）、bufferType ∈ {DIRECT, HEAP, MAPPED}（L46-48）；方法体在 L276-284：

// benchmarks/src/benchmarks/regression/ByteBufferBenchmark.java:276-284 (libcore@4ebfb391)
public void timeByteBuffer_putChar(int reps) throws Exception {
    ByteBuffer src = ByteBufferBenchmark.newBuffer(byteOrder, aligned, bufferType);
    for (int rep = 0; rep < reps; ++rep) {
        src.position(aligned ? 0 : 1);
        for (int i = 0; i < 1024; ++i) {
            src.putChar(' ');
        }
    }
}

要点：

  • aligned=false 通过 position(1) 制造 1 字节偏移（newBuffer L51-77：result.position(aligned ? 0 : 1)），不是“对齐开关”意义上的硬件对齐属性；Java 语义不要求对齐，对齐差异只可能体现在底层机器码/硬件行为。
  • worst cell 的 byteOrder=LITTLE 在 little-endian 目标（RV64/AArch64 均为小端）上即 swap=false：nativeByteOrder == true。

DIRECT 与 MAPPED 都落到 DirectByteBuffer（DirectByteBuffer extends MappedByteBuffer implements DirectBuffer，L41；MAPPED 由 FileChannel.map 创建，见 benchmark L65-73）。调用链（全部为 pin 内逐字行）：

// luni/src/main/java/libcore/io/Memory.java:365-373
    public static void pokeShort(long address, short value, boolean swap) {
        if (swap) {
            value = Short.reverseBytes(value);
        }
        pokeShortNative(address, value);
    }
    @FastNative
    private static native void pokeShortNative(long address, short value);

// luni/src/main/native/libcore_io_Memory.cpp:164-166（JNI/FAST_NATIVE 注册见 L256）
static void Memory_pokeShortNative(JNIEnv*, jclass, jlong dstAddress, jshort value) {
    put_unaligned<jshort>(cast<jshort*>(dstAddress), value);
}

ART intrinsic（参考 pin，逐字）：

// compiler/optimizing/intrinsics_riscv64.cc:378-381 (art@b753cf97)
void IntrinsicCodeGeneratorRISCV64::VisitMemoryPokeShortNative(HInvoke* invoke) {
  Riscv64Assembler* assembler = GetAssembler();
  EmitMemoryPoke(invoke, [&](XRegister rs2, XRegister rs1) { __ Sh(rs2, rs1, 0); });
}

// compiler/optimizing/intrinsics_arm64.cc:722-726
void IntrinsicCodeGeneratorARM64::VisitMemoryPokeShortNative(HInvoke* invoke) {
  MacroAssembler* masm = GetVIXLAssembler();
  __ Strh(WRegisterFrom(invoke->GetLocations()->InAt(1)),
          AbsoluteHeapOperandFrom(invoke->GetLocations()->InAt(0), 0));
}

结论边界：源码两端都有 MemoryPokeShortNative intrinsic（libcore 声明 + ART riscv64/arm64 代码生成；x86_64 亦有，L1809/1813，仅作对照）。这可以排除“当前源码没有实现”；不能据此断言冻结产物在 putChar 调用点已 intrinsify——是否 intrinsify 还取决于 AOT/JIT 的编译决策与产物状态（§1.5）。

HEAP 路径不同：

// ojluni/src/main/java/java/nio/HeapByteBuffer.java:461-469
    @Override
    public ByteBuffer putChar(char x) {
        // Android-added: Merge the Read-only buffer class with this Read-Write buffer class.
        throwIfReadOnly();
        // Android-changed: Avoid unsupported ScopedMemoryAccess.
        // SCOPED_MEMORY_ACCESS.putCharUnaligned(scope(), hb, byteOffset(nextPutIndex(2)), x, bigEndian);
        putCharUnchecked(nextPutIndex(2), x);
        return this;
    }

putCharUnchecked（L508-522）直接在 byte[] hb 上按 bigEndian 写两个字节——它不调用 Memory.pokeShortNative 这条 native intrinsic/JNI 实现，是纯 Java 字节写；这不排除其它编译优化。其运行成本由执行形态决定：AOT/JIT 生成代码或解释执行，以及相关状态检查（如数组边界、读写屏障），不能简单归为“JIT 决定”。与 DIRECT/MAPPED 不属于同一路径。

1.4 失败、边界与回退

  • 越界：相对写 putChar(char) 经 nextPutIndex(2) → BufferOverflowException；绝对写 putChar(int,char) 经 checkIndex(i,2) → IndexOutOfBoundsException（DirectByteBuffer.java:462-471）。
  • 只读/不可访问：ReadOnlyBufferException、IllegalStateException("buffer is inaccessible")（Direct）；throwIfReadOnly()（Heap）。
  • swap 分支：跨端 order 时先 Short.reverseBytes 再落盘；这是语义正确性路径，不是失败。
  • 回退（intrinsic→native）：若调用点未被 intrinsic 化，@FastNative pokeShortNative 仍有 libcore native 实现（put_unaligned<jshort>，libcore_io_Memory.cpp:164-166），功能不变、成本结构不同。当前无法判断冻结产物实际走了哪条（§1.5）；不虚构反汇编。
  • HEAP 路径无 JNI：纯 Java 字节写，不存在“解释态一概 JNI”的路径；旧稿若把 heap 写也归为 JNI/intrinsic 属错误表述。

2.3 类库 ↔ VM 的分工：注解与 native 声明

libcore 通过两种显式接口与 ART 交互：

  1. @FastNative / @CriticalNative 注解（dalvik/annotation/optimization/）：标记可被 ART 特殊调用约定处理的 native 方法。例：Memory.pokeShortNative（luni/.../Memory.java:372，ch01 已给链）；VMRuntime.is64Bit()（libart/.../VMRuntime.java:315-316）。
  2. native 声明本身：libcore 声明 native，实现由 JNI（本仓 luni/src/main/native/*.cpp）或 VM 内置实现（ART 侧）提供。例：VMRuntime 的 bootClassPath()（L268）、vmVersion()（L282）、properties()（L261）。

选择点模型（重画，三个维度不是互斥的三类）：

  1. 编译器机制有两种相关但不同的形式：①调用点替换/内联——普通 Java 方法也可被 intrinsify（例：String.equals 在 ART 有 StringEqualsOptimizations，intrinsics.h:233-241；具体注册/触发条件待核）；②native callee 的 AOT intrinsic body——native 声明的方法也可由编译器生成优化后的体内代码。注意：String.charAt 在本 pin 是 native（@FastNative），但 String.length() 是 Java 方法（String.java:1209-1223，活分支 return count >>> 1），不能把两者混成 native；不能拿 native charAt 当“普通 Java 方法可被 intrinsify”的例子，String.length() 是 Java 方法这一事实保持；System.arraycopy 是 @FastNative 声明 + SystemArrayCopyOptimizations（intrinsics.h:244）。
  2. @FastNative/@CriticalNative：它们描述调用约定/入口形态，不保证该调用点一定被 intrinsify；native 方法还可以有 AOT intrinsic callee body。
  3. 可用代码与实际调用点：boot image/AOT 里可用的编译产物、JIT 编译结果、以及“本次待测调用点实际走了哪条路径”是三个不同问题；最后一项必须有产物/机器码依据（ch01/ch09）。
Java 调用 ──> libcore Java 实现 ──┬─> 纯 Java（集合/算法；调用点仍可能被 intrinsic 化）
                                  ├─> native 声明 → JNI 实现（luni/src/main/native/*.cpp）→ bionic/libc
                                  └─> native 声明 + @FastNative/@CriticalNative → 特殊入口/可被 intrinsic
                                  └─> boot image/AOT 中已有的编译代码（是否覆盖本调用点未知）
  • 正常：按上述维度组合执行；具体到某产物需依据。
  • 失败：native 缺失/签名不匹配 → UnsatisfiedLinkError（JNI 机制，通用行为；本章未构造实例）。
  • 回退：同一 Java 语义可能有“intrinsic 路径”和“native/JNI 路径”两条实现（ch01 的 pokeShortNative 即例），功能不回退、性能结构不同；冻结产物走哪条需产物依据。

3.1 String 的存储：关键事实是「运行时托管」，不是「Java 字段 byte[] value」

在 libcore@4ebfb391 中，String.value 字段被注释掉，字符数据由 ART 运行时管理；Java 侧只保留 count（长度 + 压缩标志）：

// ojluni/src/main/java/java/lang/String.java:147-177（libcore@4ebfb391）
    // BEGIN Android-changed: The character data is managed by the runtime.
    /*
    We only keep track of the length here and compression here. ...
    If STRING_COMPRESSION_ENABLED, count stores the length shifted one bit to the left with the
    lowest bit used to indicate whether or not the bytes are compressed (see GetFlaggedCount in
    the native code).
    ...
    @Stable
    private final byte[] value;
    */
    private final int count;
    // END Android-changed: The character data is managed by the runtime.

对应实现：

// String.java:1209-1216（length：读 count，含压缩标志处理）
    public int length() { ... final boolean STRING_COMPRESSION_ENABLED = true; ... }

// String.java:1270-1272（charAt：运行时实现）
    @FastNative
    public native char charAt(int index);

// String.java:1660-1688（equals：改用 length()/charAt() 的 Android 实现）
// String.java:2291-2312（hashCode：同理，逐 char 计算）
// String.java:4971-4972（intern）
    @FastNative
    public native String intern();

ART 侧的压缩布局（参考 pin b753cf97，本批补核）：

  • mirror::String 的 count_ 字段注释明确：压缩开启时最低位是 StringCompressionFlag，其余位是长度，length = count_ >> 1（runtime/mirror/string.h:316-318）。GetLengthFromCount（L267-269）右移一位；IsCompressed(count)（L257-259）看最低位；GetFlaggedCount(length, compressible)（L271-278）把长度左移一位后或上压缩位。
  • compressible 的谓词不是“所有 Latin-1”也不是“通常含 NUL 的 ASCII”：本 pin 的 String::IsASCII(uint16_t c) 定义为 (c - 1u) < 0x7f，即 1..0x7F，明确排除 U+0000（string.h:288-291，注释说明这是为了 Modified-UTF8 检测）；AllASCII 逐字符用这个谓词（string-inl.h:108-118），AllocFromUtf16/AllocFromCharArray/AllocFromModifiedUtf8/AllocFromByteArray 的 compressible 由它或等价条件决定（string.cc:210-233、248-；string-alloc-inl.h:246-261、288-301）。string.cc:85-130 是 DoReplace/DoConcat，不是分配入口；本 pin 未找到 AllocFromChars 这个符号。因此含 NUL 的字符串不会因“ASCII”而压缩；0x80..0xFF 也不是这个谓词的范围。压缩标志是运行时表示选择，不等同于 Latin-1 的全部范围。
  • String::CharAt（string-inl.h:44-56）先做边界检查；IsCompressed() 为真时从 GetValueCompressed()[index] 取（每字符 1 字节），否则从 GetValue()[index] 取 UTF-16 码元。ComputeHashCode（L83-88）也按压缩/非压缩选择不同的字符读取，但哈希算法仍是对 UTF-16 码元序列计算。
  • 因此“压缩”不是 Java 层另存一个 byte[] 字段，而是 ART 对象内部的表示选择；Java 侧 count 承载长度+标志，字符数据由运行时布局管理。含 NUL 的字符串是明显的非压缩反例，不能把压缩标志当作“ASCII 或 Latin-1”的等价物。

String.intern() 的真实宿主（参考 pin）：

String.intern (libcore @FastNative native)
  → ART String_intern (runtime/native/java_lang_String.cc:107-111)
  → String::Intern (runtime/mirror/string.cc:459-460)
  → InternTable::InternWeak(this) (runtime/intern_table.cc:309-313)
  → InternTable::Insert (L206-258) / Intern (L261-292)
  • String::Intern() 调用的是 InternWeak，这是 Java intern() 的入口/新插入策略；但它不等于“所有 Java intern 结果必在弱表”。InternTable::Insert（L206-258）进入后先查 strong 表：命中就直接返回那个 strong 对象（L225-229）；只有 strong 未命中才查 weak 表（仅当 weak access 可用），is_strong=true 且 weak 命中时把 weak 提升为 strong，is_strong=false 时返回 weak 或插入 weak。因此：已有强 intern 时 String.intern() 返回强对象；新插入通常进入弱表，只有在没有其它强引用、且仍处于弱驻留状态时才可能被 GC 回收。不能把“Java intern = 弱表/必可回收”当成无条件结论。
  • InternTable::Intern（L261-292）对 (utf16_length, utf8_data) 先查 strong/weak 以避免分配，再 String::AllocFromModifiedUtf8 分配并 SetHashCode；失败返回 null 并保留 OOME。该路径是 dex 字符串/类名强 intern 的入口，与 Java String.intern() 的 weak 路径不同。
  • 锁与并发：intern_table_lock_ 保护 strong/weak 表；InternTable::Insert 在持锁期间做表查找，必要时在分配前释放锁（Intern 的注释/结构），避免在分配路径持锁。GC 通过 SweepInternTableWeaks/VisitRoots 维护 weak/strong 根（L65-103、L317+）；具体停顿/并发行为需运行验证。

机制结论：

  • 能下：本 pin 的 String 采用“运行时托管 + count 编码长度/压缩位”的表示；length() 是 Java 方法（String.java:1209-1223，返回 count >>> 1），charAt() 是 @FastNative native；ART 的压缩位/长度编码和 charAt 分支已核。
  • 不能下：不能把 byte[] value 当作当前实现的 Java 字段来描述（该字段已被注释）；也不能把 intern() 写成“无条件弱表/必可回收”（入口是 InternWeak，但 strong 命中会直接返回 strong）。
  • equals/hashCode 的实现分层：libcore String.equals/hashCode 是 Java 循环（length()+charAt()）；ART 对 String.equals 有 intrinsic（intrinsics_list.h:214），RV64 生成器在 intrinsics_riscv64.cc:1141-1256：先判 null、引用相等、类相等（String 不可继承，比较 class 字段）、count 字段相等（同时比较压缩标志）、空串；然后按压缩/非压缩计算字节数，用 Ld 每次比较 8 字节，依赖字符串尾部零填充；StringEqualsOptimizations（compiler/optimizing/intrinsics.h:233-241）可在已知参数非空/为 String 时省略对应检查。hashCode 没有对应的 RV64 StringHashCode intrinsic 条目（intrinsics_list.h 只有 charAt/length/compareTo/equals），仍是 ComputeHashCode 的 Java/运行时循环；因此不能把 equals 的 intrinsic 外推到 hashCode。
  • compareTo 的活入口与分层：String.java:1884-1899 中 RI 的 compareTo 方法体在 /* ... */ 注释块，活代码是 @FastNative public native int compareTo(String)（L1897-1898）。Java 层没有逐字符比较；调用进入 ART runtime/native/java_lang_String.cc:41-49 的 String_compareTo：rhs null 抛 NullPointerException，否则 mirror::String::CompareTo（runtime/mirror/string.cc:335-376）按 compressed/compressed、mixed、uncompressed 三分支比较前缀，首个不同字符返回差值，前缀相同返回长度差。ART 有 VisitStringCompareTo intrinsic 入口（intrinsics_riscv64.cc:3186/3203），但冻结调用点是否 intrinsify 仍需产物。失败边界只有 rhs null；返回值不抛异常。
  • 压缩标志与 equals 的正确性边界：intrinsic 把 count（长度+压缩标志）直接比较，只有在“满足本 pin 的 compressible 谓词（1..0x7F，排除 NUL）的内容压缩、其余不压缩”这个 ART 不变式下，“压缩标志不同 ⇒ 内容不同”才成立。AllocFromUtf16/AllocFromCharArray/AllocFromModifiedUtf8/AllocFromByteArray 等构造路径按 AllASCII/UTF-8 长度计算 compressible 并写入 GetFlaggedCount（string.cc:210-233、248-；string-alloc-inl.h:246-261、288-301），这是该不变式的来源；若某个构造/转换路径破坏它，intrinsic 会与 Java equals 的逐字符语义不一致。含 U+0000 的字符串是一个需要特别核对的边界：它不满足 IsASCII，应保持非压缩。本 pin 只做了源码阅读，未构造反例运行验证。
  • 性能含义：源码具备 StringEquals intrinsic，且 charAt（native 声明）与 length()（Java 方法）各自存在调用点优化可能，但这不等于冻结产物已 intrinsify；压缩/非压缩字符串的 count 不等时会走返回 false 的快速路径（在不变量成立时），最终语义仍由 Java equals 保证。产物状态需机器码（同 ch01 边界）。

  • 范围：srcPos/length 必须落在 src 内、dstPos/length 落在 dst 内；否则 ArrayIndexOutOfBoundsException。
  • 重叠：src == dst 且正向区间重叠时反向复制（Java 层 char 快路径显式实现；native 通用路径用 memmove 语义）。
  • 类型边界：primitive 数组按类型精确匹配；引用数组复制需通过数组存储检查（ArrayStoreException），并涉及读/写屏障——具体由 ART 运行时实现，libcore Java 层不体现。

3.3.1 ART 侧真实实现：native 与 RV64 intrinsic 两条路径

libcore 的专用 char[] Java 方法超过 32 个元素时调用 arraycopyCharUnchecked；该 native 与通用入口在 ART 中注册为：

FAST_NATIVE_METHOD(System, arraycopy, "(Ljava/lang/Object;ILjava/lang/Object;II)V"),
FAST_NATIVE_METHOD(System, arraycopyCharUnchecked, "([CI[CII)V"),
...

通用 native 路径 System_arraycopy（java_lang_System.cc:50-165）按以下顺序执行：

  1. 空指针与数组性：src==null/dst==null → NPE（消息 src == null/dst == null）；不是数组 → ArrayStoreException（“source/destination ... is not an array”）。
  2. 边界：负的 srcPos/dstPos/count，或 srcPos > src.length-count、dstPos > dst.length-count → ArrayIndexOutOfBoundsException，消息包含五个参数。
  3. 同组件类型：srcComponentType == dstComponentType 时按 primitive 宽度分组做 Memmove——boolean/byte 按 1 字节、char/short 按 2 字节、int/float 按 4 字节、long/double 按 8 字节；引用数组走 AssignableMemmove。分组是“同宽度位拷贝”，不改变元素类型语义。
  4. 组件类型不同：若目标组件是 primitive 或源组件是 primitive → ArrayStoreException（Incompatible types: src=..., dst=...）。两边都是引用数组时：目标组件可赋值自源组件 → AssignableMemcpy（整块拷贝+写屏障）；否则 AssignableCheckingMemcpy 逐元素检查，遇到不可赋值元素立即 ArrayStoreException（消息 source[i] of type ... cannot be stored in destination array of type ...）。

引用数组的读/写屏障（art@b753cf97 runtime/mirror/object_array-inl.h）：

  • AssignableMemmove（L103-172）：同数组重叠时按 copy_forward 选择正向/反向；不能直接 memmove，因为引用需要读屏障。若源数组不是 gray（Baker 读屏障状态 0），可走“无逐元素读屏障”的快循环；否则每个元素 GetWithoutChecks 内含读屏障。拷贝结束后调用 WriteBarrier::ForArrayWrite(this, dst_pos, count) 一次性做写屏障。
  • AssignableCheckingMemcpy（L234-330）：在拷贝过程中缓存“最近一个可赋值元素类”，只有类变化时才重新 dst_class->IsAssignableFrom；遇到不可赋值元素先执行写屏障，再抛 ArrayStoreException。这也说明“类型检查”和“写屏障”是两件事，不能互相替代。

RV64 编译期 intrinsic（compiler/optimizing/intrinsics_riscv64.cc）：

  • 通用对象数组 SystemArrayCopy：kSystemArrayCopyThreshold = 128（L1634）。CreateSystemArrayCopyLocationSummary（code_generator.cc:1704-1751）先做常量门：常量 src_pos<0/dst_pos<0 → 不生成 intrinsic；常量 length<0 或 length >= length_threshold → 不生成 intrinsic；若 DestinationIsSource 且两个位置都是常量且 src_pos<dst_pos → 不生成 intrinsic；generic intrinsic 遇到 primitive 数组 → 不生成 intrinsic。
  • CheckSystemArrayCopyNullOrOverlap（L1654-1721）是运行期门：源/目标 null → slow；若同一数组且 src_pos < dst_pos → 保守转 slow，不检查区间实际是否相交（即使 length=0 或区间不重叠也会转），因此不能写成“已证明重叠才 slow”。长度门分两种：变量长度用 Bgeu(length, 128)（unsigned，负数和 ≥128 都 slow，L1710-1715）；常量长度已在 LocationsBuilder 用 copy_threshold 过滤，codegen 只 DCHECK 0 <= len <= copy_threshold（L1717-1719）。引用拷贝在 Baker 读屏障下先读源数组 lockword 的 RB 状态位（LockWord::kReadBarrierStateShift），非 gray 走裸 lwu/sw 循环，gray 走 ReadBarrierSystemArrayCopySlowPathRISCV64 逐元素 ReadBarrier::Mark（L35-91、L1890-1989）；结束后 MarkGCCard(dest)（L1989）。
  • primitive 专用 intrinsic SystemArrayCopyByte/Char/Int：kSystemArrayCopyPrimThreshold = 384 字节，copy_threshold = 384/sizeof(element)（L2000-2003）。常量长度在 LocationsBuilder 用该 typed 阈值过滤；变量长度的运行期 Bgeu 仍使用全局 kSystemArrayCopyThreshold=128（CheckSystemArrayCopyNullOrOverlap 的 copy_threshold 参数只用于常量 DCHECK），所以 typed 阈值与变量门不是同一个数。主循环按 16 字节块（Ld×2/Sd×2）拷贝，尾部按剩余字节用 8/4/2/1 字节加载存储展开；常量长度与变量长度分别生成不同循环（L2071-2225）。char[] 的 Java 阈值 32 又是在 libcore 专用方法内部，三层阈值不能合并。
  • AArch64 对照：intrinsics_arm64.cc:3191/3557 也有 kSystemArrayCopyPrimThreshold=384、kSystemArrayCopyThreshold=128，slow path/重叠/边界检查结构相同；引用数组同样使用 Baker 读屏障。差异主要在指令选择（AArch64 的加载/存储与 RV64 的 lwu/sw 不同），语义与阈值不是“只有 RV64 才有”的特例。
  • 产物边界：以上是编译器“具备生成能力”和运行期 native 兜底；某个冻结调用点是否被 intrinsic、是否走到 slow path，需要 odex/aot_map 或反汇编确认（本报告缺该产物）。

  • Arrays.sort(int[])（L123-125）→ DualPivotQuicksort.sort(a, 0, 0, a.length)；范围版本 sort(int[],from,to)（L146-149）先 rangeCheck，再 DualPivotQuicksort.sort(a, 0, from, to)。DualPivotQuicksort 是双轴快排实现（ojluni/src/main/java/java/util/DualPivotQuicksort.java），源码入口接受 (a, parallelism, left, right)；算法内部的具体插入排序/双轴划分阈值不在本章展开。

4.1 Buffer 状态模型与视图

Buffer 的经典状态（position/limit/capacity/mark）与检查逻辑见 Buffer.java（nextPutIndex(int) L741-748 → BufferOverflowException；checkIndex 越界 → IndexOutOfBoundsException）。视图的关键在于共享 vs 复制：

  • HeapByteBuffer.slice()（L141-153）与 slice(int,int)（L157-167）、duplicate()（L170-179）：共享同一 byte[] hb，新建 Buffer 对象、独立 position/limit/mark。slice() 以当前 position 为起点、remaining 为容量，并把 pos+offset 作为新视图的数组偏移；slice(index,length) 用 index+offset，都不复制数组。asReadOnlyBuffer()（L182-192）在截断数组路径返回 HeapByteBufferR，否则返回 isReadOnly=true 的 HeapByteBuffer，仍共享 hb。
  • DirectByteBuffer 的 slice()（L184-196）、slice(int,int)（L198-212）、duplicate()（L215-227）、asReadOnlyBuffer()（L229-240）都传入同一个 MemoryRef，只改变 mark/position/limit/capacity 和 offset；slice 检查 memoryRef.isAccessible，duplicate/asReadOnlyBuffer 检查 memoryRef.isFreed。源码注释明确：MemoryRef 可在原始 DirectByteBuffer 失去强引用后继续存活（例如视图仍持有它，L63-70），因此清理语义不能绑定在“原始 Buffer 对象”上；视图的 isReadOnly 只是写路径检查，不改变底层 MemoryRef 的可访问性。
  • 因此 slice/duplicate/asReadOnlyBuffer 都是共享存储的视图，不是深拷贝；区别只在起点/容量/只读标志和状态字段。HeapByteBuffer 共享 Java 数组，DirectByteBuffer 共享 native 地址 + MemoryRef；后者的生命周期由最后一个持有者/Cleaner 决定（§4.3）。

4.4 生命周期与 Cleaner

  • MemoryRef.free()（DirectByteBuffer.java:90-95）把 isAccessible=false/isFreed=true 并清空地址。调用者已找到：luni/src/main/java/java/nio/NioUtils.java 的 freeDirectBuffer(ByteBuffer)（L52-64）——null 直接返回；强转 DirectByteBuffer；cleaner != null 时先 cleaner.clean()（L59-60）；随后无条件 dbb.memoryRef.free()（L63）。即显式释放是“先 Cleaner thunk、再 MemoryRef 标记释放”的顺序；别名/其它视图后续访问会命中 isFreed/isAccessible 检查（逐路径见上文）。进一步调用入口/别名安全与设备行为仍单列（未核）。
  • 检查是逐路径的：写入方法检查 memoryRef.isAccessible（如 putChar L451/L454）；视图创建路径检查 isFreed（duplicate() L216、asReadOnlyBuffer() L230，另有 L492/L594 等方法）；并非所有 get/put 都执行同一检查，具体按方法体核对。
  • Java 分配路径：无 Cleaner，内存随 buffer 引用被 GC 回收（非移动数组由 VM 管理）。
  • fd/unmapper 路径：Cleaner.create(memoryRef, unmapper)（L130）。Cleaner.create 在 thunk == null 时返回 null（sun.misc.Cleaner.java:157-160），因此“unmapper 为空仍记录 cleaner”不成立。
  • 自动 vs 显式：不可达时由 Cleaner 线程执行 thunk（时机不确定）；显式 clean() 一次性移除（remove(this) 失败即返回，L166-168）。若 thunk 抛出 Throwable，Cleaner 打印 Error("Cleaner terminated abnormally") 并 System.exit(1)（L169-179）——不是“只记录”。
  • 同仓可见的清理入口（补充）：java.nio.NioUtils.freeDirectBuffer（L52-64，cleaner.clean() → memoryRef.free()）、sun.nio.ch.FileChannelImpl.unmap（L902-907，((DirectBuffer)bb).cleaner() 不存在时跳过）、libcore.io.MemoryMappedFile.close()（直接 munmap，L65 起）。MemoryRef.free 的直接调用者即 NioUtils.freeDirectBuffer（已核）；该 API 的其它调用入口与设备行为仍可单列。
  • 失败/回退：自动 GC 清理不保证时间；显式 clean() 在调用线程同步执行 thunk（且一次性移除），但“资源是否全部消失”由 thunk 负责，不保证别名/其它资源安全消失——不要把自动清理的不确定性套给显式调用。

5.1.2 CHM initTable/putVal/helpTransfer/replaceNode 的桶锁分支

initTable（L2312-2332）：循环读 table；sizeCtl<0 说明别的线程正在初始化，只 Thread.yield() 自旋；否则 CAS(SIZECTL, sc, -1) 取得初始化权，CAS 失败就重读循环。CAS 只把对象的 SIZECTL 设为 -1，局部 sc 仍是循环开头读到的旧值（非负，0 或构造器容量）。进入 try 后按 sc>0 ? sc : DEFAULT_CAPACITY(16) 分配 new Node[n]；若分配抛 OutOfMemoryError，sc = n-(n>>>2) 尚未执行，finally 恢复的是原非负 sc（不是 -1），然后 OOME 原样传播、table 仍为空；成功路径才设置 table 并把 sc 改为 n-(n>>>2)（约 0.75 阈值）。所以“失败重试”只指 CAS/争用，不包含分配 OOME。

putVal（L1022-1092）：

  1. key/value 为 null → NPE；spread(hashCode())。
  2. 表为空 → initTable()。
  3. 目标桶为空 → casTabAt(tab,i,null,new Node)，空桶无锁；CAS 失败就重读。
  4. 桶头 hash == MOVED → helpTransfer(tab,f)，拿到 nextTab 后重试。
  5. onlyIfAbsent 且首节点 hash/key 命中且 value 非空 → 直接返回旧值，不取桶锁（这是 putIfAbsent 的无锁快路径）。
  6. 否则 synchronized(f)，进入后必须再 tabAt(tab,i)==f（防止锁前桶已被迁移/替换）；fh>=0 走链表插入/覆盖，f instanceof TreeBin 走 putTreeVal，ReservationNode 抛 IllegalStateException("Recursive update")。
  7. 锁内若命中已有键：oldVal != null 时按 onlyIfAbsent 决定覆盖后直接 return oldVal，不会走到 addCount；只有链表/树中确实新建节点（新键）才在退出循环后 addCount(1L,binCount) 更新计数并可能触发/协助 transfer。binCount>=TREEIFY_THRESHOLD(8) 的 treeifyBin 也只在有桶内遍历计数的新键/更新路径上发生。

helpTransfer（L2384-2405）：仅当 f 是 ForwardingNode 且 nextTable != null 才协助。先算 rs = resizeStamp(tab.length) << RESIZE_STAMP_SHIFT；循环条件要求 nextTab == nextTable && table == tab && sizeCtl<0（期间表未被提交/替换）；若 sizeCtl 已达 rs+MAX_RESIZERS/rs+1 或 transferIndex<=0 就退出；否则 CAS(SIZECTL, sc, sc+1) 成功后调用 transfer(tab,nextTab) 并退出。返回 nextTab 或当前 table，调用方据此重试。

replaceNode（L1124-1195）：remove/replace 共用；桶空直接返回 null；MOVED 先 helpTransfer；否则 synchronized(f) + 重新验证 tabAt。链表桶按 cv（条件值）匹配后：有 value 就改 e.val，否则 pred.next=e.next 或把桶头 setTabAt(tab,i,e.next)；TreeBin 桶用 findTreeNode，删除后若 removeTreeNode 返回 true 则 setTabAt(tab,i,untreeify(t.first))。validated 只有在确认桶未被替换时才置 true；失败则回到外层循环重试。删除成功才 addCount(-1L,-1)。

computeIfAbsent/compute/merge（L1712-2110）的额外分支：

  • computeIfAbsent：空桶先放 ReservationNode，在其上 synchronized 后 CAS 占位，调用 mappingFunction；返回 null 时 finally 把桶设回 null（保持空桶），返回非 null 则替换成普通 Node。首节点已存在且命中时不取锁、不调用函数。链表/树桶在 synchronized(f) 内计算，插入前若 pred.next != null 抛 IllegalStateException("Recursive update")——这是检测映射函数递归改同一桶。
  • TreeBin 删除与平衡（L3010-3105）：removeTreeNode 先从 prev/next 链表摘除 p（保持 first 链），若 first==null 则 root=null 并返回 true（调用方会把桶改成 untreeify 链表）；若树太小（root/right/left-left 为空）也直接返回 true，不取 root 锁。否则 lockRoot()，按 CLR 红黑树删除：有两个孩子时找右子树最小后继 s，交换 s/p 的颜色和位置（结构指针移植，不交换 key/value，因为 next 链被并发读）；单孩子/无孩子直接用 replacement；若 p 为红则无需平衡，否则 balanceDeletion(r,replacement)（红兄弟旋转、双黑上推等 CLR 情形）；最后摘除 p 的 parent 指针、unlockRoot()，checkInvariants(root) 断言后返回 false（仍是树）。调用方 replaceNode/compute/merge 只有在返回 true 时才 setTabAt(tab,i,untreeify(t.first))。
  • compute：空桶同样用 ReservationNode 占位；已有键的 remappingFunction 返回 null 时删除节点（链表改 pred.next/桶头，树走 removeTreeNode 并在需要时 untreeify），返回非 null 时改值/插入；delta 累计 +1/-1，末尾统一 addCount(delta,binCount)。
  • merge：空桶不使用 ReservationNode，直接 casTabAt(tab,i,null,new Node(h,key,value))；已有键用 remappingFunction.apply(old,value)，null 删除、非 null 更新；树桶同理。三种方法在桶头 MOVED 时都先 helpTransfer，并在桶锁内重新 tabAt(tab,i)==f 校验。

这些分支的共同正确性约束：桶锁只保护当前桶对象，迁移用 ForwardingNode/helpTransfer 把操作带到新表；链表/树的写必须在 tabAt(tab,i)==f 复核后执行；空桶 CAS、ReservationNode 锁和桶锁是不同路径，不能把 CHM 说成“所有写都加同一个锁”。

5.2 线程池：ctl 状态机与执行路径

ThreadPoolExecutor 用一个 AtomicInteger ctl 打包“运行状态 + worker 数量”（pin）：

// java/util/concurrent/ThreadPoolExecutor.java:390-400（libcore@4ebfb391，节选）
    private final AtomicInteger ctl = new AtomicInteger(ctlOf(RUNNING, 0));
    private static final int COUNT_BITS = Integer.SIZE - 3;
    private static final int RUNNING    = -1 << COUNT_BITS;
    private static final int SHUTDOWN   =  0 << COUNT_BITS;
    private static final int STOP       =  1 << COUNT_BITS;
    private static final int TIDYING    =  2 << COUNT_BITS;
    private static final int TERMINATED =  3 << COUNT_BITS;

执行路径：execute(Runnable)（L1302）→ 入队或新建 Worker；Worker.run()（L624）→ runWorker(this)（L1079）；拒绝走 reject（L796，策略：Abort/CallerRuns/Discard/DiscardOldest）。

  • 状态机：RUNNING → SHUTDOWN（shutdown）→ TIDYING → TERMINATED；RUNNING → STOP（shutdownNow，中断 worker）→ TIDYING → TERMINATED。状态与 worker 计数同字段，无锁 CAS 更新。
  • 正常：提交→排队/扩容→执行→worker 复用。
  • 失败：饱和且拒绝策略 Abort → RejectedExecutionException；任务抛出异常 → worker 线程终止并补充（processWorkerExit 机制）；OutOfMemoryError 创建线程失败。
  • 回退：拒绝策略是设计选择（如 CallerRuns 降级为调用者执行）；线程池不自动改变策略。
  • 成本：队列选择、线程创建/唤醒、上下文切换；量化留 ch09。

5.3 AQS 与 LockSupport：等待/唤醒的底层链

  • AbstractQueuedSynchronizer（本 pin）：volatile int state（L538）、volatile Node head/tail（L528/L533）。本版没有 acquireQueued 方法；acquire(int)（L1028-1030）在 tryAcquire 失败后调用统一入口 acquire(null, arg, false, false, false, 0L)（方法定义从 L705 起），其 for (;;) 循环（L727 起）负责入队/自旋/停顿，LockSupport.park(this) / parkNanos 在 L790/L792，取消路径走 cancelAcquire（L746/L796），中断在循环内以 Thread.interrupted() + interruptible 标志处理（L800-801）。
  • LockSupport：unpark(Thread)（L177）、park(Object blocker)（L217/L370）；内部使用 jdk.internal.misc.Unsafe（import L40）。park/unpark 的许可语义（先 unpark 会保留一个许可、park 消费）按 LockSupport 约定，本 pin 的 Java 委托入口见 L177/L217。
  • 链：ReentrantLock.lock → AQS acquire → 失败入队 → LockSupport.park → Unsafe.park → ART Thread::Park（park_state_ 状态机 + futex），具体见下方“ART 侧实际 park/unpark”。
  • 失败：可中断版本抛 InterruptedException；非可中断版本保留中断状态、继续等待。
  • 回退：无回退；虚假唤醒由上层循环条件处理（AQS 自旋/检查）。
  • 成本：无竞争时 CAS 快路径；竞争时入队/阻塞/唤醒（系统调用）；量化留 ch09。
  • Condition 路径（按本版完整方法重写；本版没有 addConditionWaiter/fullyRelease，不得沿用旧 JDK 名）：
  • ConditionObject L1523；OOME_COND_WAIT_DELAY = 10ms（L1534）。
  • await()（L1734-1774）入口先做一次 Thread.interrupted() 预检查：若进入方法前中断标志已置位，立即清标志并抛 InterruptedException（此时尚未 enableWait，也不存在“先重获锁”）。预检查通过后才走 newConditionNode()（L1663-1680）——正常返回新 ConditionNode，OOME 慢路为 release(savedState) → U.park(false, 10ms) → acquireOnOOME → 返回 null（await 直接返回）；随后 enableWait(node)（L1604-1626）：校验 isHeldExclusively，置 COND|WAITING 并挂入条件队列，savedState=getState() 后 release(savedState)，失败则 CANCELLED + IllegalMonitorStateException。
  • 等待循环 while (!canReacquire(node))（L1629-1636）：若循环期间 Thread.interrupted() 为真，先尝试 getAndUnsetStatus(COND)；成功说明 signal 尚未把节点转队，置 cancelled=true 并 break；失败说明 signal 已清 COND，但可能仍在 enqueue（doSignal L1555 先清 COND、L1556 才 enqueue），所以不能据此说“已完成入队”，只记录“signal 后中断”。若 COND 仍置位 → ForkJoinPool.managedBlock(node)（RejectedExecutionException → rejected=true，下一轮改 node.block()）；否则 Thread.onSpinWait()——这正是 L1758-1759 注释的“awoke while enqueuing”，canReacquire 会重新检查前驱链接/队列入队状态。
  • 循环后：clearCurrentBlocker → node.clearStatus() → reacquire(node, savedState) 先重获锁；随后才处理中断：cancelled → unlinkCancelledWaiters(node) 并抛 InterruptedException；否则 Thread.currentThread().interrupt()（signal 已清 COND，保留中断状态）。因此“等待中被中断”不是“未重获锁就抛”：本版先把锁拿回来，再按取消位决定抛异常还是恢复中断。“signal 转队≠马上拥有锁”，被唤醒线程必须重新竞争。
  • awaitUninterruptibly：同样 newConditionNode→enableWait→循环，但只记录中断、reacquire 后恢复中断标志，从不抛 InterruptedException。
  • 定时 awaitNanos（L1786-1818）：入口同样先 Thread.interrupted() 预检查；nanosTimeout<0 归零后计算 deadline=System.nanoTime()+nanos。等待循环只有 LockSupport.parkNanos(this, nanos)，不走 ForkJoinPool.managedBlock；每次循环若中断或 deadline-System.nanoTime()<=0，尝试 getAndUnsetStatus(COND)：成功（signal 尚未转队）→ cancelled=true 并退出；失败说明 signal 已清 COND，但可能尚在 enqueue，继续由 canReacquire 重查链接并等待重获锁。reacquire 后：cancelled && interrupted → unlink + InterruptedException；cancelled（纯超时）→ 返回 remaining（remaining<=nanosTimeout ? remaining : Long.MIN_VALUE，后者表示溢出饱和）；未被取消但 interrupted → 恢复中断标志并返回 remaining。OOME-null 特例直接返回 nanosTimeout - OOME_COND_WAIT_DELAY。
  • awaitUntil（L1831-1857）用 System.currentTimeMillis() >= abstime 判断超时、LockSupport.parkUntil(this, abstime) 等待：入口先 Thread.interrupted() 预检查（有中断直接抛）；循环中若中断或到期，尝试 getAndUnsetStatus(COND) 成功则 cancelled=true 并退出。reacquire 后分三路：cancelled（signal 前中断或纯超时）→ unlinkCancelledWaiters，若 interrupted 则抛 InterruptedException；cancelled 且无中断（纯超时）→ 返回 false；未 cancelled（signal 胜出）→ 返回 true，若期间有中断则恢复中断标志。不是“signal 前中断返回 false”。
  • await(time,unit)（L1874-1902）是独立的 boolean 实现，不委托 awaitNanos：同样有入口中断预检查、deadline/parkNanos/取消 COND/reacquire；newConditionNode() OOME-null 时直接返回 false（单独一路）。reacquire 后：cancelled && interrupted → unlink 并抛 InterruptedException；cancelled 且无中断（纯超时）→ 返回 false；未 cancelled（signal 胜出）→ 返回 true，有中断则恢复标志。三者的共同点是：超时/中断都要先尝试取消 COND，再 reacquire；signal 已清 COND 但可能还在 enqueue，不能把“已清 COND”当作“已入队完成”。
  • signal()（L1573-1579）先 isHeldExclusively() 校验（否则 IllegalMonitorStateException）→ doSignal(first,false)（L1546-1563）：对每个节点 getAndUnsetStatus(COND) 成功后 enqueue(first) 转入同步队列；signalAll 同路径 all=true。
  • 失败/回退：未持锁 → IllegalMonitorStateException；OOME → 释放锁+睡 10ms+重获（或返回 null）；managedBlock 被拒绝 → node.block() 兜底（不丢唤醒）。成本：条件队列/同步队列两次入队、可能多次 park/unpark 与锁重获。
  • park 许可语义（LockSupport 约定，本 pin 源码/文档）：unpark(Thread)（L177-186）对虚拟线程走 VirtualThreads.unpark，否则 U.unpark；javadoc 明确“先 unpark 会让下一次 park 不阻塞（保留一个许可）”；park 返回不报告原因（unpark/中断/虚假唤醒），调用方必须重查条件（L217-230/L370-378）。
  • ART 侧实际 park/unpark（不是 OpenJDK Parker）：普通线程 LockSupport.park → Unsafe.park(false, 0L)（LockSupport.java:226/376；Unsafe.java:2771 为 native）→ ART jdk_internal_misc_Unsafe.cc:673-676 Unsafe_park → Thread::Park（thread.cc:352-449）。ART 每个 Thread 有 AtomicInteger park_state_（thread.h:2347），取值 0=许可可用、1=无许可、2=无许可且等待者已入 futex：Park 先 fetch_add(1)，旧值为 1 才真正等待；未计时的 park 用 futex(park_state_, FUTEX_WAIT_PRIVATE, 2, nullptr)，计时版本分别用 FUTEX_WAIT_BITSET_PRIVATE|FUTEX_CLOCK_REALTIME（绝对 deadline）或 FUTEX_WAIT_PRIVATE + timespec（相对 nanos）；EAGAIN/EINTR 被当作合法的虚假返回，ETIMEDOUT 置 timed_out，其它 errno 直接 PLOG(FATAL)。返回前把 park_state_ 存回 1（消费许可）。Unpark（thread.cc:451-466）用 exchange(0)；若旧值是 2（确有等待者）才 FUTEX_WAKE_PRIVATE 唤醒 1 个。未启动线程的 unpark 记在 Thread.unparkedBeforeStart 字段（jdk_internal_misc_Unsafe.cc:687-698），线程启动时再消费（thread.cc:697-710）。条件编译：以上协议位于 #if ART_USE_FUTEXES；#else 分支（thread.cc:440-447）会 #warning "LockSupport.park/unpark implemented as noops without FUTEX support."、UNIMPLEMENTED(WARNING) 并 sched_yield()，不是同一套阻塞/许可语义。因此这是 ART 自有的 AtomicInteger+futex 许可协议（仅 futex 构建），不存在 Parker/parker_cond_ 对象；把 OpenJDK 的 Parker 类名套到这里会指错实现，也不能把 futex 行为写成所有构建的既成事实。

5.4 atomic / VarHandle / fence 与 JMM 边界

AtomicInteger 在 Android 的实现已从 Unsafe 改为 VarHandle：

// java/util/concurrent/atomic/AtomicInteger.java:59-66（节选）

 * ...

    // private static final Unsafe U = Unsafe.getUnsafe();
    private static final VarHandle VALUE;
  • 访问语义（get/set/volatile/opaque/acquire/release/compareAndSet 等）由 VarHandle 访问模式定义；本 pin 的访问器是 public final native @IntrinsicCandidate ... (Object... args)（如 getVolatile L554-557、setVolatile L584-587、compareAndSet L745-748），即签名多态 native，不是普通 Java 方法。VarHandle.fullFence()（L2123）内部落到 UNSAFE.fullFence()（L2086）；Unsafe.fullFence/loadFence/storeFence 为 native（sun.misc.Unsafe.java:828/844/857）。
  • ART intrinsic 列表：runtime/intrinsics_list.h:55-85 列出 VarHandleCompareAndSet/CompareAndExchange/Get/Set/...；runtime/intrinsics_list.h:121-123 列出 VarHandleFullFence/AcquireFence/ReleaseFence。这意味着编译器可以选择 intrinsic；是否在某个冻结调用点真正展开仍是产物问题，不能只看列表。
  • RV64 实际入口（已核）：CAS 类由 intrinsics_riscv64.cc:4236 GenerateVarHandleCompareAndSetOrExchange 生成；核心循环在 :1276 GenerateCompareAndSet：GetLrScAqRl(order)（L1085）把内存序映射为 lr.w/lr.d 与 sc.w/sc.d 的 aq/rl 位；强 CAS 在 sc 失败时回到 lr 重试，弱 CAS 只尝试一次；引用类型 CAS 在 GC 读屏障下走 ReadBarrierCasSlowPathRISCV64（L1354 起），并对新引用执行 MaybeMarkGCCard（L4266-4274）。get/set 的 acquire/release/volatile 分别用 GenerateMemoryBarrier(kLoadAny/kStoreStore/kAnyAny...) 或带 aq/rl 的加载/存储（get L3940-4055，set L4060-4105）。这是 RISC-V 后端的具体生成路径，不是“Java 语义自动等于某条指令”。
  • AArch64 对照（本批补核）：ART 的 AArch64 后端（compiler/optimizing/intrinsics_arm64.cc:1458-1545）在无 LSE 时用 ldxr/stxr 循环，有 LSE 时用 cas/casal/cash/... 指令；强/弱 CAS 的循环/单次尝试语义与 RV64 相同，VarHandle CAS 入口在 L5825-5835，引用类型同样有读屏障慢路径。因此 JMM 语义一致，指令序列由架构/CPU 特性选择；不能把 RV64 的 lr/sc 或 AArch64 的 cas 直接套到另一个平台，也不能从源码判断某个设备是否启用 LSE。
  • JMM 边界的准确表述：Java 语义（happens-before、volatile 可见性、CAS 原子性）由规范定义；上条给出的是 ART/RV64 与 AArch64 两种实现选择。具体产物是否 intrinsify、是否内联仍需机器码依据。
  • 失败/回退：原子操作无“失败回退”；CAS 返回 false 是正常语义，由上层重试；VarHandle 调用点若不是 intrinsic，则走其 native/链接路径，语义不变、成本不同。
  • 成本：无竞争 CAS 是一次 lr/sc 循环，竞争时 sc 失败重试并可能触发缓存行迁移；具体量级需 PMU（ch09）。

6.2 IoBridge 的失败语义（可复述）

// luni/src/main/java/libcore/io/IoBridge.java:598-618（节选）
    public static int read(...) throws IOException {
        ArrayUtils.throwsIfOutOfBounds(bytes.length, byteOffset, byteCount);
        if (byteCount == 0) return 0;
        try {
            int readCount = Libcore.os.read(fd, bytes, byteOffset, byteCount);
            if (readCount == 0) {
                return -1;      // EOF
            }
            return readCount;
        } catch (ErrnoException errnoException) {
            if (errnoException.errno == EAGAIN) {
                // We return 0 rather than throw if we try to read from an empty non-blocking pipe.
                return 0;
            }
            throw errnoException.rethrowAsIOException();
        }
    }
  • 正常：返回读到的字节数；0 字节读请求直接返回 0。
  • 失败映射：native 返回 0 → Java 层 -1（EOF）；EAGAIN → 返回 0（非阻塞空管道语义）；其它 errno → ErrnoException.rethrowAsIOException()（android.system.ErrnoException，luni/src/main/java/android/system/ErrnoException.java）。
  • 短写：IoBridge.write 在本仓就是循环写全——while (byteCount > 0) { int bytesWritten = Libcore.os.write(...); byteCount -= bytesWritten; byteOffset += bytesWritten; }（L645-649）；错误经 ErrnoException.rethrowAsIOException()。
  • sendto/recvfrom 精确门（已核）：sendto(byte[]) L679-691、sendto(ByteBuffer) L694-706；失败转 maybeThrowAfterSendto L708-722（datagram ECONNREFUSED→PortUnreachableException；stream EAGAIN→返回 0）。recvfrom(byte[]) L749-759、recvfrom(ByteBuffer) L762-772；成功路径 postRecvfrom L774-788（isRead && byteCount==0→-1）；失败路径 maybeThrowAfterRecvfrom L790-808（read EAGAIN→0；connected ECONNREFUSED→PortUnreachableException；非 read EAGAIN→SocketTimeoutException）。
  • 回退/EINTR（已核到包装函数）：Linux_readBytes（libcore_io_Linux.cpp:2158-2163）与 Linux_writeBytes（L2849-2854）都调用 IO_FAILURE_RETRY。宏 IO_FAILURE_RETRY_IMPL（L203-243）：每次 syscall 用 AsynchronousCloseMonitor 监视 fd；若期间被另一线程 close()（_wasSignaled）→ should_throw 时抛 InterruptedIOException("... interrupted by close() on another thread")，否则置 EBADF；普通 EINTR 且未 signaled → 重试；其它 errno → throwErrnoException。另有 NET_FAILURE_RETRY 宏（L160-187）：异步关闭时抛 SocketException("Socket closed")，是 socket 分支而非文件 IO。注意：以上是静态源码语义，未做真实信号/线程中断实测。
6.2.1 errno → Java 异常的完整分派（按 API 分开）

ErrnoException（android.system.ErrnoException）只保存 functionName/errno；rethrowAsIOException() 统一 new IOException(getMessage()) 并 initCause(this)，rethrowAsSocketException() 统一 SocketException。具体 API 会先按 errno 做更细的映射，不能把“errno 一律 IOException”当成全部：

IoBridge.connect（L177-200）EHOSTUNREACH/EADDRNOTAVAIL → NoRouteToHostException；其余 → ConnectException；已捕获的 SocketException/SocketTimeoutException 原样抛ConnectException/SocketException

native 侧 Linux_readBytes/writeBytes 用 IO_FAILURE_RETRY：普通 EINTR 重试；被另一线程 close() 触发 AsynchronousCloseMonitor 时，文件 IO 抛 InterruptedIOException("... interrupted by close() on another thread")（should_throw）或置 EBADF；socket 走 NET_FAILURE_RETRY 抛 SocketException("Socket closed")。因此“EINTR 不暴露给 Java”是这两层包装的结果，不是内核不返回 EINTR。

  • BoringSSL 内部（本批补核）：BN_mul → bn_mul_impl（mul.cc.inc:149-195）：零操作数直接 BN_zero；两侧 width==8 时走 bn_mul_comba8（:178），其余走 bn_mul_normal（:188）——后者是 schoolbook 乘加：序言先单独算 b[0] 列（rr[0] = bn_mul_words(...)，:45），随后稳态 for 每轮 b[1..4] 四列（:51/55/59/63，指针 +=4），不足 4 个时逐次 --nb 提前返回；因此不是固定的 5-word 展开因子，也不能把序言计入每轮。本 pin 的注释明确旧的一般 Karatsuba 实现已被删除，只剩 RSA 密钥生成用的部分辅助（:116-121）；因此“大数乘法=Karatsuba”在本 pin 不成立。BN_div（div.cc.inc:156-340）注释与代码都表明是 Knuth TAOCP Vol.2 4.3.1 Algorithm D：D1 规范化、D2–D7 逐 word 估商/修正/乘减、D8 反规范化；它假设输入是公开的，不是常数时间，秘密输入应使用 Montgomery 等其它策略（:156-166）。这两点只说明算法族，不宣称具体性能或侧信道结论；RISC-V 上的大数乘法/除法仍由 BoringSSL 的 C/汇编实现决定。
  • 小/中规模乘法的内部：一侧短于 50 时，若短边长度为 1 走 multiplyByInt（L1706-1750；若乘数是 2 的幂，直接 shiftLeft，否则用 long 进位并预测结果长度）；否则走 multiplyToLen（L1802-1830）→ @IntrinsicCandidate implMultiplyToLen（L1807-1830）的标准 O(n·m) 竖式：外层每个 x[i]、内层每个 y[j]，用 long 做 32×32→64 位乘加，carry = product >>> 32。21–49 个 limb 的同对象平方在 multiply 中转到 square()（L1604-1606、L2128-2165）：len < KARATSUBA_SQUARE_THRESHOLD(128) → squareToLen（L2170-2180）→ @IntrinsicCandidate implSquareToLen（L2202 起）；更大的平方进入 squareKaratsuba/squareToomCook3，但在当前 multiply 的活分支里，只有 21–49 limb 会走平方，因为 ≥50 已被 BoringSSL 路径截走。
  • Knuth 除法的内部：divideKnuth（MutableBigInteger L1182-1232）先用 b.intLen==0 抛除零、compare 处理被除数小于/等于除数、b.intLen==1 走 divideOneWord，再对大于阈值的长数消除公共 2 的幂；一般路径 divideMagnitude（L1481-1610）执行 Knuth TAOCP Vol.2 4.3.1 的 D1–D7：D1 左规范除数、D3 估计 qhat 并用 unsignedLongCompare 最多修正两次、D4 mulsub 乘减、D5/D6 借位则 divadd 加回、D7 循环。它是 O(n·m) 的精确整数算法，不含浮点估计。
  • BigDecimal：紧凑表示——intCompact（long，L354）在幅值 ≤ Long.MAX_VALUE 时直接存储；哨兵 INFLATED = Long.MIN_VALUE（L342）表示“数位只在 intVal”；MAX_COMPACT_DIGITS = 18（L358）；scale（L322，可为任意值）；add（L1389）做 scale 对齐。只写 intVal+scale 会漏掉紧凑字段这一真实结构。
  • BigDecimal 除法边界：divide(BigDecimal)（L1757-1819）先处理 0/0（“Division undefined”）与 x/0（“Division by zero”）；非零商构造 MathContext(UNNECESSARY)，精度上界为 this.precision() + ceil(10*divisor.precision()/3)，再调用 divide(divisor, mc)；若不可精确终止，捕获 ArithmeticException 并重抛“Non-terminating decimal expansion; no exact representable decimal result.”。divide(divisor, scale, roundingMode)（RoundingMode 重载 L1688-1690 委托 int 版；int 版 L1654-1680）走带 scale 的舍入路径；divide(divisor, mc)（L1819-1870）按 intCompact/intVal 的四种组合分派到 divide(long,long,...)、divide(long,BigInteger,...) 等重载。舍入辅助 divideAndRound(long,long,int)（L4715 起）和 divideAndRound(BigInteger,...)（L4794/4874 起）按 RoundingMode 决定是否加一，不是简单的截断。
  • 失败：除零 → ArithmeticException；divide 非终止小数且未指定 rounding → ArithmeticException；MathContext 精度不足且 UNNECESSARY → 同上。
  • 成本：小规模乘法 O(n·m)、Knuth 除法 O(n·m)；大数（两侧 ≥50 limb）转为 JNI/BoringSSL，成本包含两次 int[]→BN 转换、BN_CTX/BN 分配、native 乘除和结果回转；本章不给实测数字。

8.1.1 AccessibleObject 的活代码与注释块
  • 活代码：setAccessible(boolean)（L128-132）只调用 setAccessible0(this, flag)；批量版本（L93-101）逐个调用；setAccessible0（L137-160）在 flag==true 时禁止把 Class、Method、Field 自身的构造器设为可访问（抛 SecurityException），其余情况只写 obj.override = flag。isAccessible()（L169-171）返回 override。SecurityManager 调用在 L95-97、L129-131 已被 Android-removed。

  • 真正的检查在 ART：Method.invoke、Field.get/set、Constructor.newInstance0 进入 ART 后才执行下面的检查。
8.1.2 Method.invoke 的 ART 链
Method.invoke (libcore native, Method.java:418)
  → ART Method_invoke (runtime/native/java_lang_reflect_Method.cc:75-78)
  → InvokeMethod<kRuntimePointerSize> (runtime/reflection.cc:698-778)

InvokeMethod 的顺序（reflection.cc:698-778）：

  1. 栈/初始化：检查 native 栈余量，不足抛 StackOverflowError；确保声明类已初始化，失败则保留初始化异常。
  2. String 构造器特例：String.<init> 替换为 StringFactory 调用（m = StringInitToStringFactory(m)，receiver 必须为 null）。
  3. receiver 类型：非静态方法先 VerifyObjectIsClass(receiver, declaring_class)，不匹配抛 IllegalArgumentException（“Expected receiver of type ...”）；静态方法 receiver 可为 null。
  4. 虚分派：receiver->GetClass()->FindVirtualMethodForVirtualOrInterface(m, kPointerSize)，得到实际实现。
  5. 参数个数：CheckArgsForInvokeMethod 用方法签名的参数个数与 Object[] 长度比较，不等抛 IllegalArgumentException（“Wrong number of arguments; expected N, got M”）。
  6. 访问检查：若 executable->IsAccessible() 为 false，调用 VerifyAccess；失败抛 IllegalAccessException（消息带 caller、访问标志、方法名和声明类）。
  7. 参数解包/调用：ArgArray::BuildArgArrayFromObjectArray 做拆箱/加宽/引用检查，失败抛 IllegalArgumentException；InvokeWithArgArray 调 ArtMethod::Invoke。
  8. 异常包装：目标方法抛出的任何异常被包成 InvocationTargetException（ActiveTransaction 的事务中止异常除外）；创建包装异常本身失败则保留该异常。
  9. 返回值：primitive 通过 BoxPrimitive 装箱，引用直接返回。

VerifyAccess 的规则（reflection.cc:1014-1057）：

  • kAccPublic 直接通过（即使 IsAccessible() 为 false，public 成员也不需要调用者检查）。
  • 否则从栈上 GetCallingClass(self, num_frames) 取调用者；attached native thread 取不到调用者时返回 false。
  • calling_class == declaring_class 通过。
  • kAccPrivate 且不同类 → false。
  • kAccProtected：若 receiver 非空且不是调用者的实例、且声明类与调用者不同包 → false；否则若 declaring_class->IsAssignableFrom(calling_class) → true；其余落到同包判断。
  • 最终只有 declaring_class->IsInSamePackage(calling_class) 为 true 才通过。
8.1.3 Field.get/set 的 ART 链
Field.get/set (libcore native)
  → Field_get/Field_set (runtime/native/java_lang_reflect_Field.cc:170/388)
  → CheckReceiver + VerifyFieldAccess (L46-76)
  → GetFieldValue/SetFieldValue (L79+/L270+)
  • Field_set 的完整门（L388-428；primitive 版 L431-468 同序）：先 CheckReceiver；随后无条件调用 ThrowIAEIfFieldIsNotOverwritable(f)（L351-386）——这一步与 IsAccessible() 无关，setAccessible(true) 不能绕过；再解包/转换值；之后才在 !f->IsAccessible() 时调用 VerifyFieldAccess<true>（L423，内部仍有 final 检查，L46-58）；最后 SetFieldValue。因此“final 字段不能反射写”不能一概而论：外层先按 ArtField::IsUnmodifiable/WriteProtected 判定，内层再按 IsAccessible 决定是否执行成员级 VerifyAccess 和 final 检查。具体地，静态 final 在 C+ 被外层拒绝（override 也救不了）；普通、非 monotonic、非 WriteProtected、且未命中旧 target/SDK 例外的实例 final（此时 IsUnmodifiable=false）在未 setAccessible(true) 时仍被内层 final 检查拒绝，只有 accessible=true 跳过内层才可写；如果实例 final 带 kAccMonotonic，IsUnmodifiable 会在前面的 IsMonotonic() 分支直接返回 true，外层同样拒绝。WriteProtected/旧 target 的兼容例外也要通内层（或 accessible）这一关。
  • ArtField::IsUnmodifiable 的实际规则（art_field-inl.h:511-570）：!IsFinal() → false；IsWriteProtected() → false（System.in/out/err 以及 dogfood 的 android.os.Build* 静态 final）；IsMonotonic()（kAccMonotonic）→ true；targetSdk ≤ B → false（兼容旧应用）；static 且字段类型为 MethodHandle/VarHandle/Atomic*FieldUpdater/Unsafe → true；SDK ≤ B → false；其余返回 IsStatic()。也就是说：静态 final 在 C+ 默认不可改写；普通、非 monotonic 的实例 final 会落到 IsStatic()=false，不属于 IsUnmodifiable；但带 kAccMonotonic 的实例 final 在更早分支已返回 true；WriteProtected/旧 target 是可写兼容例外。本卡不推断 kAccMonotonic 由谁设置，也不把 monotonic 属性归到 record/其它类。ThrowIAEIfFieldIsNotOverwritable 的判定：WriteProtected 字段只有在 targetSdk≤B 或 SDK≤B 时放行，否则抛；非 WriteProtected 字段在 !IsUnmodifiable 时放行，否则抛 IllegalAccessException("Cannot set ... field ...")；写 static final 时另记 BCP/App static final overwrite 指标。
  • 访问检查：VerifyFieldAccess<true> 与 Method 共用 VerifyAccess，但 num_frames=1（Field_set 本身多一层 native 帧）；receiver 类型由 CheckReceiver 检查，静态字段用声明类作为 class_or_rcvr。Field_get 没有 overwrite 外层门，但有 !f->IsAccessible() && !VerifyFieldAccess<false>（L179/207），final 读不受 final 限制。
  • 读写形态：primitive 有专用 Field_getInt/setInt 等入口；GetFieldValue/SetFieldValue 按字段类型和 is_volatile 选择普通或 volatile 访问（L79-130、L270-330）。引用字段读写还涉及读屏障/写屏障，不能只看 Java 字段赋值。
  • 失败：IllegalAccessException（不可改写的外层门、或 !IsAccessible 时的成员访问/final 内层检查）、IllegalArgumentException（receiver 类型不匹配/非 primitive 的 primitive setter）、ExceptionInInitializerError（静态字段声明类初始化失败）。本卡不把上述规则宣布为安全漏洞；它只是本 pin 的源码行为。
8.1.4 Constructor.newInstance 的 ART 链与一个必须保留的边界
Constructor.newInstance (Java, libcore Constructor.java:338-347)
  ├─ serializationClass == null → newInstance0 (native, Constructor.java:353-355)
  │    → Constructor_newInstance0 (runtime/native/java_lang_reflect_Constructor.cc:62-123)
  │    → InvokeConstructor (reflection.cc:792-833)

8.1.5 MethodHandles.Lookup.checkAccess 是另一条链

Lookup.findVirtual（MethodHandles.java:960-1000）在拿到 Method 后调用 checkAccess(refc, method.getDeclaringClass(), method.getModifiers(), method.getName())（L996），再按接口/类选择 INVOKE_INTERFACE/INVOKE_VIRTUAL 并 createMethodHandle。checkAccess（L2185-2232）的规则：

  • Object.clone + 数组 + protected 的特例：把 protected 临时按 public 处理（数组没有自己的 clone 方法）。
  • protected 构造器：去掉 protected 位（不能在异包 new protected 构造器）。
  • public 成员且 refc public 且 allowedModes != 0：快速通过。
  • 否则 fixmods(mods) 后与 allowedModes 求交；命中则 VerifyAccess.isMemberAccessible(refc, defc, mods, lookupClass, allowedModes)；protected 还允许按同包规则回退。
  • 全部失败 → throwMakeAccessException。

这条链完全在 Java 层，和 8.1.1 的注释块、8.1.2 的 ART VerifyAccess 是三套不同实现，不能合并叙述。

8.2 MethodHandle：签名多态、ART 分派与 Transformer

8.2.1 Java 面：活入口与已移除的 RI 入口
// ojluni/src/main/java/java/lang/invoke/MethodHandle.java:549,586（活代码）
    public final native @PolymorphicSignature Object invokeExact(Object... args) throws Throwable;
    public final native @PolymorphicSignature Object invoke(Object... args) throws Throwable;

invokeBasic/linkToVirtual/linkToStatic/linkToSpecial/linkToInterface 在 // BEGIN Android-removed: RI implementation unused on Android. 注释块内（自 L588 起），不是本 Android 的活入口。invokeExact/invoke 是调用点签名多态：编译器按实参生成符号类型描述符，运行时走 invoke-polymorphic，不是普通 JNI 固定签名绑定。javadoc 明确：若通过 Method.invoke、JNI 或 Lookup.unreflect 直接调用这两个方法，会抛 UnsupportedOperationException（L538-543、L574-579）。

Android 另有 invokeExactWithFrame(EmulatedStackFrame)（L1588）和 transformInternal(EmulatedStackFrame)（L1612）；前者是 Transformer/invokeWithArguments 回边，后者是所有 Transformer 的统一 Java 入口。

8.2.2 ART 分派：exact、inexact 与 Transformer
MethodHandle.invokeExact (invoke-polymorphic)
  → ART MethodHandleInvokeExact (runtime/method_handles.cc:905-912)
  → MethodHandleInvokeExactInternal (L810-842)

  • 嵌套 Transformer：Transformer.invokeFromTransform（L86-94）若目标还是 Transformer，直接调用其 transform，避免再绕 invokeExactWithFrame；普通 handle 才走 invokeExactWithFrame。

  • 失败：exact 类型不匹配 → WrongMethodTypeException；引用转换失败 → ClassCastException；目标异常原样透传（声明 throws Throwable）；通过反射/JNI 直接调 invokeExact → UnsupportedOperationException（javadoc）。invoke 比 invokeExact 宽松是语义差异，不是性能回退。
  • 实现类：MethodHandleImpl 是 Android 从零实现的直接 handle（头注释 L32-35），构造时 getMemberInternal() 取 ArtField/ArtMethod，字段 handle 的 resolveTarget 生成 DirectMethodHandle$Holder 的 get/put/volatile 目标（L56-110）；getMemberInternal 是 ART native（java_lang_invoke_MethodHandleImpl.cc:33-64），按 handle kind 物化 Field/Method/Constructor。DirectMethodHandle 被裁剪为 Holder 所需方法，Invokers 的 RI 机制在注释块中。

8.3 序列化与 zip

8.3.1 写对象图：句柄、替换与字段顺序

流头不是在 writeObject/depth==0 时写的：ObjectOutputStream(OutputStream) 构造器在 L246-258 初始化 handles/subs 后调用 writeStreamHeader()（L252），再进入 block-data 模式。writeObject(Object)（L348-368）只是调用 writeObject0(obj, false)；其中的 depth==0 是 catch IOException 后是否调用 writeFatalException(ex) 的门（Android 还吞掉写 fatal exception 时的二次 IOException），不是写流头的条件。

writeObject0（L1128-1250）的顺序：

  1. subs.lookup(obj) 处理替换表；null → writeNull()。
  2. 若 !unshared 且 handles.lookup(obj) != -1 → writeHandle(h)（回引用）。
  3. ObjectStreamClass.lookup(cl, true)；若 hasWriteReplaceMethod()，调用 invokeWriteReplace(obj)。Android 改为只做一次替换（L1155-1187 的注释保留原 for(;;) 循环），替换结果类变化时重新取 descriptor；替换为 null 则写 null。
  4. 若 enableReplace，再调用 replaceObject；替换结果与 orig 不同则 subs.assign(orig, obj) 并重新做 null/回引用检查。
  5. 按类型分派：Class/ObjectStreamClass（Android 改为可替换）、String、数组、Enum、Serializable、否则 NotSerializableException。

writeOrdinaryObject（L1469-1503）先 desc.checkSerialize()，写 TC_OBJECT 和 class descriptor，然后 handles.assign(unshared ? null : obj)，再写 record/Externalizable/普通字段。先分配句柄再写字段是循环引用的关键：字段里再次遇到同一对象时，writeObject0 会命中句柄写成 TC_REFERENCE，不会无限递归。

writeSerialData（L1549-1588）按 getClassDataLayout() 从父类到子类处理：有自定义 writeObject 的类设置 SerialCallbackContext、开 block data、调用 desc.invokeWriteObject，最后写 TC_ENDBLOCKDATA；否则 defaultWriteFields。defaultWriteFields（L1592-1645）先写 primitive 字段块，再对每个对象字段递归 writeObject0，unshared 标志来自 ObjectStreamField.isUnshared()。

HandleTable（L2359-2450）是链式哈希，不是“开放寻址+链表”：spine 存每个桶的头句柄，next 存同桶下一句柄；lookup（L2405-2415）用 hash(obj) % spine.length 取桶头，再沿 next[i] 链比较 objs[i] == obj（引用相等）。assign 按递增序号分配并插入桶链。因此两个内容相等但非同一对象的实例不会共享句柄。

类描述符/record 的句柄点不同：writeClass（L1260-1272）先写 TC_CLASS 和 class descriptor，再 handles.assign(cl)；writeClassDesc 处理 null/回引用/proxy/nonproxy，writeProxyDesc/writeNonProxyDesc 在写类型码后各自 handles.assign(desc)。而 writeOrdinaryObject 对普通 Serializable 和 record 都在写 class descriptor 后、写字段/记录数据前 handles.assign(obj)；record 分支随后走 writeRecordData（要求 slots.length==1，否则 InvalidClassException），再 defaultWriteFields，它没有普通类的自定义 writeObject 钩子。不能把“普通对象先注册句柄再写字段”的结论外推成 Class/ClassDesc 的注册顺序，也不能把 record 说成走普通 writeSerialData。

8.3.2 读对象图：先占位、后填字段、再 resolve

readObject0（L1389-1475）先处理 block data 和 TC_RESET，再按 type code 分派：TC_REFERENCE → readHandle（L1549-1570，校验句柄范围并取 handles.lookupObject），TC_OBJECT → checkResolve(readOrdinaryObject(...))，TC_EXCEPTION → WriteAbortedException。

readOrdinaryObject（L1895-1970）：

  1. 读 class descriptor，desc.checkDeserialize()；拒绝 String/Class/ObjectStreamClass 的 ordinary object descriptor。
  2. desc.newInstance()（可序列化类走第一个非可序列化父类的无参构造器；Externalizable 走 public 无参构造器），失败包成 InvalidClassException("unable to create instance")。
  3. 先 handles.assign 占位（passHandle），再读 record/Externalizable/普通字段；因此循环引用在字段读取时能通过 TC_REFERENCE 找到尚未填完的对象。
  4. handles.finish(passHandle) 关闭依赖；若 hasReadResolveMethod() 且无异常，调用 invokeReadResolve(obj)；若返回不同对象，handles.setObject(passHandle, rep)。unshared 且返回数组时还要 cloneArray，避免把流内共享数组泄漏成外部共享。
  5. 读侧 HandleTable（L3620-3710）除对象/句柄外还维护 status（OK/UNKNOWN/EXCEPTION）和 deps；markDependency/markException 把 ClassNotFoundException 沿依赖图传播到引用该对象的句柄，finish 按 LIFO 结算 lowDep。这解释了“某个类缺失时，引用它的对象也会以 ClassNotFoundException 失败”的行为。

resolveClass（L680-690）用 Class.forName(name, false, latestUserDefinedLoader())，找不到时回退 primitive 名称表；resolveProxyClass（L747-780）用 latest loader 解析接口，非 public 接口必须来自同一 loader，否则 IllegalAccessError，Proxy.getProxyClass 的 IllegalArgumentException 被包成 ClassNotFoundException。

兼容性：ObjectStreamClass.initNonProxy（L625-665）在流/本地描述符同为 Serializable、且类不是数组/record 时，如果 serialVersionUID 不等就抛 InvalidClassException（“local class incompatible: stream classdesc serialVersionUID = ..., local class serialVersionUID = ...”），并检查 proxy/enum 绑定、类名、Serializable/Externalizable 一致性。缺省 SUID 由 computeDefaultSUID（L1807 起）按类名、修饰符、接口、字段、构造器、方法签名计算；显式 serialVersionUID 由 getDeclaredField("serialVersionUID") 读取（L1793-1800）。readObjectNoData 用于流中缺少该层类数据时（readSerialData 的 hasData==false 分支）。

过滤（Android 本 pin 的实际状态）：ObjectInputFilter 逻辑在 ObjectInputStream 中被整体移除——totalObjectRefs、serialFilter、filterCheck 调用均为注释（L245-266、L287-323、L1135-1136、L1414-1415、L1492-1502、L1745-1747）。因此不能把 JEP 290 的 setObjectInputFilter/Config.getSerialFilter 当作本 pin 的运行机制；readObject 的深度/引用计数也没有 totalObjectRefs 上限。需要过滤时必须在应用层或更新的平台版本实现，不能用 JDK 文档直接外推。

8.3.3 zip：Java 解析 + zlib 原语

8.4 加密：libcore 只提供 Java API 与 provider 选择框架

8.4.1 libcore 内的选择逻辑
  • libcore 内：javax.crypto.Cipher、java.security.Security/Provider 等 API 与选择框架。Cipher 的注释明确 Android 使用自己的 provider/impl 选择代码（Cipher.java:278-294），内部持有 Provider provider（L335）与 SpiAndProviderUpdater（L372/L415）。
  • 选择逻辑是有条件的继续尝试（updateAndGetSpiAndProvider L2800-2822 → tryCombinations L2866-2942）：
  • 指定 provider（L2890-2898）：按 transform 顺序 getService，遇到第一个非空 service 即 return tryTransformWithProvider(...)；该分支没有 try/catch，不会在同 provider 内继续下一个变体（返回 null/抛异常也直接向上）。
  • 未指定 provider（L2899-2922）：遍历 Security.getProviders() × transform 变体；有 key 时先用 service.supportsParameter(key) 过滤，再 tryTransformWithProvider；尝试失败/抛异常会继续下一个候选（记住第一个异常，最终按类型抛出）。
  • 选定 SPI 后：update/doFinal 走已选 spiImpl（initParams == null 时直接复用，L2809-2812），不会在运行失败时自动换 provider；再次 init 会重新走 updateAndGetSpiAndProvider，可以重新选择；显式 provider 仍只在限定 provider 内选择。
  • libcore 外：具体算法实现由 Conscrypt（JCA/TLS provider）与 BoringSSL（native 密码库）提供。libcore 源码树中没有 conscrypt/boringssl 实现文件；JavaLibrary.bp:303 仅引用 conscrypt.module.intra.core.api.stubs 作为编译期 stub。

10.1 五条主结论

  1. libcore 是“Java API + 运行时托管实现”的混合体：String 的字符数据由 ART 运行时管理（value 字段已在源码中注释，count 编码长度/压缩位；charAt 为 @FastNative native）；把 String 描述成“Java 字段 byte[] value”在本 pin 不成立（ch03）。
  2. native/intrinsic 是多维组合，不是互斥三层：编译器机制至少有两种相关形式——①调用点替换/内联（普通 Java 方法也可被 intrinsify，如 String.equals 有 StringEqualsOptimizations）；②native callee 的 AOT intrinsic body（native 方法也可有优化体内代码）。@FastNative/@CriticalNative 描述调用约定、不保证 intrinsic；boot image 可用代码与实际待测调用点需分开核。典型链 ByteBuffer.putChar → Memory.pokeShort → pokeShortNative → ART intrinsic 与 Heap 路径（纯 Java 字节写）属于不同形态（ch01/ch02/ch03/ch04）。
  3. 交付边界在构建/APEX，不在 libcore 源码：apex_available 只表示 com.android.art/debug 允许依赖 core-oj/core-libart；实际装配链已在 ART 公共源码核到——com.android.art-base-defaults.bootclasspath_fragments=["art-bootclasspath-fragment"]，该 fragment 的 contents 含 core-oj/core-libart/okhttp/bouncycastle/apache-xml，image_name="art"、dex_preopt.profile 指向 boot image profile（ch02）。APEX 内布局、odex 参数与设备安装态仍未验证。
  4. 并发与 IO 的“语义在 Java、机制在 VM/内核”：AQS/LockSupport 的等待唤醒最终落到 VM/内核；VarHandle/Unsafe 的 fence 语义由规范定义、指令由编译器/架构生成；IO 的 errno→IOException、EOF/EAGAIN、短写处理在 IoBridge 有明确映射（ch05/ch06）。
  5. 性能结论必须与产物身份同层：源码具备 intrinsic ≠ 冻结调用点已 intrinsify；现有冻结包的 commit/boot image/odex 绑定缺失，因此在产物核验前不解释任何 cell 差异；Fixed-N diagnostic 用于研发归因/A/B，不能替代正式 ns/op（ch01/ch09）。

11.3.1 ByteBufferBenchmark.timeByteBuffer_putChar

源码：benchmarks/src/benchmarks/regression/ByteBufferBenchmark.java:276-284；参数定义 L42-49。

  • 参数：byteOrder ∈ {BIG,LITTLE}、aligned ∈ {true,false}、bufferType ∈ {DIRECT,HEAP,MAPPED}；newBuffer L51-78：size = aligned ? 8192 : 8192+8+1（即 8201），position(aligned?0:1) 在 L76；MAPPED 分支 L61-73 执行 raf.setLength(8192*8) 并映射 65536 字节，不是 8192。
  • 方法体：外层 reps，每次 position(aligned?0:1)，内层 1024 次 putChar(' ')；Caliper 只提供 reps，warmup/统计在外部 harness。
  • 调用链：DirectByteBuffer.putChar L450/L457/L444 → Memory.pokeShort L365-372 → pokeShortNative → libcore_io_Memory.cpp:164-166 或 ART intrinsic（RV64 Sh L378-381、arm64 Strh L722-726）。Heap：HeapByteBuffer.putChar L508-522 直接写 Java byte[]；不是“必解释”，JIT/AOT 仍可优化。
  • 正常/失败/回退：正常写 position 后前进；失败 BufferOverflowException、只读 ReadOnlyBufferException、已释放 IllegalStateException；无自动回退，Direct/Heap 是构造类型决定的路径。
  • 执行模式：native JNI、ART intrinsic、AOT/JIT 或解释器都可能；源码具备 intrinsic ≠ 冻结调用点已 intrinsify。缺 odex/aot_map，不能判定该 benchmark 调用点实际路径。
  • 成本：Direct 路径包含状态检查、Memory.pokeShort 的 swap 分支和 native/intrinsic 边界；Heap 路径是 Java 数组写。量级需 目标 RISC-V64 平台/Arm64 对照平台 实测与 PMU，不由源码常量推断。

11.3.3 SystemArrayCopyBenchmark 的 8×18 参数矩阵

源码：benchmarks/src/benchmarks/SystemArrayCopyBenchmark.java:22-97。8×18 是源码参数轴（8 个 primitive 方法 × 18 个长度），不是未来 eligible cell 数；eligible 以未来 run 的 manifest/harness 为准。

11.3.4 CipherBenchmark 的 provider×算法×模式矩阵

源码：benchmarks/src/benchmarks/regression/CipherBenchmark.java:51-80/134-144。

  • 参数：Algorithm=AES；Mode ∈ {CBC,CFB,CTR,ECB,OFB}；Padding ∈ {NOPADDING,PKCS1PADDING}；keySize ∈ {128,192,256}；inputSize ∈ {16,32,64,128,1024,8192}；Implementation ∈ {OpenSSL,BouncyCastle}。setUp 用 Cipher.getInstance(cipherAlgorithm, providerName) 显式 provider，再 init。
  • 方法：timeEncrypt/timeDecrypt 在 reps 内 cipher.doFinal(DATA,0,inputSize,output)；DATA 为 8192 字节，IV 16 字节（L35-44）。
  • 调用链：Cipher 选择（Cipher.java:2800-2942）→ Conscrypt OpenSSLEvpCipher → NativeCrypto.EVP_CipherInit_ex/EVP_CipherUpdate/EVP_CipherFinal_ex → JNI common/src/jni/main/cpp/conscrypt/native_crypto.cc:4135/4188/4241（Conscrypt fd1a4303）→ BoringSSL cipher.cc.inc:101/638/666、e_aes.cc.inc:162-173、cbc.cc.inc:24-63/65-132（BoringSSL 0cd1f6a9）。跨仓行号以这两个 pin 的绑定为准；若绑定失效，本段降为跨仓 gap。BouncyCastle 是另一 provider，不走这条 Conscrypt 链。

  • 执行模式：Java provider/SPI + JNI + BoringSSL native；AOT/JIT 可能优化 Java 层，但密码学主体在 native。成本包含 JNI、EVP 上下文、AES 实现选择；缺产物/CPU 特性，不做收益承诺。

11.3.5 BigIntegerBenchmark 的 1024-bit cell

源码：benchmarks/src/benchmarks/regression/BigIntegerBenchmark.java:23-47。

  • 方法：timeRandomDivision、timeRandomGcd、timeRandomMultiplication；每个方法用 new BigInteger(1024, r) 生成两个随机操作数，在 reps 内分别 divide/gcd/multiply。
  • 关键边界：1024 bit 最多 32 个 32-bit limb；乘法两侧都 <50 → Java multiplyToLen；除法 mag.length<40 → divideKnuth。因此该 cell 不触发 BoringSSL BN_mul/BN_div 的 ≥50/≥40 阈值，不能拿它推断 native 大数路径成本。

  • 成本：乘法 O(n·m)、Knuth 除法 O(n·m)，还有 MutableBigInteger 的分配/规范化；不做未测收益承诺。
