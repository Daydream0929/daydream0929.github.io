摘要

  • 三层里都存在可用代码而非概念稿：平台层 Paperclip（心跳执行、唤醒合并、运行时评审/审批、预算结构）、模式层 Magentic（经理代理 + 任务/进度台账、停摆重规划）、客户端层 claude-code-router 与 ruflo（请求路由、插件/观察面）；三条与本场景最相关的机制已核到函数+行号 [S02][S24][S09][S12]。
  • 与「CLI 会话 + 订阅额度 + 单机部署」边界兼容的路径是「分机制借鉴」而非整装平台：合并去重（调度层已核，见发现一）、台账五字段、回执强制今天即可用（零依赖）；CCR 属请求路由类、与心跳/台账不同层，其端点覆盖与订阅兼容均未知——非当前优先采用 [S24][S09][S12]。

背景与现状

本报告的出发场景是一类常见分工：旗舰模型担任「主控」，负责规划、派发与验收；订阅制 CLI（固定额度）承担具体执行；用户通过任务文件与执行端交互，并保留随时接管。这种形态的成本收益清晰，但四类问题反复出现：其一，主控过度参与排障与日志阅读，旗舰额度被机械性消耗；其二，管理者与执行者耦合在同一循环，缺少可靠的「完成/阻塞」事件与防重复派活；其三，验收依赖人肉记忆，没有运行时的评审/审批强制；其四，经验散落在会话里，无法检索、复用与去重。本次调研据此筛选出三层代表并深挖。本报告的适用假设：读者已有（或计划建设）「订阅制 CLI 执行 + 主控规划/验收」的自托管工作流，且关注点是不破坏现有订阅与权限形态、控制迁移成本——建议与结论均在此前提下给出，前提变化（如官方接口形态变化）时应按新场景重估。

口径与核验纪律：只读检索（2026-10-16），未安装未运行任何框架。核验分四级——doc（打开官方文档/README 原文）、fn（读函数级源码，给出文件+函数+行号+commit）、path（目录/文件结构级）、meta（仓库元数据快照）。两条措辞规则：带「未见」的表述=在已读材料中未发现（非绝对否定）；未归档且无官方声明时，只写「截至快照最近 push 日期」，不推断「停更/未维护」。三个深入对象各配一条与本场景直接相关的调用链（链 A/B/C，见下）。

调研发现（一）：Paperclip——平台把唤醒、验收与预算做成运行时能力

Paperclip（paperclipai/paperclip，MIT，Node.js + React）定位「用 AI 代理团队干活」的编排应用：BYO agents、每代理可选模型与 harness、看板跟踪任务与成本 [S01]（读到的 master 提交 90924d61；快照时 head 已前移 560d8953，引用一律以 pin 为准 [S26]）。机制一（链 A，fn 级，两轮核验）：心跳执行 + 运行中唤醒合并。文档侧（doc）：代理不常驻，仅在被唤醒后开启短执行窗口（启动适配器→注入提示→运行至退出/超时/取消→回写 状态/token/错误/日志）；唤醒四源（timer/指派/按需/自动化）；运行中重复唤醒「merged (coalesced) instead of launching duplicate runs」[S02]。调度侧（fn，两轮核验后修正）：真正的忙时合并发生在 server/src/services/heartbeat/queue.ts（@90924d61，4667 行）的准入路径——议题存在活动执行（if (activeExecutionRun)，L3653）时：①通用路径调用 wakeQueue.admitWakeBehindIssueExecution(...)（L3700），返回 kind:"coalesced" 即把新唤醒合并进正在运行的执行（L3739）；②Dot 适配器路径把未消费输入写成 status="deferred_issue_execution" 的持久排队唤醒，同键合并时 coalescedCount + 1（L3681），已被读取则记 status="coalesced"（L3688）；③评论/交互响应类输入走 shouldQueueFollowupForRunningIssueWake（定义 L313、调用 L4181）另开运行边界而非合并。运行结束的续接由未读输入留存语义保证：「a finish racing the event tick must leave unread input available for the next assignment」（L3661）；准入事务接线在 server/src/modules/wake-queue/index.ts（L85-98）。更正说明（初版误引）：先前引为合并主体的 execution-wait.ts recordExecutionWait()（L14-54）实为「已知门控等待（依赖阻塞/对账）诊断回执」路径——它合并的是同 idempotencyKey 的 skipped 记录，头注明确「诊断不是抑制未来 wake 的依据」（L10-11），不能单独证明调度级合并；该结论现以 queue/wake-queue 两文件为准 [S24]。代理侧触发按心跳协议五步：取身份（含预算）→ 先处理审批 → 拉「收件箱」→ 选活 → checkout 认领后才开工 [S24]。这组语义（准入合并 + deferred 排队 + 评论另开边界 + 未读输入留存）可复刻到自建的巡检/通知脚本。

机制二（doc 级）：运行时强制验收——执行策略不是「代理记得请求评审」，而是运行时强制「每次运行必须回写评论（恒定不变量）→ 可选评审（可打回）→ 可选审批（人/代理参与，运行时排除原执行者）」；approvalsNeeded: 1，多审批暂不支持 [S03]。机制三（path 级）：预算三件套（budget_policies.ts、budget_incidents.ts、budget-reservations.ts）与 heartbeat-run.ts 入口 [S06]——即预算是有策略/事故/预留语义的一等公民，但限额算法未读（未知），不据此做订阅额度换算。人类操作面成体系（审批/成本与预算/委派/活动日志/仪表盘）[S05]。适配器面（doc 级）：claude_local、codex_local、opencode_local、cursor、pi_local、hermes_local/gateway、process、http；本地适配器「假设 CLI 已安装且已登录」——据此推断登录态留在本机 CLI 侧；平台侧是否另存令牌未核（未知）[S04]。选型视角：机制全盘可借鉴；整装部署（部署+流程重编）暂不进入。

调研发现（二）：Microsoft Agent Framework · Magentic——经理台账与停摆重规划

选型背景（meta/doc 级）：microsoft/autogen 主仓截至快照最近 push 为 2026-04-15（未归档）；官方 Discussion #7066 宣布与 Semantic Kernel 合并为 Microsoft Agent Framework，后者同团队维护、2026-02 迁移博文面向 RC [S10][S11]。Magentic 由 AutoGen 时代 Magentic-One 演进为 Agent Framework 官方编排模式（文档发布 2026-09-21/更新 2026-10-06）[S08]。

机制（链 B，fn 级）：经理代理产出任务台账并进入协调循环——按上下文动态选择下一位执行者；每轮更新进度台账五字段（满足/绕圈/推进/下一位/指令）。停摆判定在 python/packages/orchestrations/agent_framework_orchestrations/_magentic.py（@deecbcb0，1859 行）：_run_inner_loop_helper（L1100）中 L1149-1158——「无推进或绕圈」则 stall_count += 1（否则 max(0, stall_count-1) 衰减），超过 max_stall_count 即 _reset_and_replan(ctx)；_reset_and_replan（L1189）依次执行 magentic_context.reset()（L1200；实现 L388-396：清历史、stall_count=0、reset_count += 1）→ 重置参与者（L1203）→ manager.replan（L1206）→ 广播 REPLANNED 事件（L1207）。人工介入链：计划评审响应 handle_plan_review_response（L1027-1057）支持 Approve 放行 / Revise 打回并重规划；检查点暂停-恢复在文档示例中演示；上限有三：max_round_count/max_stall_count/max_reset_count；并发警告：不要跨并发工作流共享有状态 manager（用 manager_factory 隔离）[S09][S08]。供应商面（path 级）：python/packages/ 供应商/存储包矩阵齐全（anthropic/openai/gemini/ollama/mistral/mem0/redis/postgres…），代理级独立 client 使「强模型经理 + 轻量模型执行」在结构上成立；跨供应商混搭无官方实测数据（未知，不作省额度承诺） [S07][S08]。

选型视角：价值在信息结构（台账五字段→中文进度卡；停摆→巡检告警；计划评审→开工确认点）；形态不达标（库，需自建进程），且无任何现成 CLI 接线（见适配空缺节）[S07][S08]。另注：Magentic 的经理本身在编排循环内逐轮驱动，本报告只借鉴台账字段与停摆思想，不照搬「每轮调用旗舰模型」的用法。

调研发现（三）：CLI 原生层——本地网关路由（CCR）与插件化团队（ruflo）

claude-code-router（doc+fn 级）：定位「面向编码代理的本地模型网关与控制面」——给一批 CLI 一个稳定本地端点（默认 http://127.0.0.1:3456），其后统一管理 providers/模型/账号/路由规则；能力含重试、凭据池、键轮转、有序回退与请求日志/令牌/成本观测；协议面覆盖 OpenAI/Anthropic/Gemini/OpenRouter/DeepSeek/SiliconFlow/Moonshot/Mistral/Z.AI/Bailian 与自定义端点 [S12]。链 C（分两层核验）：脚本层（fn）——packages/core/src/routing/route-script-runtime.ts 的 RouteScriptRuntime（L57）执行 resolveRouteScript（L83/L125），其熔断键（L130）与超时（L146）管理的是用户路由脚本 worker 的执行，不代表供应商层行为 [S12]；供应商层（doc）——重试、凭据池、键轮转、有序回退为 README 功能清单声明，本次未见实现级核验，两层不可混同。接线方式的准确说法是「客户端需一次性指向本地端点（CCR 以 Agent Profiles 的 environment/launch 入口管理这一步，README L228），此后切换供应商/模型才无需改各 CLI 配置」——「不改配置即生效」的表述并不充分 [S12]。支持清单未见 Qoder（空缺见下节）[S12]。

ruflo（doc+path 级）：包名 claude-flow v3.56.10（MIT），以 Claude Code 插件市场直装（ruflo-core/console/mods），其他客户端经 npx ruflo mcp start 接 MCP；TUI 含 Overview/Cost/Swarm/Events/Missions 视图 [S13]。结构实查：plugin/{agents,commands,hooks,scripts,skills}、v3/@claude-flow/cli、v3/mcp/tools/swarm-tools.ts、plugins/ruflo-console/hooks/cost.ts 等 [S14]。作者自述边界：「Claude Code 与 Codex 已有强原生能力，RuFlo 是附加的协调/记忆/工作流层」[S15]；hook support depends on the client（原文）——Qoder 仅 MCP 面或可用 [S13]。记忆与 swarm 的机制未逐读（未知）。

同层对照与措辞修正：claude-squad 用 tmux+worktree 管多 CLI 会话（快照最近 push 2026-08-20，未归档；其余能力未见/未核）[S16]；coder/agentapi 已归档 [S17]；LangGraph 的 checkpoint 系与 prebuilt/interrupt 仍在主仓维护，langgraph-supervisor-py 已归档（2026-07-15）[S18]；RouteLLM 截至快照最近 push 2024-08（未归档，维护状态未确认——不作「停更」断言）[S21]。

订阅制 CLI 执行端的适配空缺（逐项核）

以下为各候选与订阅制 CLI 执行端（以 Qoder CLI 为重点核对对象；其他订阅制 CLI 同理）的适配空缺核对结果：

候选结论依据（等级）
Paperclip需自建：适配器清单未见 Qoder；process 适配器可包任意 shell 命令但官方明示无跨运行会话持久（不适合交互式会话复用）；提供 External Plugin 机制可自建适配器（须处理会话持久与人工接管）S04/S25（doc）
claude-code-router未核：支持清单未见 Qoder；能否接入取决于 Qoder CLI 是否支持自定义端点覆盖——未知S12（doc）
ruflo部分：插件面（console/mods/hooks）为 Claude Code 专属→不可用；MCP 面面向支持 MCP 的客户端→Qoder CLI 具备 MCP 配置能力，或可用、需实测S13/S14（doc+path）
Magentic / Agent Framework需自建 wrapper：库形态，无任何现成 CLI 接线S07/S08（path+doc）

落地建议（唤醒/去重/预算、持续执行与状态真实性、人工接管、学习依据）

四组建议全部落在现有终端会话 + 本地脚本 + 项目文件内，零新依赖；每条给「来源机制（带等级）→ 最小做法 → 可数验收口径」。护栏重申：不新增常驻经理模型、不转 API、人工接管保留。四组均为工程建议，未经运行实测；效果以可数验收口径为准，非已验证的节省数据。

A. 主控的事件唤醒、去重与预算。 机制来源：链 A（coalesce+幂等键+回执不吞未来唤醒，fn，[S24]）、四类唤醒语义（doc，[S02]）、预算三件套（path，[S06]）。最小做法：①「唤醒主控」限定三类事件——任务完成回执、真阻塞/需决策、用户点名；②幂等分两层：事件层按「任务 / 事件 / 修订版本」标识——同一事件的重复触发可去重；通知层区分发送成功与接收/处理确认（sent 与 ack 分离），同一任务产生新 revision 时不因旧 sent 记录被吞，已发送或处理期间出现的新进展保留为未读版本、衔接进下一次通知（等价 coalesce 的「更新原通知」语义，但以 revision 为最小单位）；③预算三层观察表只统计三个可数指标：每日被唤醒次数/必读汉字量/重复派活次数（不换算公开 API 价）。验收：按预期事件 ID/版本对账——抽查恢复（暂停后继续）、重复（同事件重触发）、修改（同任务新 revision）三类场景均无漏报、无吞报，再核对三指标连续两周下降（不只看「回执数=完成数」的总数比对）。

B. 执行端持续执行与「状态真实性」。 机制来源：台账五字段（doc+fn，[S08][S09]）、comment-required（doc，[S03]）、停摆思想（fn，[S09]）。最小做法：①进度卡固定五字段：目标/当前事实/是否推进/下一步/执行者；②状态必须绑定可复核锚点（报告路径、sha256、日志名、命令输出片段），口号式「已完成」不算数（本报告的元数据与来源台账即示范）；③完成回执强制（成败都回写「结论+路径」）；④巡检加「疑似停摆」判定：须结合任务 handle（承诺的阶段产出）、阶段时限与可观测进度综合判断；长编译/长启动类等待不因两次巡检无新产物自动认定停摆（仅标黄提示、不打扰）。验收：随机抽 3 条状态行，按锚点 60 秒内复核通过。

C. 人工接管。 机制来源：计划评审 Approve/Revise 与检查点续跑（doc+fn，[S08][S09]）、活动日志信息结构（doc，[S05]）。最小做法：①任务单顶部「确认区」（目标/边界/验收），改动即视为介入；②接管靠「阶段账本」（进度文件顶部三行摘要）而非回放日志；③接管留痕：人工改写标注 [接管：谁/何时/改了什么]。验收：第三人按任务单+三行摘要在 5 分钟内复述状态并指出下一步。

D. 学习与依据。 机制来源：发现三元组（本报告方法示范）、ruflo 技能/记忆结构（path，[S14]）、记忆服务（meta，[S20]）。最小做法：①项目 Findings 文件每项带 source_ids / verification / applies_to / date，新增前查重同题；②Skill/HANDOFF 升版必须附来源锚点与核验等级——禁止把 doc 级宣称写成实测；③过期以「复核日期+重跑来源」处理，被推翻保留「已更正」行。验收：一个月后随机抽 5 条沉淀结论可复现到来源。

建议分级负责人验证办法回滚
A 三类事件+合并去重+三指标马上可做主控 + 巡检脚本两周指标曲线恢复旧通知策略
B 五字段+锚点绑定+回执强制马上可做执行端（模板）抽 3 条 60 秒复核退回自由文本
C 确认区+阶段账本+接管留痕小范围试验用户与主控一次接管演练取消确认区
D 发现三元组+升版锚点纪律马上可做调研团队（本报告示范）抽 5 条复现保留旧格式
E CCR（请求路由类）观察（非当前优先）—仅当出现端点覆盖与订阅兼容的可行依据再评估 [S12]—
F Paperclip 整装 / Magentic 自建 / 记忆服务化 / 转 API 方案暂不做待论证先跑 A-D 再评估—

结论与建议

三条结论。第一，当前改进重点是补「事件与台账」，而非引入新工具：Paperclip 的合并唤醒（两轮核验后核到 heartbeat/queue.ts 准入路径）与 Magentic 的停摆重规划（fn 级核到 _magentic.py L1149/L1189）都是用结构化事件替代人读日志，本报告的 A/B 两组建议即为零依赖复刻 [S24][S09]。第二，CCR 属「请求路由类」，与心跳/台账层不同，且其端点覆盖与订阅兼容均未知——非当前优先采用；先做事件+台账+真实交付（建议 A–D），不改动现有认证与模型路由；整装平台与自建编排在边界内收益/成本比不成立 [S12][S01][S07]。第三，适配空缺是硬约束而非细节：Paperclip/CCR/ruflo/Magentic 均无现成 Qoder 通道（Paperclip 需自建 External Plugin，process 适配器无会话持久），任何落地讨论都不应绕过「保住订阅会话与人工接管、不新增常驻经理模型、不转 API」的护栏 [S25][S12][S13][S07][S08]。

行动清单：先做 A/B/D（零依赖，两周出曲线），准备 C 的接管演练；CCR 仅观察，待出现端点覆盖与订阅兼容的可行依据再评估，当前不开展接入或路由试验；其余保持「机制已借鉴、组件不引入」。以上建议均以背景所列适用假设为前提（保留现有订阅与权限形态、迁移成本受控）；对公开信息的小范围试用、以及对官方接口变化的增量评估不受此限。本报告为公开调研性质，未安装未运行任何框架、未做成本外推；结论与建议以来源台账与三条调用链为准。
