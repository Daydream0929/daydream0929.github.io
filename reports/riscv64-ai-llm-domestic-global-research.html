1. 核心判断（TL;DR）

  • 【C*】“RV64 设备能运行 Linux”不是“具备 RISC-V LLM 加速能力”的同义句：RVV 需由 Linux riscv_hwprobe 或 HWCAP 检测，用户态向量状态又可受 prctl 控制；编译器还必须生成与目标 -march/ABI 匹配的代码 [S01][S02][S03][S04]。
  • 【C*】开源 LLM 的最可见入口是 GGUF + llama.cpp 的 CPU/RVV 路径；上游已提供 RISC-V/RVV 构建选项和内核，但没有通用 riscv64 发布二进制，因而“源码可构建”仍须经过目标机器的功能、性能与稳定性验收 [S05][S06][S18]。
  • 【C*】ONNX Runtime、TVM 已给出 riscv64 Linux 的构建或交叉编译路径，ExecuTorch 的一等 RISC-V 支持仍在演进；它们说明工程入口存在，却不能替代特定模型、算子集、后端和目标 SoC 的实机验证 [S07][S08][S09][S10]。
  • 【S】中国生态已形成 RISC-V CPU/RVV、NPU SoC、板卡、Linux 发行版与 Qwen 本地模型路径的连接点，但量产交付的主要风险转向内存带宽、驱动和编译器成熟度、模型量化、后端受理率与设备矩阵，而非“是否为 RISC-V”这一标签 [S13][S14][S16][S18][S20]。
  • 【P】选型和发布应分别记录 CPU ISA/RVV/VLEN、NPU 实际受理、模型量化、上下文/KV cache、首 token、热稳态 token/s、RSS、功耗/温度和质量；单报 NPU TOPS、模型参数或一次短测 token/s 均不足以证明 LLM 体验 [S01][S02][S14][S16]。

2. 问题、范围与方法

本文将 RISC-V 64 位 AI/LLM 部署拆成四个不可相互替代的层：第一层是 RV64 Linux 与工具链能否稳定运行；第二层是 CPU 是否含 RVV 及其向量长度、内核使能和二进制分发是否匹配；第三层是 SoC 是否含独立 NPU/TPU、其驱动/编译器是否真正接受目标模型；第四层是模型格式、量化、推理运行时、上下文与内存系统能否满足用户 workload。这样拆分可避免将 CPU ISA、向量扩展与专用加速器混为一项“AI 算力”。

研究优先采用 Linux、GCC/LLVM、PyTorch/ONNX/TVM、llama.cpp/Qwen 等上游资料，以及芯片/板卡/操作系统厂商的公开页面。直接规格或接口事实标为【C】；多个一手来源支持的工程结论标为【C*】；对量产成熟度、实际 LLM 速度、功耗和市场走向只作受限的【S】判断。任何厂商 TOPS、可运行参数量或演示宣称只保留为原始口径，不与其他芯片作归一化排名。

3. 全球技术基线

3.1 RV64 Linux、RVV 与二进制分发是三个独立的前置条件

Linux 的 RISC-V Vector 文档明确将 V 扩展作为独立硬件能力处理：应用可通过 riscv_hwprobe 或 COMPAT_HWCAP_ISA_V 判断，且可通过 prctl(PR_RISCV_V_SET_CONTROL) 设置用户态向量状态。riscv_hwprobe 还提醒，若查询的 CPU 集合在某项能力上不一致，结果可能无法作为统一基线使用 [S01][S02]。因此，面向 RVV 的模型内核应采用能力发现、同构 CPU 集合约束或明确的 CPU 回退，而不应只以 uname 的 riscv64 标识分发。

LLVM 将 RVV 表示为 scalable vector，并持续优化向量长度设置和固定长度向量 lowering；GCC 以 -march 指定 ISA 扩展，并要求 ABI 与 ISA 选择兼容 [S03][S04]。对推理软件而言，这意味着源码中的 RVV intrinsic、编译器向量化和运行时实际使用 RVV 是三层不同证据：前两层可证明潜在路径，最后一层仍需通过目标机反汇编、功能测试和 profiler 验证。不同 VLEN、缓存、内存带宽、调度策略与核间异构都会使相同源码表现不同。

层次可直接检查的对象常见误判正确的工程动作
RV64 基础环境Linux、动态链接、基础 ISA把 RV64 当成“已有向量/NPU”先建立普通 CPU 功能基线
RVV 可用性riscv_hwprobe、HWCAP、prctl根据架构名直接执行 RVV 二进制运行时发现、按特性分发与回退 [S01][S02]
编译代码-march、ABI、汇编、intrinsic编译通过即代表目标硬件可跑在目标机核验 ISA、非法指令和性能 [S03][S04]
NPU/TPU 后端驱动、编译器、模型受理报告SoC 标称 TOPS 等于模型已上 NPU记录图切分、未受理算子和端到端开销

3.2 LLM 与通用推理运行时：入口存在，产品化仍以目标验证为准

llama.cpp 的 CPU CMake 配置已包含 RISC-V/RVV 相关开关，GGML 源码存在 RVV 内核；Qwen 的 llama.cpp 指引也提供 GGUF 下载与本地运行的版本要求 [S05][S18]。这为 RV64 Linux 上运行量化 Qwen/其他 GGUF 模型提供了现实入口。边界在于，上游没有提供通用 riscv64 发行二进制，且特定 RISC-V 扩展/编译配置会影响构建与执行，因此应将它视为“可由源码适配和验证的路径”，而非“所有 RISC-V 设备已认证的 LLM 平台” [S06]。

ONNX Runtime 官方构建文档已列出 Linux RISCV64，MLAS 的构建逻辑也包含 RVV 内核选择与标量回退；TVM 文档给出了 riscv64-unknown-linux-gnu 的 LLVM 交叉编译示例 [S07][S08][S09]。这些能力更适用于受控模型、交叉构建和编译部署链路，但不等于已存在覆盖所有 Transformer 算子和所有加速器的统一 RISC-V 后端。ExecuTorch 将一等 RISC-V 支持列为进行中的 RFC，规划以 RV64GC(V) Linux 与 XNNPACK 为基础，故项目采用时需以目标版本和实际 operator coverage 复核，而非将 RFC 当作已完成的通用支持 [S10]。

3.3 全球 IP 与加速器：区分向量 CPU、NPU IP 与整机系统

国际生态同时出现三种不同路线。SiFive X280 是 64 位 RISC-V 向量处理器 IP，说明 RVV 可作为 CPU/vector 计算路径；Semidynamics Cervell C1 则定位为可编程 RISC-V NPU IP，属于专用推理单元 [S11][S12]。两者都不能单独推出某块开发板的 LLM 速度：前者受 CPU 核数、VLEN、内存和软件内核影响，后者还取决于模型编译器、数据类型、算子集合和主机/NPU 数据传输。

【C*】全球 RISC-V AI 的稳定技术主线不是一个统一的“RISC-V AI API”，而是 Linux 特性发现、编译器目标控制、通用 CPU/RVV 内核、图编译/运行时与厂商 NPU 工具链的组合。图 2 将这几层的边界并列展示。对团队而言，最重要的可观测物是实际执行路径和回退，而不是芯片宣传页上的单一算力字段 [S01][S03][S05][S07][S11][S12]。

4. 国内发展、差距与机会

4.1 中国 SoC 与板卡：已出现 CPU/RVV/NPU 组合，但规格不能替代模型验证

SpacemiT K1 的公开资料列出 X60 RISC-V CPU、RISC-V 64GCVB/RVA22、RVV 1.0、不同集群 VLEN 以及 2 TOPS NPU 和最高 16GB LPDDR4/4X；这使其成为可同时讨论 RVV 和 NPU 的中国 SoC 样本 [S13]。K3 的公开资料将其定位于更高端的端侧/本地 AI 场景，并披露 RISC-V CPU、向量与 AI 核组合；其“可本地推理 30B 模型”等表述应保留为厂商能力定位，不能在没有模型、量化、上下文和测试条件时转换成 token/s 结论 [S14]。

ESWIN EIC7700 的公开资料说明其采用 SiFive P550 CPU 集群与 13.3 TOPS INT8 DNN 加速器；StarFive JH7110 则公开为四核 RISC-V CPU 与 GPU 的 SoC，页面没有标称 NPU/TOPS [S16][S17]。这两个样本说明，“RISC-V 板卡”内部差异很大：有 NPU 的平台仍需模型编译和受理验证；没有 NPU 的平台可作为 RV64/Linux/RVV 或轻量 CPU 推理和控制面验证环境，却不应被要求承载超出内存预算的现代 LLM。

Milk-V Oasis/SG2380 的公告描述了 P670 CPU、X280 向量核和最高 20 TOPS INT8 的目标配置，但公告同时标明项目处于搁置状态，不能作为当前可采购量产桌面系统的证据 [S15]。这也提醒方案评审必须单独确认产品状态、固件/BSP、驱动、可获得内存配置和长期软件维护，而不能仅从芯片计划或开发板发布新闻推断项目可交付性。

4.2 模型、运行时与操作系统：连接点正在形成，统一性仍不足

Qwen 官方文档为 llama.cpp 提供 GGUF 获取和运行说明，Qwen3 的本地部署入口可以与上游 llama.cpp 的 RISC-V/RVV CPU 路径组合使用 [S05][S18]。这是一条可验证的“国内开放模型 + 上游运行时 + RV64 Linux”原型路径，但 Qwen 文档并未将所有 RISC-V SoC 列为认证硬件，因此不能把格式兼容写成每个设备上的已验证性能。MNN 的 CPU 构建文件中也有 RVV 后端编译选项，说明国内运行时对向量路径存在代码层连接；其 README 或构建项本身不证明特定 Qwen 模型、长上下文或 NPU 委派已可量产 [S19]。

openEuler 24.03 LTS 公布了 RISC-V 原生支持，并提到 SG2380 与 JH7110 等平台。它降低了操作系统、内核和发行版适配门槛，却不替代模型运行时、NPU SDK、量化或性能验证 [S20]。图 3 概括国内外生态中“开放模型—运行时—SoC—OS”的连接关系：当前机会是将这些分散的连接点做成可复制的模型转换、能力发现、基准和回归链路；当前差距则是设备特性、编译器/驱动版本、后端受理和公开评测口径尚未形成统一契约。

4.3 机会与差距：从可启动原型转向可运营的异构部署

【S】国内 RISC-V AI 的短期价值不在于宣称一个统一胜出的硬件平台，而在于将开放模型、小型/量化模型、RVV CPU 内核、厂商 NPU、Linux 发行版和本地化场景组合为可验证方案。对控制、机器人、网关和端侧原型而言，CPU/RVV 路径可提供最低可运行基线；对资源更高的 SoC，NPU 路径可被当作独立加速候选。两条路径必须以相同 workload、质量和资源指标对照，不能因同在一个 RISC-V SoC 上便合并为同一性能结论 [S01][S13][S14][S16][S18]。

【P】最应优先建设的基础设施是设备能力清单与部署证据链：启动时采集 ISA/RVV/VLEN、核拓扑、内存和驱动版本；编译阶段锁定 -march、编译器和模型转换版本；运行阶段记录 CPU/RVV/NPU 图分配、回退与复制；发布阶段保留模型 hash、量化、上下文、token/s、RSS、温度/功耗和质量结果。它能将“开发板能跑”升级为可定位、可回归、可解释的产品能力。

5. 关键机制深挖

5.1 ISA、RVV 与编译分发：功能可用性先于向量优化

接口与实现依据。 Linux 提供 riscv_hwprobe、HWCAP 与 prctl(PR_RISCV_V_SET_CONTROL) 等接口，用来查询和控制用户态 RVV 条件；LLVM 和 GCC 分别通过 RISC-V 目标后端、-march 与 ABI 规则把源码映射到目标 ISA [S01][S02][S03][S04]。实现上，应用或运行时应在进程启动或工作线程建立阶段确定特性集合，再选择标量、RVV 或厂商专用内核；构建系统则应保留对应的目标字符串、编译器版本、ABI 和反汇编证据。

失效边界。 仅检测到 riscv64 并不能保证 V 扩展存在、已经对当前任务开启或在所有可调度 CPU 上一致；即使存在 RVV，VLEN、微架构、编译器版本和内存访问模式也会改变结果。将一个 rv64gcv 构建投放到不含 V 的机器会触发非法指令；将单一 VLEN 的短测结论迁移到另一颗核，也可能因向量设置开销、cache 或带宽而失效。静态向量化报告不能证明真实 LLM 热点已进入向量路径。

验证条件。 每次测试保存 riscv_hwprobe/HWCAP 结果、核拓扑、内核版本、prctl 策略、编译器和完整 -march/ABI；对标量和 RVV 产物分别跑同一模型、相同 prompt/上下文和固定线程策略。结合反汇编确认目标指令，结合 runtime profile 确认热点实际走入该内核；如 CPU 集合不一致，应绑核、分组调度或回退到可移植实现。功能、数值输出和长时间稳定性要先于速度比较。

成本与权衡。 多 ISA 产物、动态分发和特性测试会增加构建、包体、CI 与故障排查成本；强制统一 CPU 集合会降低调度弹性；为追求向量化而重写内核可能提高维护代价或损害无 RVV 机器的可移植性。收益应以真实模型/上下文的端到端指标计量，而非仅以汇编指令数或理论向量宽度计量。

5.2 LLM 运行时与模型格式：GGUF 入口不等于整条推理链已优化

接口与实现依据。 llama.cpp 提供 GGUF 模型加载和 RISC-V/RVV CPU 构建入口，Qwen 文档给出以 llama.cpp 运行指定 GGUF 文件的模型侧接口；ONNX Runtime 的 RISCV64 构建、TVM 的 riscv64 LLVM target 和 ExecuTorch 的 RISC-V RFC 则提供图模型及 PyTorch 路径的实现依据 [S05][S07][S09][S10][S18]。实现工作需要同时管理 tokenizer、权重量化、矩阵乘内核、采样、线程、KV cache、内存分配和模型图的受理/回退。

失效边界。 模型“能加载”可能只说明权重和格式兼容，不能说明预填充、解码、采样、长上下文或多并发均满足目标；小模型也可能因 KV cache、临时张量或内存碎片在持续运行中失败。ONNX/TVM 的交叉编译可产出目标代码，不代表所有 Transformer 算子、动态 shape 或第三方 NPU 后端都被覆盖。ExecuTorch 的 RFC 说明方向和阶段，不能被写成已完成的一等 RISC-V 发布支持。

验证条件。 固定模型 hash、GGUF/ONNX/PT2E 格式、量化、tokenizer、prompt、采样参数、上下文、线程和 CPU 亲和性，分别测加载、prefill、首 token、稳态解码、最长上下文、并发和持续运行。同步记录 RSS、KV cache、内存峰值、失败/回退和任务质量；对于图运行时，还应保存算子覆盖、未受理节点、数据复制和实际后端报告。比较不同量化时必须以质量阈值与完整用户任务做门槛，而非仅比较 token/s。

成本与权衡。 更低比特量化减少权重和带宽压力，却可能降低任务质量并提高转换/校准成本；更大的 batch 可能提高吞吐，却损害交互首 token 与内存；为了减少复制而复用缓冲区会增加生命周期管理复杂度。兼容更多模型格式与运行时会加大测试矩阵，故应先收敛到有业务价值的模型、上下文和硬件组合。

5.3 NPU、内存与端到端指标：标称 TOPS 需要被实际图执行证伪或确认

接口与实现依据。 SpacemiT K1/K3、ESWIN EIC7700 等公开资料说明部分中国 RISC-V SoC 同时具备 CPU、向量或 DNN/NPU 单元 [S13][S14][S16]。这些硬件通常通过独立驱动、模型转换器和厂商编译器接受图或算子；CPU/RVV 路径则由通用运行时和内核承担。实现设计必须把权重、KV cache、激活、NPU buffer、host/device 复制和系统内存竞争共同纳入资源账本。

失效边界。 INT8 TOPS 是特定精度和条件下的峰值操作数，不等于某个量化 LLM 的 token/s、首 token、长上下文或持续功耗。Transformer 的算子、动态序列、量化格式、KV cache、带宽、编译器支持、CPU/NPU 同步与未受理节点都可能导致局部 NPU 最快、端到端反而更慢。更重要的是，SoC 含 NPU 并不证明当前模型真的经过该 NPU 编译和执行；只看初始化日志或厂商规格页属于失败边界。

验证条件。 对每个模型路径，报告实际 NPU 编译成功状态、接受图/算子比例、CPU/RVV 回退节点、传输/同步时间、加载和缓存时间；并在相同输入上对比纯 CPU、CPU+RVV 和 NPU 主路径。端到端结果至少覆盖 prefill、首 token、稳态 token/s、P50/P99、峰值 RSS、NPU/CPU 利用率、温度/功耗代理指标与输出质量。连续运行、最长上下文和设备热稳态须另行记录，避免把一次短测外推为产品体验。

成本与权衡。 NPU 专用模型或静态 shape 可提高受理率，却会增加转换、调试、精度回归和版本锁定成本；使用更大内存 SKU 可容纳模型和 KV cache，却提高 BOM、功耗和散热设计压力；维护 CPU 回退可提高覆盖，却扩大测试矩阵。负责人应把资源、质量、维护和供应可用性一起纳入门槛，而不是只选择峰值 TOPS 最大的方案。

6. 演进方向与情景

RISC-V AI/LLM 的技术演进更像多条链路逐步接合：Linux/LLVM/GCC 让 RV64 与 RVV 的基础能力可发现、可编译；llama.cpp/GGUF 给开放模型提供 CPU 入口；ORT、TVM 和 PyTorch 生态逐步补足图模型与部署路径；中国 SoC 和发行版让本地板卡、NPU 与 OS 组合更可获得 [S01][S03][S05][S07][S09][S10][S13][S16][S20]。但这不意味着异构性会快速消失：不同芯片的 VLEN、内存、NPU SDK、驱动、模型格式和后端覆盖仍会决定产品级差异。

图 3 所示的生态连接还意味着，模型团队、编译器/运行时团队和 SoC 团队需要围绕同一 workload 协作。模型团队不能只交付参数量和权重；芯片团队不能只交付 TOPS；系统团队也不能只报告能启动 Linux。共同事实应包括输入分布、上下文、质量标准、资源预算、实际执行路径、回退和长期热稳定性。只有这些字段可追溯，RISC-V 的开放软件优势才可以转化为可发布的平台能力。

6.1 对研发组织的含义

组织应按“一个可重放的模型 workload”而不是按 CPU、NPU、模型或 OS 各自的局部指标分工。模型负责人定义质量、上下文和量化边界；运行时负责人输出模型受理、图切分和回退证据；编译器/系统负责人管理 -march、特性发现、线程、内存和二进制分发；芯片/驱动负责人提供 NPU 受理、性能与功耗诊断。共同发布门禁则比较相同模型和输入下的 CPU、RVV、NPU 端到端结果。

6.2 对个人能力的含义

从 RISC-V Linux 开发走向 AI/LLM 性能负责人，关键不是记住一组扩展名，而是能把 ISA、代码生成、模型格式、内存和硬件后端建立证据链：先判定机器实际拥有何种能力，再解释编译产物和运行时走了哪条路径，随后以正确性、首 token、稳态、内存和热状态验证收益，最后把设备差异沉淀为能力矩阵和自动回归。这样才能在开放 ISA 的灵活性与异构设备的复杂度之间做出可复核取舍。

7. 建议与验收

7.1 从第一天建立“RISC-V LLM 工作负载合同”

项目开始时应固定目标设备、CPU ISA 与扩展、RVV/VLEN、RAM、内核/BSP、驱动、编译器、模型和量化；同时定义语言、任务、prompt/输出长度、最大上下文、并发、质量阈值、延迟、内存、功耗与离线/联网边界。它将 hwprobe、-march、模型格式和 NPU 受理等底层条件转换为可验收的产品合同 [S01][S02][S03][S18]。

第二步是为每次运行保存执行证据：实际选择的 CPU/RVV/NPU 后端、模型编译日志、图受理与回退、线程/绑核、加载、prefill、首 token、稳态 token/s、RSS、温度/功耗和质量。第三步才是优化内核、量化、图编译、批处理或缓存。这个顺序可避免把单次启动成功或芯片规格页误判为平台收益。

7.2 团队机制建议

  1. 建立 RISC-V 能力清单：按设备记录 ISA、RVV/VLEN、核拓扑、内核、BSP、驱动、NPU SDK、内存和已验证运行时版本。
  2. 建立 双基线：每个候选模型同时保留可移植 CPU 基线与 RVV/NPU 优化基线，优化路径不可用时必须有可解释回退。
  3. 建立 模型受理报告：保存模型转换、实际图/算子分配、复制、同步、缓存和未受理原因；禁止以 NPU 初始化成功替代图级证据。
  4. 建立 资源稳态协议：分开测试加载、prefill、首 token、短/长上下文、并发与连续运行，保持温度/电源/频率和输入版本可复现。
  5. 建立 跨层发布门禁：模型、编译器、内核、驱动或固件任一升级时，同时检查质量、非法指令、回退率、内存、热稳态和端到端 SLO。

8. 不确定性与研究限制

  1. 本报告不对 RISC-V、Arm、x86 或任何厂商做市场份额、出货量、性能或能效排名；公开资料的模型、量化、序列长度、内存、温度和测试方法不同，不能归一化比较。
  2. Linux、编译器和上游源码所述的“支持”表示接口、构建或代码路径存在，不等价于特定模型、特定板卡的完整功能、稳定性或量产认证 [S01][S03][S05][S07][S10]。
  3. 芯片 TOPS、可推理参数量和演示口径不等于 LLM 的首 token、稳定 token/s、长上下文、并发、功耗或质量；这些均需在目标 workload 上单独实测 [S13][S14][S16]。
  4. RISC-V 设备可能在 V 扩展、VLEN、核拓扑、内核、编译器和 NPU SDK 上差异显著。任何单机结论都不应自动迁移到其他 riscv64 设备 [S01][S02][S03][S04]。
  5. 公开产品页会更新，项目状态与供货状态会变化；例如公告中的开发板计划不等同可持续供货。采购和量产决策前应重新核验实际 SKU、BSP、驱动和维护承诺 [S15]。
  6. 本文不替代模型安全评估、开源许可审查、数据合规、固件安全审计或硬件可靠性验证；这些应作为实际产品项目的独立门禁。

附录：研究方法

A. 证据采集规则

  1. 优先采用 Linux、编译器、模型/运行时上游项目，以及 SoC/板卡/OS 厂商的原始资料；不以聚合跑分、二手评测或社交媒体截图支持技术事实。
  2. 将“RV64”“RVV”“NPU/TPU”分开记录。任何关于 AI 加速的结论必须明确实际执行单元、模型格式和后端，而不能仅引用架构名称。
  3. 对模型可运行、TOPS、参数量和 token/s，保留原始来源条件；除非模型、量化、上下文、并发、温度、内存和方法可比，否则不进行跨设备排名。
  4. 对上游 RFC、产品计划和 OS 支持，明确其生命周期状态；采购、上线和量产前必须在目标 SKU、BSP、驱动和运行时版本上复核。
