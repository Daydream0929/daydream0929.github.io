摘要

  • RISC-V 64 启动链的每一级交接都由一组可以 grep 的寄存器与结构体约定承载：M→S 交接是 a0=hartid、a1=FDT、satp=0 与 mstatus.MPP=S；SPL→OpenSBI 是 struct fw_dynamic_info 的 magic/version/next_addr/next_mode/options/boot_hart 六字段；内核入口要求在 Documentation/arch/riscv/boot.rst 逐条写明。bringup 挂死绝大多数是某级字段写错，而不是「玄学」。 [S02][S06][S07]
  • OpenSBI master（v1.9 开发线）已把 PMP 配置重构为 hart protection 框架：冷启动在 sbi_init() 末尾经 sbi_hart_protection_configure() 落盘，root 域默认为「固件区 M+FW 权限 + 全内存 SU RWX」；域 dump 形如 Domain0 Region00 … M: (F,RWX) S/U: (RWX)，S 态越界首访即 trap 回 M 态并可在 mepc 定位。 [S02][S03]
  • Linux v7.3.0-rc6 的 head.S 中 relocate_enable_mmu 已回到 head.S 本体（非 mm/init.c），satp 经 trampoline 两次切换后才启用内核页表；a1=FDT 的现行要求不含旧版报告所称的「8 字节对齐」要求，真实硬约束是 a0=hartid、$satp=0、镜像置于 PMD 边界（rv64 为 2 MiB）。 [S06][S07]
  • SMP 从核的两条路径在 cpu_set_ops() 分流：探测到 SBI_EXT_HSM 才用 cpu_ops_sbi，否则回退 spin-table；后者要求所有 hart 各就各位自旋等 __cpu_spinwait_stack_pointer，是 QEMU virt 与真板行为差异的常见来源。 [S06][S15]
  • 排查顺序应先建立「串口最后一句 → 下一级第一个越界访问」的映射，再分别核对 PMP 区间、页表项与 init 候选链；JTAG 读 pmpcfg/pmpaddr、satp、mepc/mcause 能在不重启的情况下把故障钉死到单条指令。 [S02][S06][S23]

背景与现状

RISC-V 64 的启动链由四级交接串成：BootROM/ZSBL 复位后按介质装载 → SPL（片内 SRAM）→ OpenSBI（M 态）→ U-Boot proper（S 态）→ 内核 Image（S 态）→ 用户态 init。与 x86/ARM 的主要差别不在顺序，而在于每一级交接的载体都是可逐字核对的寄存器与内存结构：hartid/FDT 走 a0/a1，SPL 与 OpenSBI 之间以 struct fw_dynamic_info 传递入口与选项，内核入口条件在 boot.rst 中逐条写死。bringup 的工程本质因此是「把每一级交接的字段核对到字节」。本文版本锚点全部锁定到 commit：OpenSBI master 6ad246a1（v1.9 开发线）、Linux master 3857c2fe（v7.3.0-rc6）、U-Boot master ece349ad（2026.07 开发线），其余见参考来源台账。图 1 给出逐级交接的全景。

标准与上游实现现状

在规范层，M 态与 S 态的职责边界已由 RISC-V SBI Specification v3.0 与各 Profile 固化：S 态内核永不自管时钟与 IPI，一切经 ecall 走 SBI 扩展（TIME/IPI/RFENCE/HSM/SRST/SSE 等）；固件实现侧由 OpenSBI（master 线为 v1.9-dev）参考实现兜底，其 fw_dynamic_info 结构把「下一级入口地址/模式/FDT/选项/偏好 boot hart」序列化成可校验的交接块 [S01][S02]。平台层，Boot and Runtime Services（BRS）v1.0 于 2025-08-29 冻结，把「OS 期望固件提供什么」写成标准，配合 OS-A 平台规范与 RISC-V UEFI 集成指引，收敛出「BootROM → SPL/固件 → U-Boot/EDK2 → 内核」的主流形态 [S16]。

在实现层，上游三件套的行为可以逐文件核对：OpenSBI 的 firmware/fw_base.S 在 _start 后先处理 128 字节固件头（magic 0x4942534f）并选 boot hart，再由 lib/sbi/sbi_init.c 的 init_coldboot() 按固定顺序初始化十余个子系统，最后经 sbi_hsm_hart_start_finish() 调用 sbi_hart_switch_mode() 以 mret 交接；U-Boot 在 arch/riscv/cpu/start.S 里区分 SPL 与 proper 两段入口，proper 段经 relocate_code 自搬移后进入 board_init_r 启动 bootstd 扫描；Linux 内核入口在 arch/riscv/kernel/head.S，_start_kernel 清 BSS、setup_vm 建恒等映射后 relocate_enable_mmu 写 CSR_SATP（Sv39/Sv48/Sv57 由 satp_mode 探测），随后 tail start_kernel 进入 init/main.c [S02][S04][S06]。

在接口层，所有交接的要求都在上游文档中可查：内核入口要求 $a0=hartid、$a1=FDT 物理地址、$satp=0（MMU 关闭），镜像须置于 PMD 边界（rv64 为 2 MiB）；/memory 节点提供 memblock 的全部原料；镜像头以 magic "RISCV" 与 image_size 自描述，供引导器装载前校验 [S06][S07][S08]。值得强调的是，现行 boot.rst 并未规定 a1 的 8 字节对齐——这一在旧版报告与二手文章间流传的说法没有一手依据，真正需要对齐的是内核对 DTB 的 fixmap 映射（FIX_FDT % (PMD_SIZE / PAGE_SIZE) 的编译期断言）。这类「流传甚广但无出处」的细节正是本文以 commit 级源码逐条校正的对象 [S06]。

启动软件的成熟度也可以从版本节奏读出：OpenSBI 从 v1.7（2025-06）的 SBI v3.0 合规、v1.8（2025-12）的动态堆与国内平台（SpacemiT K1、ESWIN EIC7700）接纳，到 v1.9 引入 Zkr 栈保护与 Smrnmi NMI；Linux 侧 RISC-V 已长期处于「入口稳定、平台支持持续合入」状态（本轮 master 甚至移除了长期缺乏维护的 XIP 分支）；U-Boot 的 bootstd 框架把「找设备 → 找方法 → 引导」从板级代码收敛为通用框架 [S02][S06][S04]。三者的共同趋势是：板级私有差异被压缩到设备树与少数平台钩子（如 spl_board_init()）中，其余全部上游公共路径可复用——这正是「按接口排查」能够跨平台成立的前提 [S04][S05][S16]。整体层级与失败面见图 1。

国内平台与生态现状

国内平台近两年的 bringup 主线是「固件上游化 + 发行版就绪」。VisionFive 2（JH7110）与 HiFive Unmatched 是完整上游化的参照平台：SPL → OpenSBI → U-Boot proper → 内核四段链条与镜像分区均有公开文档可复现；SpacemiT K1 自 OpenSBI v1.8 起获得上游支持，社区同时维护 UEFI 替代方案；Pioneer（SG2042）官方安装镜像走 EDK2 UEFI + GRUB2 路径，把服务器类平台的启动固化到标准固件栈；Lichee Pi 4A（TH1520）沿厂商 DDR blob + fastboot 写入 u-boot-with-spl.bin 的路径，是「SPL 前阶段不可审计」的典型样本 [S17][S18][S19][S20]。

发行版侧的门槛已明显降低：openEuler 24.03 LTS 同时为 Pioneer 与 Lichee Pi 4A 提供安装文档，使 bringup 完成后的系统验证可以直接走发行版安装流程而不必自建根文件系统；RTOS 侧，Zephyr 与 NuttX 在 RISC-V 上游支持（含 S 态运行路径与 SBI 依赖说明）为国内物联网与车规场景提供可选底座，RT-Thread 维护 libcpu/risc-v 移植层 [S12][S13][S14][S19]。

差距集中在三点：其一，部分国产 SoC 的 DDR 训练仍以 blob 交付，SPL 之前的失败只能依赖厂商工具；其二，同一生态内 EDK2 UEFI 与 U-Boot extlinux 两条固件路线并存，跨平台复用的排查方法有限，BRS v1.0 与 OS-A 规范的落地程度成为分水岭；其三，Android 在 RISC-V 的官方支持仍缺位（GKI 移除后仅存社区追踪），国内 Android on RISC-V 的 bringup 工程多依赖厂商闭源 patch。机会在于：上游对国内平台的持续接纳（K1 等）、RVA23 基线发行版的成熟，以及 HIL 自动化验证工具链的成形，使「把板卡纳入逐级验证矩阵」第一次具备完整条件 [S12][S16][S19]。

技术详解：从加电到 init

本章按启动顺序逐个机制吃透：每一节都给出接口/实现依据、步骤级调用链、失效边界与验证条件，全部锚点以 commit 锁定的上游源码为准（OpenSBI 6ad246a1、Linux 3857c2fe；U-Boot 与 Android/RTOS 的版本见台账），可逐条 grep 复核。

OpenSBI：fw_base.S 冷启动、域与 PMP 落盘

接口与实现依据。OpenSBI 对外只有两个接口面：对上，S 态仅能经 ecall 访问 SBI（EID 在 a7、FID 在 a6，返回值在 a0/a1，语义由 SBI v3.0 规范锁定）；对下，上一级经 a0/a1/a2 交付「hartid / FDT / 选项块」。fw_dynamic 形态中 a2 指向 struct fw_dynamic_info（include/sbi/fw_dynamic.h），六字段依次为 magic、version、next_addr、next_mode、options、boot_hart（偏移 0–5，单位为一个长字），magic 固定 0x4942534f，version 上限为 2；firmware/fw_dynamic.S 中的 fw_boot_hart() 先校验 magic/version，不符即跳 _start_hang——这是「SPL 与 OpenSBI 版本对不上就黑屏」的第一现场。源码锚点：firmware/fw_base.S、firmware/fw_dynamic.S、lib/sbi/sbi_init.c、lib/sbi/sbi_hsm.c。

冷启动序列（行号按 master 6ad246a1）。_start（L58）→ 128 字节固件头（FW_HEADER_*）→ _start_real（L111）→ fw_boot_hart() 择主（L145）：返回 -1 时全体 hart 以 amoswap.w 对 _boot_lottery 原子抽签，未中者进入 _wait_for_boot_hart（L401）轮询 _boot_status → boot hart 执行 .rela.dyn GOT 重定位（L169-189，以 FW_TEXT_START 为链接基址、_fw_start 为装载基址，凡「运行地址 ≠ 链接地址」的装载方式都靠它修正 GOT 项）→ _reset_regs/清 BSS/CLEAR_MDT（L194-214）→ 临时栈 → fw_save_info()（L223）→ fw_platform_init()（L237）→ _scratch_init（L273-348）→ 置 _boot_status（L393）→ _start_warm（L411）→ csrw CSR_MSCRATCH，tp 后 call sbi_init()（L477-479）。进入 C 世界的顺序并非任意：init_coldboot()（lib/sbi/sbi_init.c L224）先 sbi_scratch_init() 与 sbi_heap_init()，再 sbi_domain_init()（L241，此时按平台是否单固件区生成 1–2 个 M 态 region 与一个全内存 SU region），随后 sbi_hsm_init(scratch, true) 把本 hart 置 START_PENDING、其余置 STOPPED；hart/trap/timer/platform_early/pmu/dbtr 依次初始化后打印横幅，再经 irqchip/ipi/tlb/fwft/mpxy/domain_finalize/platform_final/sse/ecall_init 补齐运行时设施；最后 sbi_hart_protection_configure()（L436）把域 region 写入 PMP 条目，并以 sbi_hsm_hart_start_finish()（L446）走 sbi_hart_switch_mode() 的 mret 交付 S 态。热启动侧对称：init_warm_startup()（L448）复用同一批子系统（全部走非 boot 路径），同样经 protection_configure 与 start_finish 进入 S 态。

域与 PMP 的落盘。root 域 region 采用「固件区在前、全内存在后」的固定序——这正是 PMP 隐式优先级（低编号先匹配）的标准用法：前面的固件区对 SU 关闭且带 FW 标志，后面的全内存区才给 S 态 SU RWX 权限，因此「S 态可读写自己、不可碰固件」由一条条目序而非两条规则保证。sbi_domain_dump() 的输出格式为 Domain%d Region%02d … 后跟 M: (F,RWX) 与 S/U: (RWX) 两串动态拼接的权限字母，排查时可直接逐字对照。自 v1.9 开发线起，PMP 不再由 sbi_init() 直呼 sbi_hart_pmp_configure()：sbi_hart_pmp_init()（lib/sbi/sbi_hart_pmp.c）按 SMEPMP 扩展存在与否注册 epmp_protection（rating 200）或 pmp_protection（rating 100），由 sbi_hart_protection_configure()（lib/sbi/sbi_hart_protection.c）统一落盘。配置失败时唯一会打印的原始错误串在 oldpmp 与 smepmp_set 两条路径内：Can not configure pmp for domain %s because memory region address 0x%lx or size 0x%lx is not in range.——出现它意味着域 region 的地址或 size 超出 PMP 粒度/可编码范围（NAPOT 最小 8 字节、地址 >>2 编码），此后 S 态的首个越界访问会立即 trap 回 M 态，现场留在 mepc/mcause。

运行时服务与从核启动。S 态 ecall 进入 sbi_trap_handler()（lib/sbi/sbi_trap.c）后按 mcause 分流：中断走 AIA/非 AIA 两条路径，异常中的 CAUSE_SUPERVISOR_ECALL 交 sbi_ecall_handler()（lib/sbi/sbi_ecall.c），按 a7 查扩展、a6 查函数、结果写回 a0（非 0.1 规范同时写 a1），并把 mepc += 4 继续执行。扩展探测走 base 扩展的 probe（EID 0x10、FID 0x3）：未注册返回 0、注册且无自定义 probe 返回 1——内核 cpu_set_ops() 正是用它判定 HSM 是否可用。从核启动全链路：S 态准备好 saddr/arg1 后 ecall HSM hart_start → sbi_hsm_hart_start() 以 atomic_cmpxchg 把目标 hart 的 STOPPED 改为 START_PENDING 并 sbi_ipi_raw_send 唤醒它 → 目标 hart 在 sbi_hsm_hart_wait()（MIE 置 MSIE|MEIE）等待票据 → sbi_hsm_hart_start_finish() 释放票据后 sbi_hart_switch_mode() 以同一入口要求进入 S 态。注意 sbi_hart_switch_mode() 只设置 a0/a1，a2 不在其职责内——把 sbi_init 之前的 a0-a4 归档成「下一级要从哪里取什么」正是 fw_save_info() 与 _scratch_init 的分工。

失效边界与验证条件。三类可 grep 的现场：其一，PMP/域配置失败（错误串见上）或域未覆盖某 MMIO，症状是「S 态访问该地址即静默挂死或 trap 进 M 态且无任何日志」；其二，options 置位 SBI_SCRATCH_NO_BOOT_PRINTS（bit0）后横幅消失，容易被误判为「固件根本没跑」，而该位既可在编译期 FW_OPTIONS=0x1 固定，也可由 SPL 在 fw_dynamic_info 的 options 字段打开；其三，next_addr/next_mode 写错时 mret 后第一条 S 态指令就取指异常，串口停在上一条横幅。验证路径：串口 grep Platform Name、Boot HART MP Count/Firmware Base 与 Domain0 Region 开头的行；JTAG/GDB attach 后读 mepc/mcause/mstatus（MPP 位）判断 trap 来自哪一级、停在哪条指令；对照 docs/domain_support.md 的域语义核对 region 覆盖。

成本与权衡。boot prints 提供冷启动时间参照与开机自检输出，代价是每次上电的串口输出与少量时间；子域（domain）能把 UART/CLINT 等 MMIO 收窄给特定 hart 组，换来更强的隔离但增加 bringup 期配置面；fw_dynamic 比 fw_jump 多一次结构体校验与间接取址，换来 SPL 可传 options 与 boot hart 偏好的灵活性——量产固件常关闭 boot prints 并冻结为 fw_jump 形态，而 bringup 期应反过来打开全部可观测项。图 2 把冷启动与热启动两条路径并列画出，读图时先沿红色虚线框走完 boot hart 的全部九步，再对照蓝色框确认从核始终以 sbi_hsm_hart_wait() 等待票据。

U-Boot：SPL 与 proper 的两次接力 —— FIT 装载与 boot_jump_linux 交接

接口与实现依据（本小节按 U-Boot master ece349ad（2026.07 开发线）源码逐字核实）。U-Boot 在 RISC-V 上分两段执行，两段共用 arch/riscv/cpu/start.S 的 _start，由 XPL/proper 编译期分支分体。寄存器的开局动作决定了整个交接的正确性：_start 先把上级传来的 a0（hartid）与 a1（FDT）搬进 tp 与 s1（mv tp, a0；mv s1, a1），再 mv gp, zero 给 gd 指针一个已知值以防早期 trap；真正的 gd 由 board_init_f_init_reserve()（定义在 common/init/board_init.c，:151 调 arch_setup_gd()）经 set_gd() 写入 gp（arch/riscv/include/asm/global_data.h:67 声明 register gd_t *gd asm ("gp")）。两条关键信息随即转入全局数据：SREG s1, GD_FIRMWARE_FDT_ADDR(gp) 与 SREG tp, GD_BOOT_HART(gp)（start.S:175；boot_hart 在本轮核实文件集内唯一写入点）——U-Boot 不是「保留 a0/a1 到跳内核」，而是把 hartid/FDT 持久化为 gd->arch.boot_hart 与 gd->arch.firmware_fdt_addr，跳转前再按要求放回寄存器。寄存器视角可以一句话概括：a0/a1 是外部输入、tp/s1 是内部暂存、gp 是全局数据通道，三组寄存器各司其职；任何一级若把 hartid 或 FDT 放错位置，下一级都会以「FDT 解析失败」或「从核唤不醒」的形式把错误还回来。

SPL 装载链与交棒。SPL 侧顺序为 _start → board_init_f_alloc_reserve（start.S:134，从内存顶部划出 gd 与各 hart 栈）→ board_init_f_init_reserve（:171）→ board_init_f（:218，a0 清零为 boot_flags）→ spl_relocate_stack_gd → j board_init_r（:271，SPL 完全跳过 relocate_code）→ board_init_r（common/spl/spl.c:672）→ spl_board_init()（:738，仅 CONFIG_BOARD_INIT 生效；QEMU 两个 defconfig 均未开启）→ board_boot_order（:755）→ boot_from_devices（:626）→ 媒介装载（典型 spl_mmc_load，common/spl/spl_mmc.c:369→mmc_load_image_raw_sector）→ 统一入口 spl_load()（include/spl_load.h，检出 FDT_MAGIC 后分派 spl_load_simple_fit()，common/spl/spl_fit.c）。FIT 搜索顺序逐字为 firmware →（SPL_OS_BOOT 时）kernel → loadables；entry_point 由 fit_image_get_entry() 从 FIT 属性读得，缺失或为 0 时回落 load_addr。跳转由 RISC-V 覆盖版 jump_to_image() 执行（arch/riscv/lib/spl.c:39-61；旧 jump_to_image_no_args 在本 master 已删除），末段逐字为 image_entry(gd->arch.boot_hart, fdt_blob)——把 a0=hartid、a1=FDT 的 SBI 入口要求原样复述给 OpenSBI；SMP 配置下先 smp_call_function() 唤醒从核再统一跳转。串口最早锚点是 Trying to boot from MMC1（spl.c:646 的统一 printf，%s 来自 spl_loader_name()）与 SPL 横幅（preloader_console_init()，spl.c:870）。

Linux：head.S 到 PID 1 —— 两级页表、satp 切换与 init 候选链

接口与实现依据。内核入口要求在 Documentation/arch/riscv/boot.rst 逐条给出：$a0 为当前核 hartid、$a1 为设备树物理地址、$satp = 0（MMU 若存在必须关闭）；镜像需置于 PMD 边界（rv64 为 2 MiB）。需要纠正一个流传很广的表述：现行 boot.rst 并未要求 a1 满足 8 字节对齐；与 DTB 相关的真实硬约束是内核对 DTB 的 fixmap 映射必须 PMD 对齐（mm/init.c 中以 BUILD_BUG_ON(FIX_FDT % (PMD_SIZE / PAGE_SIZE)) 断言），以及镜像本身的 PMD 边界放置。镜像头（boot-image-header.rst）以 magic "RISCV" 与 image_size 等字段自描述，供 U-Boot 的 booti_setup() 装载前校验。Linux 源码锚点：arch/riscv/kernel/head.S、arch/riscv/mm/init.c、init/main.c（版本 master 3857c2fe，即 v7.3.0-rc6）。

入口序列。_start（head.S L21）只做镜像头与一条 j _start_kernel；_start_kernel（L210）先 csrw CSR_IE, zero 关中断、S 模式置 SCOUNTEREN、SPINWAIT 构建下以 hart_lottery 抽签选 boot hart（越界 hart 直接 park）、清 BSS 并记录 boot_cpu_hartid；随后 call setup_vm（入参 a0=DTB 物理地址或内置 DTB）、la a0, early_pg_dir; call relocate_enable_mmu 完成 satp 两次切换，再建立 C 环境（tp=init_task、sp=init_thread_union+THREAD_SIZE−PT_SIZE_ON_STACK）、call soc_early_init，最后 tail start_kernel 进入 init/main.c。satp 的两次写是刻意的：先把 trampoline_pg_dir 装入 satp 并 sfence.vma，让 PC 附近的小范围恒等映射生效，再切换为内核 PGD——MMU 关闭状态下不能一步跳到远端页表，这正是 relocate_enable_mmu 被放回 head.S 本体、以物理地址连续执行的原因。页表模式由 satp_mode 决定（默认 Sv57，boot 时经 set_satp_mode() 探测降级：写 early_pg_dir 后 csr_swap(CSR_SATP, 0) 回读校验，硬件不接受则逐级降档），这是「内核在只支持 Sv39 的核上运行」不挂死的机制。paging_init() 的三步（setup_bootmem → setup_vm_final → memblock_allow_resize）把恒等映射升级为正式 linear mapping（swapper_pg_dir），DTB 则全程走 fixmap（fix_fdt_va），保证在 setup_vm 与 setup_vm_final 两套映射下都可访问——boot.rst 第 142–148 行对此有专门说明。

成本与权衡。earlycon 换取最早可观测性，代价是依赖 UART 时钟在早期已就绪；initramfs 内嵌换取根设备无关性，代价是镜像体积与解包内存；spin-table 路径实现简单，代价是需 bootloader 侧协议配合且无法热插拔，SBI HSM 反向取舍；print_vm_layout/memblock=debug 提升可观测性但属 DEBUG 级开销量级，量产内核应默认关闭。图 4 将 Linux 主链与 Android/RTOS 分岔画在同一张图上，读图时先确认 relocate_enable_mmu 位于页表与 C 世界之间，再看 kernel_init 的三个去向。

启动参数与数据流细节。启动参数走 bootconfig 而非 /proc/cmdline：内核文档明确 /proc/bootconfig 是 "a user-space interface of the boot config"，载体是追加在 initrd 尾部的 [initrd][bootconfig][padding][size(le32)][checksum(le32)][#BOOTCONFIG\n] 结构；init 侧对两者都做 chmod 0440 防泄露，FirstStageConsole() 与 GetBootMode() 都从 bootconfig 键读取。ramdisk 切换由 ForceNormalBoot 触发：mkdir("/first_stage_ramdisk",0755) → PrepareSwitchRoot() 预置 snapuserd → 自 bind mount 后 SwitchRoot("/first_stage_ramdisk")（first_stage_init.cpp:515-522），使 prepare_namespace() 的 pivot 语义在 Android 分区布局下同样成立。三个阶段各自的时间戳在二阶段汇总：kEnvFirstStageStartedAt（first_stage_init.cpp:556 设置）与 kEnvSelinuxStartedAt（selinux.cpp:800 设置）由 RecordStageBoottimes()（init.cpp:855-868）消费，这是官方提供的「分段耗时」第一手数据。属性空间一旦在二阶段就位，rc 中的 on 触发器与 service 停机超时都可以用 getprop/setprop 在线复现，这把用户态问题从「看日志猜」降级成「改属性试」。此外，一阶段在 InitKernelLogging(argv) 之前先 SetStdioToDevNull(argv)，这正是「一阶段早期日志会短暂丢失」的根源——在 /dev/kmsg 节点建立并完成日志初始化之前，内核环缓冲还接不上用户态的写入口，排查阶段边界时对首个字符出现的时刻要有预期。

失效边界与验证条件。第一手的「段界」就是三行日志：内核→用户态看到 init first stage started!，一阶段→SELinux 看到 restorecon 类 FATAL，init second stage started! 之后才轮到 rc 解析与 service 启动失败；AVB 拒绝表现为 avb_slot_verify failed, result: 或红色 boot 界面；分区缺失表现为 Failed to mount required partitions early ...（FATAL）或 recovery 分支的 First stage mount skipped (recovery mode)。验证路径：串口/earlycon 抓三行日志定段；一阶段问题用 /proc/bootconfig 与 /proc/cmdline 内容对照；AVB 用 avbtool verify_image 离线复核 vbmeta 链；二阶段用 logcat -b all 的 early buffer 追 service 启动序。成本与权衡：三段式（一阶段→SELinux→二阶段）让策略与 property 在最小 context 下先就位，可审计性强；代价是 bringup 问题分布在内核、init 一阶段、init 二阶段与 rc/genfstab 四个平面，且每段都以 execv 重进同一二进制，进程内不留「上一段的调用栈」——排查必须依赖日志分段而非栈回溯。另外两个可直接 grep 的辅助串：一阶段挂载能力未就绪时为 FirstStageMount not available；SELinux 阶段 restorecon 失败时逐字报 restorecon failed of /system/bin/init failed。把四个平面与三行日志对齐后，Android bringup 的排障路径与发行版 Linux 本质相同：分区与策略在前、服务与界面在后，只是分段边界更清晰。

RTOS：Zephyr/FreeRTOS/NuttX 如何收敛到同一入口

接口与实现依据（三家快照：Zephyr e989541e [S12]、FreeRTOS-Kernel 8be86d4a [S13]、NuttX 321105a3 [S14]，均 main 线）。RTOS 与 Linux 共享同一入口要求（a0=hartid、a1=FDT、satp=0，M 态职责外包给 OpenSBI/fw_jump），但终点不是 exec 用户态而是调度器。Zephyr：arch/riscv/core/reset.S 的复位符号是 __reset → __initialize（不是 __start），CONFIG_INCLUDE_RESET_VECTOR 时先 call __initialize；非外部 SBI 配置下从 csrr a0, mhartid 起步，与 CONFIG_RV_BOOT_HART 相等的一核走 boot_first_core、其余进 boot_secondary_core，末尾 call z_prep_c 进 C 域；z_prep_c()（arch/riscv/core/prep_c.c）清 BSS、拷 RW 数据后进 z_cstart()（kernel/init.c:535）：z_sys_init_run_level(INIT_LEVEL_EARLY) → arch_kernel_init()（arch/riscv/include/kernel_arch_func.h:46，置 TLS tp=0、sscratch/mscratch 指 _kernel.cpus[0]、z_riscv_pmp_init()）→ z_dummy_thread_init() → soc/board 各级 early hook → prepare_multithreading()（L438，建 "main" 线程并 z_init_cpu(0)）→ switch_to_main_thread()（L475）落主线程；bg_thread_main（L266）再跑 POST_KERNEL/APPLICATION/SMP 三级 init 后调用 (void)main(argc, argv)——应用 main() 实际是内核主线程。FreeRTOS：xPortStartScheduler()（portable/GCC/RISC-V/port.c:159）先 vPortSetupTimerInterrupt()（L129，用 csrr mhartid 选 configMTIMECMP_BASE_ADDRESS + hartid*8）再 csrs mie, 0x880 开 MEIE/MTIE，随后 xPortStartFirstTask()（portASM.S:254）从 pxCurrentTCB 取栈并恢复 mstatus（MIE 置位）——首个任务不是 ARM 惯例的 SVC 起跳，而是把任务上下文里保存的 PC 当返回地址、以 ret 落入，源码注释逐字为 "exception return address is used as the function return address"；异常统一走 freertos_risc_v_trap_handler（:353），mtimer 中断分支 xTaskIncrementTick() → vTaskSwitchContext()，li t0, 11 /* 11 == environment call */ 也复用同一上下文切换点。NuttX：__start（arch/risc-v/src/qemu-rv/qemu_rv_head.S:47，CONFIG_NUTTSBI 时为 __start_s）保留 a1=DTB、以 riscv_set_inital_sp 给每核栈、la t0, __trap_vec; csrw CSR_TVEC, t0 装向量表后 jal x1, qemu_rv_start（:80）→ qemu_rv_start.c 清 BSS、fdt_register(dtb)、riscv_earlyserialinit() → nx_start()（sched/init/nx_start.c:503）按状态机推进：OSINIT_BOOT → OSINIT_TASKLISTS → OSINIT_HARDWARE → OSINIT_OSREADY → OSINIT_IDLELOOP（每步写 sched_trace_mark），up_initialize()（:677）与 drivers_initialize()（:681）就位后 nx_bringup()（:748）创建初始任务，CPU0 最后进 for (;;) up_idle();。三家共同常量：异常向量在复位早期即装（NuttX 的 __trap_vec 位于 riscv_vectors.S，.balign 64），SMP 从核经 SBI HSM 或平台 spin 协议进入 secondary 路径（NuttX riscv_cpu_boot()、Zephyr boot_secondary_core）。Zephyr main 的 reset.S 已内置 S-mode 直通形态：外部 SBI 配置下先从 M 态接管、设好 mtvec 与委托后再 mret 进 S 态——同一份复位代码同时服务「内置 M 态」与「外包 OpenSBI」两种形态，是国内 SoC 移植时判断固件依赖的第一处开关。三家移植层还都把「最早期异常」当成一等公民：Zephyr 在 arch_kernel_init 初始化 per-CPU scratch 与 PMP、FreeRTOS 对 ISR 栈做对齐断言与填充、NuttX 把向量表 64 字节对齐后立即装载；共同动机是——调试通道（串口）就绪之前，任何异常若没有合法 trap 向量都会变成静默挂死，而静默挂死恰是 RTOS bringup 最难反推的故障类别，这也让「是否引 SBI」成为移植期第一个要拍板的架构决策。

失效边界与验证条件。共同故障模式是最早 trap 向量未就位时的静默挂死（NuttX 在 csrw CSR_TVEC 之前若发生异常，只能靠 JTAG）；Zephyr 的 CONFIG_RV_BOOT_HART 配错会让所有核进 secondary 等不到 boot hart；FreeRTOS 的 configMTIMECMP_BASE_ADDRESS 与真实 CLINT 不符则 tick 中断永不触发（任务只跑一次即停）；NuttX 的 CONFIG_SMP_NCPUS 小于实际 hart 数时，多余 hart 在 wfi 静默等待（源码注释即「多余 hart: 关中断 wfi」）。对量产场景额外提示：三家都提供静默启动选项，关闭串口横幅后「无输出」不再等价于「未启动」，验收时应以 JTAG 或预置内存标志为准。验证条件：QEMU virt 上以 -bios fw_jump.bin 直接加载 RTOS 镜像即可在串口看到各自启动标记（NuttX 的 showprogress('A') 进度字母最直观）；-s -S 配合 GDB 在 __trap_vec、z_prep_c、qemu_rv_start 下断点确认执行流；核对每核栈基址（如 NuttX QEMU_RV_IDLESTACK_BASE）不与内核映像重叠。

成本与权衡。RTOS 启动路径短、确定性好、无 MMU 依赖，代价是缺乏内存隔离与工具生态，可观测性远弱于 Linux/Android（很多失败表现为静默挂死），因此更依赖 JTAG/仿真器；三家都选择「只跑 S/U 态、M 态全外包」以换取与固件生态的兼容，代价是在不提供 SBI 的裸机核上需自带 M 态启动桩。图 4 右侧把 Android 与 RTOS 画成与 Linux 主链并列的对照：Android 在 PID 1 处换入口为两阶段 init，RTOS 则根本没有 exec 路径、初始化完成即进调度器与 main()。工程上更稳妥的做法是把三者各自的启动标记与断点写成板卡验收脚本，让「静默挂死」在验收阶段就被拦住，而不是流入现场。

总结与展望

本文把从加电到 init 的整条链路压缩成三级可核对对象：每级交接的字段（a0/a1、fw_dynamic_info、/chosen）、承载它的源码落点（fw_base.S、start.S、head.S、init/main.c）与失败时的逐字错误串。三者对齐后，bringup 从「点亮实验」变成可交接的检查流程。以下三条主线决定了这套流程未来两年的演化方向。

主线一：交接接口继续「进规范」。BRS v1.0 于 2025-08-29 冻结后，「OS 期望固件提供什么」（含 fw_dynamic_info 语义与 HSM 使用时机）第一次有了可引用的规范性文本，并与 OS-A 平台规范、RISC-V UEFI 集成指引组成完整接口面；OpenSBI v1.9 开发线把 Zkr 栈保护与 Smrnmi NMI 纳入冷启动可选项；Linux 侧本轮 master 甚至删除了长期缺乏维护的 XIP 分支，收窄入口要求的历史兼容面 [S02][S06][S16][S21]。情景判断：当 RVA23 基线发行版成为国内主流，「固件接口核对」会像 PC 侧 UEFI 一样成为 bringup 交付物的一部分——直接含义是把 boot.rst 与 fw_dynamic_info 字段核对写进 CI 门禁，而不是等板子点亮后手工排除。

主线二：引导框架收敛到「配置化」。U-Boot 的 bootstd/bootflow 把「找设备 → 找方法 → 引导」从板级代码收进通用框架（bootmeth 可插拔），distro_bootcmd 宏以兼容路径并存；SPL 的 FIT 打包从「手工 mkimage」进化为发行版流水线的一环（.its 描述 + 签名 + 校验）[S04][S05]。情景判断：bootflow 标准化让「同一条排查方法跨板复用」第一次成立；但本轮快照里 QEMU 等默认配置仍走 distro_bootcmd——双路径共存期的代价是排查手册必须同时覆盖两套分析工具（bootflow scan -l 与 env 宏调试）。

主线三：国内平台从「移植」转向「归并」。VisionFive 2 与 SpacemiT K1 的固件链已进入上游并由 openEuler 等发行版直接支持，bringup 的重心从改 SPL/OpenSBI 变成写设备树与 board 钩子；尚未上游化的平台（DDR blob、私有存储驱动）仍是黑盒段 [S17][S18][S19][S20]。Android on RISC-V 在官方支持缺位下将维持「厂商 patch + 社区追踪」双轨形态 [S22]；RTOS 的增量场景在车规与工业（含 AUTOSAR 适配与双核异构），其确定性优势只有在 JTAG 可达时才兑现 [S12][S13][S14]。完整的行动要点见附录 B 的检查与验收清单。

附录 C：研究方法与局限

取证流程分四步：其一，锁定版本锚点（OpenSBI master、Linux master、U-Boot master、AOSP system/core main、Zephyr/FreeRTOS/NuttX main），以 GitHub API 取得 HEAD commit 与目标文件的最后修改 sha；其二，抓取源码与文档文本（CDN 镜像与 GitHub contents API，避开不稳定的 raw 通道），全部落在本地快照目录，行号以快照实测为准；其三，由独立核查代理分别完成 OpenSBI、U-Boot、Linux、Android/RTOS 四份材料清单，每条结论必须附「文件:行号 + 逐字片段」，无法给出逐字依据的推断一律进入局限清单（见下文）；其四，正文写作以「接口与实现依据 → 失效边界 → 验证条件 → 成本与权衡」四问逐节过关，所有错误串与结构体字段保持逐字，包括 No working init found. Try passing init= option to kernel. 的双空格与 RSC\x05 这类易错细节。

本文为版本快照式调研，以下限制不改变总体结论，但影响细节复核时的预期。其一，U-Boot 结论基于 2026-10-10 的 master 快照 ece349ad（2026.07 开发线），且经 CDN 镜像抓取——已用 GitHub tree/commits API 交叉验证路径与修改时间，但未逐文件比对 blob sha，镜像缓存滞后于 GitHub HEAD 的风险不能完全排除 [S04]。其二，Android AVB 的行号取自社区镜像（platform_external_avb 的指定上游镜像缺 main 分支内容），与 AOSP 主线可能存在行号差异；init 侧材料（a3b721a3）取自 AOSP 镜像 main [S09][S11]。其三，OpenSBI 域 dump 的字母拼接逻辑由 sbi_domain_dump() 代码推得，未在真实硬件上运行核对；AIA 相关链路在本轮未做全量验证 [S02][S03]。其四，Zephyr 的 mtvec/stvec 最终写入点未在已查文件集内定位（soc_interrupt_init() 为疑似安装点但未验证）；「向量表拷贝」的常见说法在本轮快照中不成立 [S12]。其五，「唯一写入点」类结论（U-Boot boot_hart、OpenSBI boot 状态变量）基于已抓取的文件集而非全仓库穷举。其六，「QEMU 默认走 distro_bootcmd」只对 qemu-riscv64_defconfig 成立，其他板卡 defconfig 需单独判定 [S05]。其七，FreeRTOS 仅审 GCC/RISC-V 主路径的 trap handler 节选，芯片扩展宏未逐行展开；NuttX 仅核对 qemu-rv 芯片路径 [S13][S14]。最后，全部材料来自公开文本抓取，未执行任何构建、运行或仓库脚本；外部资料文字一律按研究数据处理。
