# Document Skill

## 适用范围

本技能用于 Markdown 技术文档的编写、审阅、校验与发布。规范覆盖两类报告：`技术调研报告`（源码级深度，见下节）与 `调研报告`（通用调研，轻量结构，见「调研报告（通用调研）」节）。规范只约束**新建或明确升级为对应类型**的文档；不得因为本规范而默认重写、拒绝发布或要求补齐既有报告。只有执行 `publish.py --validate` 时，才校验元数据中声明 `| 文档类型 | 技术调研报告 |` 或 `| 文档类型 | 调研报告 |` 的文件；校验器识别到旧版结构时按冻结处理，仅执行通用检查，不因结构与语言新规被动阻断。

## 技术调研报告：强制结构

新建技术调研报告的第一处非空行必须为一级标题。标题只写主题与范围，不写“源码级追踪”“深度解析”“全解析”等方法词或营销词。一级标题后先放元数据表；表中必须包含：`文档类型`、`版本`、`状态`、`密级`、`作者`、`生成日期`、`研究截点`、`目标读者`、`调研问题`、`覆盖范围`、`排除范围`。其中 `文档类型` 的值为 `技术调研报告`。

正文二级标题按固定顺序组织：

1. `摘要`
2. `背景与现状`
3. `技术详解`（可加副题，如 `技术详解：从加电到 init`）
4. （可选）`故障定位速查`
5. `总结与展望`
6. `参考来源`
7. `附录 A：主要结论与依据对照`
8. `附录 B：检查与验收清单`
9. `附录 C：研究方法与局限`
10. （可选）`附录 D：术语与缩略语`

**正文只承载技术内容**：讨论对象、机制、数据、结论与判断。过程性材料一律进附录——“主要结论与依据对照”“检查与验收清单”“研究方法与局限”（含修订记录）、术语表都不得留在正文。正文不出现任何证据标记（如 `【C】`、`【S】`）或“证据等级”式表述。

两个档位唯一差异在 `背景与现状` 是否设“国内”三级小节，其余结构完全相同：

- **档位 A `technical-research`（含国内小节）**：主题存在真实的国内外对照信息量时使用——国产 SoC、国内生态、厂商与平台落地等。`背景与现状` 必须含一个标题以“国内”开头的三级小节。
- **档位 B `technical-research-general`（通用）**：纯技术、上游、全球性主题；不设国内小节。确有两三处国内信息时并入相关段落即可，不单列标题。

选择方法：自问“删掉国内小节后，报告会损失实质信息吗？”会 → 档位 A；不会 → 档位 B。拿不准时优先 B。

图：至少三幅本地图片，分别覆盖总体结构、机制/流程与排障/对照；Markdown 引用 PNG（工作区预览器不渲染 SVG），同名 SVG 保留作矢量源供 HTML 发布内嵌。每张图以 `图 N：` 开头的图注写明来源与 `[Snn]`，正文必须以“见图 N”引用并给 2–4 句读图要点，不把图丢给读者自己猜。表格合计 ≥4 个：元数据表、附录 A 对照表、附录 B 清单表，加上正文必要的数据/对照表。

## 调研报告（通用调研）

适用于非源码级的综合调研：开源社区/生态调研、技术选型对比、行业与现状扫描、学习与职业规划调研等。与技术调研报告的差异在正文组织——不要求机制拆解、调用链与源码锚点，改为“自由主题章节 + 结论与建议”；元数据、来源台账、语言规范、图注来源要求、附录 A/B/C 与发布流程与前者一致。

结构要求（校验器按元数据 `| 文档类型 | 调研报告 |` 自动选用，以下门槛由 validate_research_report.py 执行）：

1. 一级标题；随后元数据表（11 字段同技术调研报告，`文档类型` 值为 `调研报告`）。
2. 二级标题顺序：`摘要` → `背景与现状` → 主题章节（≥2 个，标题自定）→ 以“结论”或“总结”开头的收束章节 → `参考来源` → 附录 A/B/C（同固定标题，可再加附录 D）。
3. 质量门槛：摘要 3–5 个要点（每点 ≥40 汉字、带 `[Snn]`）；`背景与现状` ≥400 汉字且带来源；每个主题章节 ≥300 汉字且引用至少一个 `[Snn]`；收束章节 ≥300 汉字且带来源，其后不再出现正文小节；本地图片 ≥2 张（PNG 引用、同名 SVG 留作矢量源；图注含来源/数据口径与 `[Snn]`，正文以“见图 N”引用并给 2–4 句读图要点）；表格合计 ≥4 个；附录 A/B 含表格与 `[Snn]`，附录 C ≥260 汉字。
4. 来源与语言规则同技术调研报告。来源编号格式为 `[Snn]`；方括号内以“S+数字”开头的记号会被按编号尝试报错（如 `[S1]`），普通英文词形链接文本（如 `[SConstruct]`）不受影响。

## 语言与写作质量

默认读者是技术专家而非初学者：调研目的是把机制拆到可复述、可验证、可排障的粒度。深度由**可追溯的具体事实**定义，不由篇幅或名词密度定义。

- 用工程师直读的语言写作，不使用报告腔与 Meta 词汇：`契约`（写“约定/接口/要求”）、`证据`与`证据等级`（写“依据/来源/源码/实测”）、`TL;DR`（写“摘要”）、`可靠性标记`、`主张—证据`、`可证伪`都不出现在正文。来源用自然句式加编号交代，如“按 OpenSBI v1.9 源码”“SBI v3.0 规定……[S01]”，不写“证据等级 A”式注记。
- `摘要` 必须恰有 3–5 个要点；每个要点给出至少一个 `[Snn]`、至少 40 个汉字，能脱离正文独立成立，不带任何标记前缀。
- 在 `参考来源` 中维护来源台账，使用唯一的 `[S01]`、`[S02]` 等 ID；正文中每个 `[Snn]` 都必须能在台账中解析。关键结论优先采用一手、上游或权威规范/源码/实验数据；源码类来源写到具体文件（属主/仓库 + 路径 + 版本或 commit/tag），不只给仓库首页。
- `背景与现状` 超过 600 个汉字，包含至少 8 个可定位锚点（版本号、规范字段、函数/文件、寄存器或行内代码）；国内小节不少于 260 个汉字并引用来源。
- `技术详解` 是全篇核心，按源码级标准验收：全章超过 4000 个汉字、至少 3 个三级小节、至少 2 段围栏代码块（逐字源码片段、关键日志或可复制的命令记录）、至少 12 个源码锚点（函数名或文件路径）。每个小节至少 800 个汉字、引用至少 2 个不同来源，并同时满足：
  - **步骤序列**：给出可复述的调用链（≥3 个环节，`A() → B() → C()`）或编号步骤序列，写明谁在什么条件下按什么顺序做什么。
  - **锚点密度**：≥12 个可定位锚点（去重合计，含函数名、源码文件路径、寄存器/字段、行内代码），其中 ≥2 个必须是函数名或源码文件路径；≥2 处行内代码片段（错误串、寄存器名、命令或参数写成 `...`）。
  - **四项必答**：实现与接口依据、失效边界、验证条件、成本与权衡；失败模式必须给出可 grep 的错误串、日志或可观察症状，验证条件必须给出可复制执行的命令/观测方法。
- 深度的判据是“读者能否自行验证”：机制必须落到具体锚点（函数名、寄存器/字段、参数、日志字符串、命令、文件路径、版本号）。只复述文档结论、没有函数名/文件/错误串的机制段落按未完成处理；概念名词密度不等于深度。
- `故障定位速查`（可选）不少于 260 个汉字，`总结与展望` 不少于 400 个汉字，二者都要有来源支撑；`附录 C` 记录检索方法与研究限制，不少于 260 个汉字。
- 完成前清除 `TODO`、`TBD`、`FIXME`、`待补充` 等未决标记。区分事实、推断、情景与建议，避免把预测写成事实。

## 发布到个人网站（实时）

站点仓库 `Daydream0929/daydream0929.github.io`（Jekyll + GitHub Pages）是全部报告的线上归档，报告生成后实时上传：

- 报告以自包含 HTML（CSS/SVG 已内嵌）存放于站点仓库 `reports/`，元数据登记在 `_data/reports.yml`，索引页 `reports/index.html`（Jekyll 页面）会自动列出全部报告。
- 站点仓库 `skills/document/` 保存本 skill 的副本，不参与站点构建（`_config.yml` 已排除 `skills`）。
- 每次生成报告后必须执行发布（用户另有说明时才跳过）：

```bash
python3 skills/document/scripts/publish_site.py reports/<report>.html \
  --summary "一句话摘要（用于索引页）" --tags RISC-V,Linux
```

脚本行为：拷贝 HTML → 合并 `_data/reports.yml`（按 id 更新，未提供的字段保留旧值）→ 提交 → 推送；推送触发 GitHub Actions，约 1 分钟后可访问 `https://daydream0929.github.io/reports/<report>.html`。批量发布用 `--manifest <yml>`（条目字段：`file`/`title`/`summary`/`date`/`tags`）。站点仓库路径默认 `~/github/daydream0929.github.io`，可用环境变量 `TECH_REPORT_SITE` 覆盖；`--no-push` 仅提交不推送，`--dry-run` 仅预览。

## 工作流

1. 先界定调研问题、时间截点、覆盖与排除范围；选择档位 A 或 B；建立来源台账。全流程以一手、上游、权威材料为准绳，写不出可定位来源的机制不进正文。
2. 优先收集原始论文、标准、上游项目文档/**源码**、厂商规格、公告与可复现实验；对每个机制结论，先取得逐字素材（源码片段、规范原句、日志/错误串、命令输出）并记录 file:line 与版本（commit/tag），再动笔。写不出函数级调用链或文件级路径的机制，要么继续补料，要么降级为背景陈述、不得占据技术详解小节。
3. 按结构起草：摘要给结论；背景与现状给标准、上游与国内现状；技术详解逐机制按“调用链 + 锚点 + 失败模式 + 逐字片段 + 验证方法”写足深度；故障定位速查给症状到验证的映射；总结与展望给判断与方向；附录 A/B/C 分别承载结论依据对照、检查验收清单、方法与局限。
4. 在发布前运行：

```bash
python3 skills/document/scripts/validate_research_report.py <report.md> --profile auto
python3 skills/document/scripts/publish.py --root . --validate
```

`--profile auto` 按 `背景与现状` 是否含国内小节自动识别档位；需要强制按某个档位检查时显式传 `technical-research` 或 `technical-research-general`。`--profile` 仅作用于技术调研报告；`文档类型` 为 `调研报告` 的文件按通用调研结构自动校验。两类文件都会被 `publish.py --validate` 纳入检查。`--json` 可用于机器可读的校验结果。未传 `--validate` 的发布命令保持原有行为，不会以新规范阻断遗留报告。

**渲染与执行的次序（重要）。** `publish.py` 会把根目录下每个 md 文件都重新生成为预览态 HTML（含外链脚本与 `assets/` 相对引用）并写入 `reports/`。因此自包含渲染必须放在**最后一次** `publish.py` 调用之后——正确顺序是「写报告 → validator 校验 → `publish.py --validate` → 渲染自包含 HTML → html_check → publish_site 发布」；渲染完成后不要再对同一根目录运行 `publish.py`，否则自包含产物会被覆写成预览态，且可能被 publish_site 直接发布出去（线上表现为图片 404、出现外链脚本）。

5. 渲染完成后执行实时上传（个人网站归档）：`python3 skills/document/scripts/publish_site.py reports/<report>.html --summary "一句话摘要" --tags RISC-V,Linux`。脚本提交并推送站点仓库，GitHub Actions 随后自动部署；发布完成以脚本输出的线上 URL 可访问为准（详见下节「发布到个人网站（实时）」）。

**生效时间。** 本节结构与语言规范（2026-10-10 版）及源码级深度门槛自 2026-10-10 起对新建与重写报告生效；此前已发布的旧结构报告保持原状态，待其下一次升版时按新标准重写。2026-10-13 增补 `调研报告`（通用调研）类型及其校验；既有两类报告不受影响。
