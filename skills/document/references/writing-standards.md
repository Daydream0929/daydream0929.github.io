# 写作风格细则（彭博社/BBC 新闻体 × 工程文档）

文字规范参照彭博社、BBC 等主流媒体的写作方法：这些媒体每天让千万非专业读者看懂专业内容，靠的不是降低信息密度，而是清晰的表达纪律。技术调研同样如此——要让读者看懂，逻辑必须清晰。

## 动笔前（think-first 三问）

这份文档回答什么问题？什么材料能定论？已经知道什么？三个答案没想清前不写第一段。

## 段落与结构纪律（新闻体核心）

1. **倒金字塔**：每一章、每一段，最重要的信息放在最前面。读者的注意力从上到下递减，按重要性排序内容，不按你调研的时间顺序。
2. **5W 导语**：每章第一句回答核心问题——是什么、多大程度（数字）、何时、对谁、为什么重要。读者只读每章第一句也能拼出全貌。
3. **一段一观点**：一段只说一件事。一段里出现"同时""另外"，就该拆段。
4. **短句主动**：句子平均不超过 25 字（中文），主动语态为主。一句话说不完，就拆成两句。
5. **"So what" 测试**：每节写完自问"读者为什么在乎"。答不上来的节删掉。

## 报告语言纪律（2026-10-10 起，正文强制）

报告的读者是工程师，不是审稿人。写作时遵守三条：

1. **不写报告关于自己的话**。正文不出现"本文以……为准绳""读者可自行验证""证据不足"这类元话语；检索方法、来源筛选、版本锁定方式统一写进 `附录 C：研究方法与局限`。
2. **不用 Meta 词汇**。下列词在正文一律替换：

   | 不要写 | 改写为 |
   | --- | --- |
   | 契约（逐级契约、硬契约、交接契约） | 约定 / 接口 / 要求（逐级交接要求、入口要求） |
   | 证据、证据等级、一手证据 | 依据 / 来源 / 源码 / 规范原文 / 上游文档 / 实测 |
   | 可证伪、主张 | 结论 / 判断 / 可验证的结论 |
   | TL;DR | 摘要 |
   | 可靠性标记、【C】【S】【P】等前缀 | 直接写结论；来源用 `[Snn]` 与自然句式交代 |

3. **来源自然化**。写"按 OpenSBI v1.9 源码，……[S02]"或"SBI v3.0 规定……[S01]"，不写"证据等级 A、来源 [S02]"式注记。错误串、日志、命令保持逐字，方便 grep。

小节标题同样不要方法词："源码级追踪""深度透视""全解析"不进入标题；`技术详解` 可用副题说明范围（如"技术详解：从加电到 init"）。

## 表达习惯

- **术语即用即释**：专业词第一次出现就用一句话解释，或者链接到术语说明。读者不该停下来猜。
- **数字带语境**："3 倍"必须写成"相对 XX 基线、在 XX 条件下 3 倍"。孤立的数字不可解读。
- **具体胜过抽象**："编译时间增加约 40 秒"优于"编译时间显著增加"；"2026-05-05 合入 master"优于"近期合入"。
- **不用比喻代替解释**：比喻只能装饰已解释的机制，不能替代解释。
- **结论先行、理由随后**：先给判断，再给依据链；不要让读者陪你想。
- **平实工程语言**：对营销话术零容忍——"业界领先""大幅提升""生态完善"这类词出现即重写。

## 核心内容的深度与清晰度（机制章节标准）

机制章节的深度不来自名词密度，而来自可复核的具体事实。判断标准：读完这一段，读者能否复述"先发生什么、由谁触发、在什么条件下成立"，并且能自己找到源码或日志核对。

**源码级四件套（每个「技术详解」小节必答）：**

1. **调用链**：从入口到出口的可复述序列，环节带真实函数/标签名与文件（如 `_start (fw_base.S) → fw_save_info → sbi_init (sbi_init.c)`）；跨系统交接要写清寄存器与内存约定（谁把什么放进哪个寄存器、写到哪个地址）。
2. **数据结构与字段**：寄存器位、结构体字段、取值与默认值（如 `mstatus.MPP`、`struct fw_dynamic_info` 的 `next_addr/next_mode`），而不是只提对象名称。
3. **逐字片段**：关键行为用围栏代码块给出来源片段（带文件路径与版本注释）；错误串、日志、状态打印保持原文可 grep（如 `"No working init found.  Try passing init= option to kernel."`）。
4. **验证与复现**：给出可复制执行的命令或观测方法（串口字符串、`memblock=debug`、`scause/stval`、JTAG 断点），并写明通过/失败判据。

- **讲序列，不讲名词**：先用一条按时间或依赖排序的步骤链把过程说清（"内核在 rest_init() 中派生 kernel_init，待其完成解包后 exec 用户态 init"），再解释每步的输入输出；只罗列概念名词不算讲清机制。
- **给具体锚点**：函数名、寄存器、命令行、日志字符串、文件路径、版本号，至少三类同时出现；锚点是校验器强制的门槛（每小节 ≥12 个锚点、≥2 个函数/文件锚点、≥2 处行内代码）。
- **必答"为什么"**：每个非显然的设计都要有一句动因解释——它解决了什么问题，去掉它会怎样。
- **必答"坏了什么样"**：写明失败模式与可观察症状（静默挂起、panic 文案、循环重启），错误串保持原文。只写正常路径的报告支撑不了排障。
- **图后给读图要点**：每张图后用 2–4 句说明"这张图成立的条件、该看哪条边或哪个排序"，不把图丢给读者自己猜。
- **表格带口径**：表名前或引言中一句话交代版本、日期、样本或测量条件。
- **密度自检**：每段写完自问"这段给出了哪个新的具体事实"；答不出就删掉或补事实。

**按未完成处理的写法（反例）：**

- 只复述官方文档的结论性句子（"SPL 负责初始化 DDR 并加载下一级"），没有函数名、文件、配置项或错误串。
- 用"三种形态/四个阶段/两层结构"之类的分类学代替时序与状态机；读完不知道任何一步输入什么、输出什么。
- 失败模式写成"可能出错/可能失败"，不给可观察症状、错误串或异常码。
- 验证条件写成"用 QEMU 验证"级别的空话，不给命令、参数与预期输出。
- 引文转述函数名、寄存器名、错误串（翻译或改写），导致读者无法 grep 回原文。

## 资料与数据的呈现

- 表格承载数据，散文承载判断；不把数据写成段落。
- 每个技术事实后跟一句"**工程含义**"。
- 可复现：指向 provenance 文件与精确命令行；不可追溯的数字不发布——它与错误数字不可区分。
- 结论按依据强度分组，不按数值大小排序——未核实猜测不与确认测量并列。
- 被推翻的结论保留记录（原地说明被推翻），不静默替换。
- 发现错误**原地修正**：改文档本体 + 附录 C 的修订记录（版本—日期—变更）+ 必要时在正文单列说明。
- 方法局限、未核实清单、时效性说明统一写在 `附录 C：研究方法与局限`，不在正文穿行。

## 读者画像适配

默认读者：RISC-V CPU 软件性能优化工程师。关心指令级细节（ISA 扩展、内存模型、微架构代价），关心"能不能用、怎么用、什么时候快、什么时候慢"；对营销话术零容忍，对显式标出的数据缺口容忍度高。换读者画像时先调整：术语密度、摘要的决策指向、工程含义的落点。
